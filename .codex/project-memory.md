## Actual Service Boundaries From Code
- `apps/gateway`
  - HTTP entry only.
  - Connects to `auth`, `user`, `relation`, `msg`, `group` via gRPC.
  - Installs global logger, Redis, async pool, MinIO, IP limiter, device-active syncer at `GatewayApp.Run`.
  - Redis and MinIO are optional degradable dependencies here.
- `apps/auth`
  - Owns account registration/login/password reset/verify code/device token lifecycle.
  - Writes outbox events on key account mutations.
  - Runs Redis retry consumer and `profile_display_changed` Kafka consumer.
  - Redis is degradable; falls back toward MySQL-only for some behavior.
- `apps/user`
  - Current code is profile-centric, not old “user + relation” mixed service.
  - Owns profile read/update, batch profile lookup, search, QR code token mapping, internal profile RPCs.
  - Runs `user_created` and `account.deleted` consumers.
- `apps/relation`
  - Owns friend apply/friend list/sync/delete/remark/tag/blacklist.
  - Relation semantics are mostly single-direction records in `user_relation`, with service-level orchestration.
  - Runs `account.deleted` consumer.
- `apps/group`
  - Not just read-only.
  - Already implements create/dismiss/update info/transfer owner/update member role/add member/remove member/list members/list user groups/check member/get member ids.
  - Has substantial repository logic: DB transactions, Redis caches, singleflight, async cache patching, outbox/event-style writes.
  - Runs `group.cache` projector consumer.
- `apps/msg`
  - Message service with DDD-ish split:
    - `internal/domain/message`
    - `internal/domain/conversation`
    - `internal/usecase`
  - Strongly depends on Redis and Kafka; no graceful nil Redis path in providers.
  - Talks to `group` and `relation` via gRPC for permission and group-member related behavior.
- `apps/connect`
  - WebSocket access + internal gRPC push surface.
  - Maintains connection manager and Redis routing table.
  - Can degrade if Redis or auth-device gRPC is unavailable.
  - Requires `CONNECT_SELF_GRPC_ADDR` at runtime for route cleanup and routing identity.
- `apps/message-push`
  - Consumes `msg.push` from Kafka.
  - Reads routes from Redis, queries group members from `group-service`, calls `connect` via gRPC.
  - Has real routing logic for `MSG_PUSH`, `MSG_RECALL`, `MSG_MARK_READ`, `MSG_READ_RECEIPT`.

## Message Chain As Implemented
- Main send path:
  `Gateway -> msg gRPC -> msg usecase/domain -> Kafka(msg.push) -> message-push consumer -> connect gRPC -> WebSocket`
- `apps/msg/internal/usecase/send_message_workflow.go`
  - checks permission through relation/group clients
  - creates message with idempotency and seq
  - upserts sender conversation
  - upserts receiver conversation for P2P
  - updates group conversation hot data for group chat
  - best-effort ensures group member conversation rows
  - publishes `MsgPushEvent` asynchronously via `async.RunSafe`
- `message-push` behavior:
  - P2P `MSG_PUSH` / `MSG_RECALL`: deliver to receiver routes + sender’s other devices
  - Group `MSG_PUSH` / `MSG_RECALL`: expand group members except sender, then also sync sender’s other devices
  - `MSG_MARK_READ`: sync only to same user’s other devices
  - `MSG_READ_RECEIPT`: notify only receiver side routes
  - Ack required only for `MSG_PUSH` with `seq > 0`
- `apps/message-push/internal/consumer/consumer.go`
  - only four event types are handled right now: `MSG_PUSH`, `MSG_RECALL`, `MSG_MARK_READ`, `MSG_READ_RECEIPT`
  - proto decode / validation / unsupported-type failures are treated as permanent skip, not retried
  - route/connect/group failures are treated as retriable and retried locally with short backoff
  - local retry policy is finite: 3 attempts with `100ms / 300ms / 800ms`
  - stage-1 behavior still commits Kafka offset even after retries fail, to avoid one bad message blocking the whole partition
  - if at least one target device push succeeds, the event is considered handled even if some device pushes fail
  - routes are deduplicated by `user_uuid + device_id` before calling connect

## Msg Domain Details
- `apps/msg/internal/domain/message/service.go`
  - `CreateMessage` uses Redis idempotency lock + result cache, then Redis seq allocation, then DB insert.
  - If Redis idempotency path degrades, DB unique index on sender/device/client-msg-id is fallback.
  - `conv_id` rules:
    - group: `target_uuid`
    - p2p: `p2p-{sorted(uuid_a,uuid_b)}`
  - `msg_id` uses ULID, not snowflake.
  - Pull direction supports forward/backward by seq anchor.
  - `PullMessages` returns `limit+1` then trims to implement `hasMore`.
  - `PullMessages` filters out `status=2` and anything `seq <= clear_seq`.
  - `GetMaxSeq` is "largest allocated seq" semantics, not guaranteed "largest persisted seq"; seq holes are possible if Redis alloc succeeds but DB write fails.
  - Recall rules:
    - sender can recall within recall window
    - group admin/owner can recall others without time limit if group role querier says role >= 1
- `apps/msg/internal/usercli/permission_checker.go`
  - Message send permission is enforced before persistence in the send workflow.
  - P2P send rejects self-send.
  - P2P send checks both blacklist directions:
    - sender blacklisted peer -> `CodeYouBlacklistPeer`
    - peer blacklisted sender -> `CodePeerBlacklistYou`
  - P2P send then requires `relation.FriendService.CheckIsFriend`.
  - Group send requires `group.GroupService.CheckGroupMember` to return `is_member=true`.
  - Missing relation/group client dependencies are treated as internal errors, not fail-open.
- `apps/msg/internal/groupcli/client.go`
  - msg-service asks group-service for member role through `CheckGroupMember`.
  - group role mapping for message recall is `0=member`, `1=admin`, `2=owner`, `-1=not in group`.
  - group member fan-out uses `GetGroupMemberIds` and de-duplicates UUIDs client-side.
- `apps/msg/internal/handler/msg_handler.go`
  - handler is thin but enforces identity hard:
    - `from_uuid` / `owner_uuid` are taken from auth context, not trusted from request body
    - `device_id` for send/recall/read-sync is taken from request context when available
  - `PullMessages` and `GetMessagesByIds` first require a conversation row for the caller
  - conversation access check currently returns `clear_seq`, so deleted conversations still allow post-clear incremental history reads
- `apps/msg/internal/domain/message/repository_impl.go`
  - Redis keys are authoritative for seq allocation.
  - `GetMaxSeq` prefers Redis and falls back to DB `MAX(seq)`.
- `apps/msg/internal/domain/conversation/service.go`
  - Conversation preview is stored as JSON payload, not plain text only.
  - P2P unread is maintained per-recipient row.
  - Group unread is derived dynamically from `group_conversation.max_seq - read_seq`.
  - `EnsureGroupMembersConv` exists to lazily initialize group conversation rows.
- `apps/msg/internal/domain/conversation/repository_impl.go`
  - P2P and group list queries are split.
  - Group conversation list joins `group_conversation` and maps `gc.last_msg_at` onto `UpdatedAt` for sort/merge.
  - Group full-list cursor uses `gc.last_msg_at`, but incremental filter still keys off personal row `conversation.updated_at` so delete/settings changes are visible.
  - `UpdateReadSeq` uses SQL `GREATEST` to keep `read_seq` monotonic across devices.
  - Delete conversation is logical:
    - `status=1`
    - `clear_seq=max_seq`
    - `read_seq=max_seq`
    - `unread_count=0`
  - Later new messages reactivate the row through upsert.
- `apps/msg/internal/usecase/mark_read_workflow.go`
  - DB read-state update is the only strong step
  - self-device sync event `MSG_MARK_READ` is best-effort and goes only to the same user’s other devices
  - P2P read receipt `MSG_READ_RECEIPT` is emitted separately to the peer
  - marshal/Kafka publish failures do not roll back DB read state
- `apps/msg/internal/usecase/recall_message_workflow.go`
  - DB `status=1` update is authoritative
  - Kafka `MSG_RECALL` publish is best-effort only
  - if recall event publish fails, next history pull still shows recalled message state

## Connect Service Details
- `apps/connect/internal/handler/ws_handler.go`
  - WebSocket endpoint is `GET /ws?token=...&device_id=...`.
  - Handshake auth errors are returned as HTTP JSON before upgrade.
  - Origin policy comes from `CONNECT_ALLOWED_ORIGINS`:
    - unset: only same-origin or empty Origin
    - `*`: allow all, intended for local development
    - comma-separated exact origins: allowlist
  - Current live WebSocket wire format is Binary protobuf, not JSON:
    - frame payload is `connect.MessageEnvelope`
    - `MessageEnvelope.data` holds type-specific protobuf bytes
    - old JSON `Envelope` helpers have been removed; live frames only keep the Binary protobuf path
  - Supported client upstream envelope types today:
    - `heartbeat` -> server replies `heartbeat_ack`
    - `message` -> TODO placeholder, server only replies `message_ack`
    - `MSG_ACK` / `msg_ack` -> parsed as `connect.MessageAck`
  - Unsupported frame type or non-binary frame returns type=`error` protobuf envelope.
- `apps/connect/internal/svc/auth.go`
  - WebSocket auth is fail-close.
  - JWT parse is not enough; if Redis exists, connect also checks stored access-token MD5 hash.
  - `claims.DeviceID` must equal query `device_id`.
- `apps/connect/internal/manager/client.go`
  - Per-connection outbound queue size is 64.
  - If enqueue fails because queue is full or connection is closed, callers treat delivery as failed and may close the socket.
  - Max inbound frame size is 1 MiB.
  - Write timeout is 5s, pong wait is 60s, ping period is 54s.
  - Write loop drains up to 16 queued frames per wake to reduce scheduling overhead under bursts.
  - ACK validation uses a per-socket delivered watermark; client ACK is rejected if seq was never successfully written to that socket.
- `apps/connect/internal/svc/lifecycle.go`
  - On connect:
    - force active sync touch
    - upsert route into Redis using `CONNECT_SELF_GRPC_ADDR`
    - enqueue async device-status-online RPC
  - On heartbeat:
    - refresh active sync and route active time
  - On disconnect:
    - delete local active cache
    - remove route from Redis
    - enqueue async device-status-offline RPC
  - Device status RPC work is queue-based and lossy under pressure by design.
- `apps/connect/internal/grpc/server.go`
  - `PushToDevice`, `PushToUser`, `BroadcastToUsers`, `KickConnection` are real working RPCs.
  - ACK metadata is derived for `MSG_PUSH`; it tries to parse embedded `msg.MsgItem` to recover `conv_id`.
  - Only `MSG_PUSH` can currently attach `conv_id` for ACK watermarking; non-`MSG_PUSH` with `ack_required` will not become recordable unless metadata gains a conv id.
  - `BroadcastToUsers` counts a user as success if at least one local device accepted the frame.
- `apps/connect/internal/svc/ack.go`
  - client ACK envelope types are `MSG_ACK` / `msg_ack`
  - ACK store is Redis-only for now
  - key dimension is `user_uuid + device_id + conv_id`
  - value is max acked seq and can only move forward
  - TTL is 30 days, aimed at short-term reliability and troubleshooting rather than permanent receipt storage
  - server replies with type `MSG_ACK_ACK`, data=`connect.MessageAckAck`
  - protocol error payload is `connect.ErrorFrame { code, message }`
- `apps/connect/internal/manager/connection_manager.go`
  - Connection registry is sharded by user hash, not a single global lock.
  - Register can replace same-user same-device old connection.
  - Shutdown closes all tracked clients gracefully first, then force closes after 1 second.

## Route Storage Details
- `apps/message-push/internal/route/repository.go`
  - Routing storage is Redis hash per user.
  - Field is `device_id`.
  - Value format is `connectGrpcAddr|lastActiveMs`.

## Group Service Details
- `proto/group/group_service.proto` is a better truth source than old docs for exposed group capabilities.
- Group service now owns four areas:
  - group profile
  - membership and role management
  - join application workflow
  - internal member checks / member-id lookup
- Create group:
  - owner identity comes only from auth context
  - empty avatar is replaced by a service-level default avatar URL
  - owner is always inserted as the first active member with role `2`
  - request member UUIDs are trimmed, de-duplicated, and owner is excluded from the invitee list
- Group write permission matrix:
  - dismiss group: owner only; repeated dismiss still checks owner
  - update name/avatar/notice: admin or owner
  - update `add_mode`: owner only
  - transfer owner: owner only; target must be an active member
  - update member role: owner only; role API can only set `member/admin`, never owner
  - admin count is capped at 10
  - add members: admin or owner
  - remove member:
    - self-leave is allowed except owner cannot leave directly
    - owner can remove any non-owner
    - admin can remove ordinary members only
    - ordinary members cannot remove/probe others
- Member lifecycle details:
  - group dismissal only changes group status; it does not bulk-delete member rows
  - removed/quit members are soft-deleted and keep history
  - adding or approving a historical member restores the old row, clears deleted state, resets role to ordinary member, and updates inviter/join time
  - already-active add/remove-like operations are mostly idempotent, but permission checks still run first where needed
- Read-side group membership:
  - `GetGroupMembers` first confirms the group is normal, then returns active members ordered by role desc, joined time asc, id asc
  - `CheckGroupMember` first verifies group status so stale `group_members` cache cannot make a dismissed group look active
  - member list reads use Redis hash + DB fallback + singleflight rebuild
- Join application flow is real and implemented:
  - `ApplyJoinGroup`
  - `CancelJoinGroupApplication`
  - `GetMyJoinGroupApplication`
  - `ListMyJoinGroupApplications`
  - `ReviewJoinGroup`
  - `ListJoinRequests`
  - `ListReviewedJoinRequests`
- `apps/group/internal/service/group_join_service.go`
  - `ApplyJoinGroup` behavior depends on `groups.add_mode`:
    - `0`: direct join, returns `joined_directly=true`, no pending application
    - `1`: create pending application, returns `apply_id`
  - applying while already an active member returns already-member semantics
  - duplicate pending application returns already-exists semantics
  - cancel only cancels the current user's own pending application; terminal applications are not rolled back
  - review action is `1=approve`, `2=reject`; only admin/owner can review
  - approving creates/restores a normal member and uses reviewer as inviter
  - rejecting only updates the application record
  - user-facing application list is enriched with group name/avatar inside group-service
  - admin-facing request lists are enriched with applicant profile inside group-service
  - page defaults: page 1, page size 20, hard cap 100
- `apps/group/internal/repository/group_join_request_query.go`
  - “my join applications” keeps all terminal states, not just pending
  - “reviewed join requests” includes approved/rejected only, excludes user-cancelled records
- `apps/group/internal/repository/group_cache_projector_repository.go`
  - `group.cache` consumer is a Redis projector, not a second business service
  - it validates minimal event payloads, then only projects final snapshots into Redis
  - `group_created` is allowed to fully create `group:info` and `group:members`
  - later incremental events mostly keep patch-if-exists semantics, especially for `group:user_groups`
  - projector never re-runs permission checks; it assumes the event already represents committed truth

## Outbox And Kafka Event Flows
- Kafka topic defaults from `config/kafka.go`:
  - redis retry: `redis-retry-queue`
  - user-created: `user_created`
  - profile display changed: `profile_display_changed`
  - account deleted: `account.deleted`
  - message push: `msg.push`
  - group cache projector: `group.cache`
- `pkg/outbox` is CDC-oriented:
  - business transactions insert rows into `outbox_events`
  - Debezium/Kafka Connect is expected to move events to Kafka
  - consumers use `idempotent_events` with unique `(event_type,event_id)` for consumer-side dedupe
- Account/profile event payloads live in `pkg/accountevent`.
  - `user_created`: initializes `user_profile` in user-service
  - `profile_display_changed`: lets auth-service update redundant login display fields
  - `account.deleted`: lets user/relation clean service-local data after account deletion
- Group event payloads live in `pkg/groupevent`.
  - all group cache projection actions share event type/topic `group.cache`
  - action determines Redis projection behavior
  - `entity_id` is `group_uuid`, giving same-group ordering when Kafka Connect preserves keying
- Event decoders intentionally support several wrapped payload shapes.
  - raw JSON payload
  - JSON string containing JSON
  - Debezium-like wrappers under `payload`, `after`, or `data`
  - recursion stops after depth 4
- Reliable event consumers use `kafka.NewManualCommitConsumer`.
  - offset is committed only when handler returns nil
  - decode/invalid payload errors usually log and return nil so bad messages do not block the partition
  - real processing errors return error so the same message is retried after `ErrorBackoff`
- Current outbox consumers:
  - `apps/user/internal/consumer/user_created_consumer.go`: `user_created:user-service`
  - `apps/user/internal/consumer/account_deleted_consumer.go`: `account.deleted:user-service`
  - `apps/relation/internal/consumer/account_deleted_consumer.go`: `account.deleted:relation-service`
  - `apps/auth/internal/consumer/profile_display_changed_consumer.go`: `profile_display_changed:auth-service`
  - `apps/group/internal/consumer/cache_projector.go`: `group.cache:group-cache-projector`
- `message-push` is different from outbox projector consumers.
  - it consumes `msg.push` with its own loop and finite local retry
  - stage-1 behavior commits offset even if local retries eventually fail

## Account/Profile Lifecycle Events
- Register path:
  - `auth.Register` writes `user_account`
  - same DB transaction writes outbox `user_created`
  - user-service consumes it and calls internal `CreateProfile`
  - `CreateProfile` is idempotent: existing profile is reused
- Profile update path:
  - user-service updates `user_profile`
  - same transaction writes `profile_display_changed`
  - auth-service consumes it and calls internal `UpdateLoginDisplay`
  - auth repository updates only non-empty `login_nickname` / `login_avatar`
- Account deletion path:
  - auth-service verifies password
  - same DB transaction soft-deletes `user_account` and writes `account.deleted`
  - then auth-service clears all device tokens/sessions through device repo
  - user-service consumes `account.deleted` and deletes `user_profile`
  - relation-service consumes `account.deleted` and soft-cleans relations/apply records plus related caches
- Account deletion response currently reports a 30-day recovery deadline, but the code path is still soft-delete + cleanup event; read restore behavior before assuming recovery is implemented.

## Group Cache Event Mapping
- `apps/group/internal/repository/group_event_mapper.go` writes `group.cache` outbox events inside the same DB transaction as group writes.
- Event IDs are generated in the mapper if missing, so every group cache event can be idempotently consumed.
- Action-to-payload shape:
  - `group_created`: group snapshot + initial member snapshots + user UUIDs
  - `member_added`: group snapshot + changed member snapshots + user UUIDs
  - `member_removed`: group snapshot + single removed user UUID
  - `group_dismissed`: group snapshot + active member UUIDs captured inside the transaction
  - `group_info_updated`: latest group snapshot only
  - `owner_transferred`: latest group snapshot + affected member snapshots
  - `member_role_updated`: latest group snapshot + affected member snapshots
  - `join_request_created`: join request snapshot
  - `join_request_reviewed`: join request snapshot, used to remove pending cache entry
  - `join_request_canceled`: join request snapshot, also removes pending cache entry
- The mapper intentionally sends final snapshots rather than field diffs so the projector does not need to query MySQL again.

## Gateway Entry And Middleware
- Route setup truth is `apps/gateway/internal/router/router.go`.
- Middleware order matters:
  - recovery
  - trace logger
  - client IP extraction
  - request logger
  - Prometheus
  - CORS
  - per-route timeout
  - global IP blacklist/rate limit
  - JWT auth only on `/api/v1/auth`
  - user rate limit after JWT auth
- Gateway request timeout budget is explicitly mapped per route.
  - default timeout is 2s
  - health/metrics have no timeout wrapper
  - heavier routes such as search/avatar/send/delete-account use 3s
  - timeout middleware writes `CodeTimeoutError` if no response was written
- JWT middleware:
  - requires `Authorization: Bearer <token>`
  - parses JWT locally
  - stores `user_uuid` and `device_id` in `ctxmeta`
  - touches device-active syncer best-effort
  - does not perform Redis token hash validation; connect-service does the stricter Redis token check for WebSocket
- Client IP middleware priority:
  - `X-Real-IP`
  - first value of `X-Forwarded-For`
  - `Client-IP`
  - `X-Client-IP`
  - Gin `ClientIP`
  - it writes canonical `client_ip` into both Gin context and request context
- Gateway rate limiting is Redis-backed token bucket and fail-open.
  - Redis nil/error/timeout means request is allowed
  - global IP default in router: 10 rps, burst 20
  - authenticated user default: 100 rps, burst 200
  - sensitive user operations use stricter 2 rps, burst 5
  - `/health`, `/metrics`, and OPTIONS bypass global guards
- HTTP response shape is centralized in `pkg/result`.
  - success and business errors usually return HTTP 200 with business `code` in JSON
  - server errors `30000-39999` map to HTTP 500
  - auth middleware explicitly returns HTTP 401 for missing/invalid token
- Gateway outbound gRPC connections use `newGatewayConnection`.
  - metadata propagation
  - method timeout
  - exact service-name retry config
  - optional method-scoped `x-internal-caller`
  - circuit breaker
  - gRPC metrics observer
  - max receive message size 4 MiB
- Gateway circuit breaker defaults:
  - `MaxRequests=3`
  - interval 15s
  - open timeout 45s
  - trips only after at least 5 requests and failure ratio >= 50%
- Gateway only injects internal-caller `gateway` for `/auth.InternalAuthService/FindAccountByEmail` on its auth connection.

## Data Model Truths From Schema And Models
- `config/mysql/001_schema.sql` is the most reliable source for live table/index shape.
- Identity and profile are split in storage, not just service naming:
  - `user_account` belongs to auth-domain and stores login identity, status, password hash, redundant login nickname/avatar.
  - `user_profile` belongs to user-domain and stores nickname/avatar/gender/signature/birthday/qrcode token.
- Relation model is explicitly single-direction:
  - table `user_relations`
  - unique key `(user_uuid, peer_uuid)`
  - status `0=friend`, `1=blacklist-from-friend`, `2=deleted`, `3=blacklist-from-nonfriend`
  - delete friend is not "delete both rows automatically" at repository level.
- Friend application truth is still `apply_requests` with `apply_type=0`.
- Group join application truth is separate `group_join_requests`, not reused from `apply_requests`.
  - status `0=pending`, `1=approved`, `2=rejected`, `3=cancelled`
- Group membership truth is `group_members`.
  - role `0=member`, `1=admin`, `2=owner`
  - status `0=normal`, `1=quit`, `2=kicked`, `3=pending`
- Group profile truth is `groups`.
  - status `0=normal`, `1=disabled`, `2=dismissed`
  - `member_cnt` is maintained explicitly and patched in write transactions.
- Device session truth is `device_sessions`.
  - unique key `(user_uuid, device_id)`
  - service code uses statuses `0=online`, `1=offline`, `2=logged_out`, `3=kicked`
- Conversation and message schema details matter:
  - `conversation.type` is `1=P2P`, `2=GROUP`
  - `conversation` unique key is `(owner_uuid, target_uuid)` rather than `(owner_uuid, conv_id)`
  - watchlist: conversation repository methods query by `owner_uuid + conv_id` and their `OnConflict` comments/columns mention `(owner_uuid, conv_id)`.
  - current MySQL schema still only declares unique `(owner_uuid, target_uuid)`; because current writes set `target_uuid` consistently, MySQL duplicate-key upsert can still work, but align the index/queries before changing DB dialect, migrations, or conversation identity semantics.
  - `message` unique key on `(client_msg_id, from_uuid, device_id)` is the DB fallback for send idempotency
  - `message.status` is `0=normal`, `1=recall`, `2=delete`
  - `message.msg_id` is global unique; `conv_id + seq` is per-conversation order
  - `conv_id` and `message.conv_id` are `VARCHAR(128)` in schema
- `group_conversation` is a real hot table, not derived on the fly.
  - one row per group
  - stores `max_seq`, `last_msg_id`, `last_msg_preview`, `last_msg_at`
  - group list sort/unread logic depends on it

## Redis Keys And Cache Contracts
- Current key names from `consts/redisKey` are the real contract:
  - verify code: `user:verify_code:{email}:{type}`
  - verify email minute limit: `user:verify_code:1m:{email}`
  - verify email 24h limit: `user:verify_code:24h:{email}`
  - verify IP hour limit: `user:verify_code:1h:{ip}`
  - access token: `auth:at:{user_uuid}:{device_id}`
  - refresh token: `auth:rt:{user_uuid}:{device_id}`
  - profile: `user:profile:{uuid}`
  - QR token -> user: `user:qrcode:token:{token}`
  - QR user -> token: `user:qrcode:user:{user_uuid}`
  - device info: `user:devices:{user_uuid}`
  - device active: `user:devices:active:{user_uuid}`
  - routing: `user:routing:{user_uuid}`
  - friend hash: `user:relation:friend:{user_uuid}`
  - blacklist zset: `user:relation:blacklist:{user_uuid}`
  - friend apply pending: `user:apply:pending:{target_uuid}`
  - friend apply unread: `user:notify:friend_apply:unread:{uuid}`
  - group info: `group:info:{group_uuid}`
  - group members: `group:members:{group_uuid}`
  - group join pending: `group:join_requests:{group_uuid}`
  - user groups: `group:user_groups:{user_uuid}`
  - gateway IP blacklist: `gateway:blacklist:ips`
  - gateway user rate limit: `gateway:rate:limit:user:{user_uuid}`
  - gateway IP rate limit: `rate:limit:ip:{ip}`
  - msg seq: `msg:seq:{conv_id}`
  - msg idempotent: `msg:idempotent:{from_uuid}:{device_id}:{client_msg_id}`
  - msg ack: `msg:ack:{user_uuid}:{device_id}:{conv_id}`
- Important TTLs:
  - verify code rate limit: 1 minute / 24 hours / 1 hour by key family
  - device info: 60 days
  - device active and friend-apply unread: 7 days
  - user profile: 1 hour; empty profile: 5 minutes
  - friend relation / blacklist / group members / group join requests / user group list: 24 hours
  - QR code: 48 hours
  - message idempotent result: 10 minutes
  - device message ACK: 30 days
- Message-type truth from `model/message_const.go`:
  - normal business messages are `1-99`
  - currently implemented: text/image/voice/video/file/location/system
- Empty placeholders are used deliberately and differ by structure:
  - string caches often use `"{}"` for "known empty / not found"
  - hash/zset caches often keep `__EMPTY__` sentinels because Redis removes truly empty collections
  - group cache uses both patterns: `groupInfoEmptyValue="{}"`, `groupMembersEmptyField="__EMPTY__"`, `userGroupsEmptyValue="__EMPTY__"`
- Common cache write strategy across group/relation/auth-side repositories:
  - DB remains source of truth
  - write path first commits DB
  - Redis usually does patch-if-exists only
  - if key is missing, code prefers read-path full rebuild later rather than creating a partial cache now
- Common cache repair strategy:
  - read miss triggers DB fallback and async/full rebuild
  - Redis `WRONGTYPE` means "delete polluted key and rebuild later"
  - hot keys use TTL jitter and occasional read-side `Expire` refresh instead of every read touching TTL
- Specific repositories worth remembering:
  - user profile cache uses `user:profile:{uuid}` and empty placeholder `"{}"`
  - friend cache is one Redis Hash per user; each field is peer uuid with JSON meta `{remark, group_tag, source, updated_at}`
  - blacklist cache is one Redis ZSet per user; member is peer uuid, score is blacklist timestamp
  - friend apply pending cache is one Redis ZSet per target user; member is applicant uuid, score is created time
  - group members cache is one Redis Hash per group; each field is user uuid with JSON `{role, joined_at}`
  - user group list cache is one Redis ZSet per user; member is group uuid, score is group updated time
- Route storage contract:
  - `user:routing:{user_uuid}` is a hash
  - field is `device_id`
  - value is `connectGrpcAddr|lastActiveMs`
  - read side filters stale routes by TTL window even if Redis still contains them

## Infra Contracts That Affect Code Changes
- `pkg/apperr` is not just an error helper; it is the cross-service biz-code transport.
  - `ToStatus` writes biz code into gRPC `ErrorInfo` metadata `biz_code`
  - `FromStatus` first tries `ErrorInfo`, then message parse, then gRPC code mapping
  - `Sanitize` preserves biz code/message while stripping internal details
- `pkg/grpcx.NewClient` has a fixed interceptor order:
  1. metadata
  2. internal-caller
  3. timeout
  4. logging
  5. observers
  6. extra interceptors
- Internal gRPC caller contract is strict:
  - internal-only methods require metadata `x-internal-caller`
  - caller value must be allowlisted per full gRPC method
  - external methods reject requests that carry this header
- Retry config on gRPC clients must use exact protobuf service names, not ad hoc labels.
- `pkg/async` has two distinct concurrency modes:
  - `RunSafe`: background work, detached from parent cancellation via `context.WithoutCancel`, runs through non-blocking ants pool
  - `Group`: request-scoped fan-out, inherits parent cancellation/deadline and does not use the background pool
- Async pool behavior to remember:
  - pool is non-blocking only
  - rejected submissions are counted
  - recommended timeouts are standardized as `AsyncRedisTimeout`, `AsyncRedisPipelineTimeout`, `AsyncDBTimeout`, `AsyncRetryTimeout`
- `pkg/deviceactive.Syncer` is a throttled batcher, not a direct write-through helper.
  - sharded "last touch" map avoids over-updating one device
  - pending batch map is flushed periodically
  - failed batches merge back into pending instead of being dropped
  - config normalization guarantees `updateInterval < onlineWindow` and `flushInterval <= updateInterval`
- `pkg/outbox.InsertEvent` only writes the DB row inside the business transaction.
  - Debezium / Kafka Connect is expected to ship it onward
  - do not invent extra "publish success" state machines around outbox writes without checking existing CDC assumptions

## Relation Service Notes
- Friend and blacklist logic are implemented in `apps/relation/internal/service`.
- Friend flow includes:
  - send apply
  - inbox/outbox list
  - handle apply
  - unread count and mark read
  - friend list and incremental sync
  - delete friend / remark / tag
  - batch check friendship / relation status
- service-layer semantics worth remembering:
  - `SendFriendApply` checks in this order: self-check -> already-friend -> pending-apply -> target blacklisted me -> I blacklisted target
  - inbox list read will async mark loaded items as read and clear unread counter best-effort
  - `HandleFriendApply` accept path creates bidirectional friend relations transactionally; reject path is status update only
  - accept path writes remark only on handler/current-user side; opposite direction does not overwrite peer remark
  - `SyncFriendList` intentionally rolls latest version back by 2 seconds to reduce boundary misses
  - `DeleteFriend` currently deletes only current user’s directional relation, matching current single-direction model
- `GetTagList` is intentionally not implemented and returns method-not-allowed semantics.
- Blacklist service semantics:
  - self-blacklist is rejected
  - remove-blacklist first checks current state so "not in blacklist" becomes a clean biz error
  - internal `CheckIsBlacklist` does not depend on login context and is suitable for downstream service checks
- Friend repository details:
  - `CheckIsFriendRelation` checks only one direction: `user_uuid -> peer_uuid`.
  - friend cache is a Redis Hash; existence of the Hash plus absence of a field is treated as authoritative false.
  - friend Hash value stores JSON metadata: remark, group_tag, source, updated_at.
  - cache miss triggers DB lookup and async full rebuild of the user’s friend Hash.
  - empty friend list is represented with `__EMPTY__` field and short TTL.
  - `GetRelationStatus` can return `none`, `friend`, `blacklist`, or `deleted`.
  - `GetRelationStatus` uses Unscoped DB fallback so historical soft-deleted relations remain meaningful.
- Blacklist repository details:
  - blacklisting is also single-direction.
  - blacklist cache is a Redis ZSet; member is peer uuid, score is blacklist timestamp ms.
  - `status=1` means blacklisted from an existing/historical friend state and remove-blacklist restores friend.
  - `status=3` means blacklisted from non-friend state and remove-blacklist restores deleted/non-friend.
  - adding blacklist removes only current user’s friend-cache field; the opposite direction is not automatically removed.
- Friend apply repository details:
  - pending inbox cache is a Redis ZSet keyed by target user.
  - ZSet member is applicant uuid, score is created time.
  - cache hit still fetches MySQL for full apply rows because ZSet stores only applicant ids.
  - sent-apply list is MySQL-only.
  - unread apply count prefers Redis counter and falls back to DB only when Redis is nil.
  - clearing unread count deletes only the counter key; read flags are handled separately.
- `account.deleted` in relation-service:
  - soft-deletes any relation where user is either side
  - clears blacklisted_at and marks relation status deleted
  - soft-deletes related friend applications
  - invalidates friend/blacklist/apply/unread caches for affected users

## User Service Notes
- Profile service owns:
  - self profile
  - other profile
  - search
  - update profile
  - upload avatar URL
  - QR code token generation / parsing
  - batch profile lookup
- Search result intentionally returns `is_friend=false`; friend state is meant to be aggregated upstream.
- Profile read/cache behavior:
  - `GetByUUID` uses Redis first, `"{}"` as empty placeholder, then MySQL fallback and async cache fill
  - `BatchGetByUUIDs` preserves input order for existing users and skips missing users
  - batch profile cache miss writes both found profiles and empty placeholders asynchronously
- Profile write behavior:
  - `UpdateProfile` requires at least one non-zero field
  - nickname/signature/birthday/gender only update when non-empty/non-zero
  - this means empty string cannot currently clear signature/birthday through `UpdateProfile`
  - birthday must match `YYYY-MM-DD` and be a real calendar date
  - profile update and avatar update both write `profile_display_changed` outbox in the same DB transaction
  - after commit, profile cache is invalidated; failed invalidation goes to Redis retry task
- QR code behavior:
  - token is reused while `user:qrcode:user:{user_uuid}` exists
  - URL shape is hard-coded as `https://www.LCchat.top/q/{token}`
  - both `token -> user_uuid` and `user_uuid -> token` mappings use 48h TTL
  - parse only returns `user_uuid`; caller must fetch profile separately
- Internal profile service:
  - `CreateProfile` is idempotent and used by `user_created` consumer
  - `BatchGetUserCard` maxes at 200 UUIDs
  - `BatchGetPublicProfile` maxes at 100 UUIDs
- `apps/user` still registers a legacy/proto-local `user.GroupService`.
  - it only exposes `GetGroupMembers`
  - it reads `groups` / `group_members` directly from MySQL
  - current msg-service and message-push use the newer `apps/group` service instead
  - do not confuse `proto/user/group_service.proto` with the main `proto/group/group_service.proto`

## Auth Service Notes
- Register writes `user_account` and outbox event together.
- Verification code types in current auth-service:
  - `1`: register
  - `2`: login by code
  - `3`: reset password
  - `4`: change email
- SendVerifyCode flow:
  - validates email format first
  - rate limit dimensions are email per minute, email per 24h, and IP per hour
  - default limits from repo code are 1/min/email, 10/day/email, 100/hour/IP
  - code TTL is 2 minutes
  - Redis write happens before count increment and before email send
- Redis absence in auth:
  - rate-limit check is fail-open
  - verification-code reads return missing/expired semantics
  - verification-code writes fail the request
  - access/refresh token writes are hard requirements for login
- Login/login-by-code:
  - issue access + refresh token per device
  - access/refresh token writes are hard requirements
  - device session upsert is best-effort
  - device active timestamp write is best-effort
  - password login currently looks up `req.Account` by email
  - `device_id` comes from context metadata, not request body
- Refresh token validates against stored device refresh token.
  - refresh keeps the refresh token itself unchanged and only rotates access token
- Logout removes tokens and best-effort updates device status.
- ChangePassword:
  - verifies old password
  - rejects setting the same password
  - currently does not kick other devices
- ChangeEmail:
  - checks target email uniqueness before validating type-4 verification code
  - deletes consumed verification code best-effort after DB update
- DeleteAccount:
  - password confirms identity
  - soft-deletes `user_account` and writes `account.deleted` outbox in one transaction
  - then deletes all device login state
  - response recovery deadline is computed as deletion time + 30 days
- Internal auth service semantics:
  - `FindAccountByEmail` returns `Found=false` on miss instead of business error
  - `FindAccountByTelephone` is still intentionally not implemented
  - `UpdateLoginDisplay` is the auth-side sync point for profile nickname/avatar redundancy
  - `BatchCheckAccountStatus` is the internal bulk account existence/status API for other services
- Device service semantics:
  - device list is assembled from device-session snapshot + per-device active timestamps
  - online status is derived from both session status and `pkg/deviceactive.OnlineWindow()`
  - `KickDevice` cannot target the current device
  - `UpdateDeviceStatus` only accepts `online` and `offline`; missing session is treated idempotently
  - batch online-status query hard-caps request size at 100 users
- auth internal-caller whitelist currently matters for cross-service calls:
  - `/auth.InternalAuthService/FindAccountByEmail`: `gateway`, `relation-service`
  - `/auth.InternalAuthService/FindAccountByTelephone`: `gateway`
  - `/auth.InternalAuthService/UpdateLoginDisplay`: `user-service`
  - `/auth.InternalAuthService/BatchCheckAccountStatus`: `relation-service`, `group-service`
