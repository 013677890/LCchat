# 配置说明

本文整理当前项目的关键环境变量、端口和依赖关系。事实来源为 `deploy/env/chatserver.env.example`、`docker-compose.yml` 和各服务启动配置。

## 1. 配置来源

| 来源 | 用途 |
| --- | --- |
| `deploy/env/chatserver.env.example` | 本地与容器运行的标准模板。 |
| `deploy/env/chatserver.env` | 本地实际运行配置。 |
| `docker-compose.yml` | 容器内服务默认覆盖值。 |
| 各服务 `cmd` / `config` | 代码默认值与运行时回退。 |

原则：

1. 文档中只写字段语义，不写真实敏感值；
2. 真实账号、密码、SMTP 授权码只能写入本地 `.env` 或部署平台；
3. 变更环境变量时必须同步更新模板和本文。

| `KAFKA_MSG_GROUP_MEMBERSHIP_PROJECTOR_CONCURRENCY` | msg membership projector 每进程独立 Reader 数，默认 `3`；规则同上。建议等于 partition 数；大于 partition 时多余 worker 空闲。 |
| `KAFKA_AUTH_PROFILE_DISPLAY_CHANGED_CONSUMER_CONCURRENCY` | auth 资料展示事件 Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_AUTH_REDIS_RETRY_CONSUMER_CONCURRENCY` | auth Redis 补偿 Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_USER_CREATED_CONSUMER_CONCURRENCY` | user 注册事件 Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_USER_ACCOUNT_DELETED_CONSUMER_CONCURRENCY` | user 注销事件 Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_USER_REDIS_RETRY_CONSUMER_CONCURRENCY` | user Redis 补偿 Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_RELATION_ACCOUNT_DELETED_CONSUMER_CONCURRENCY` | relation 注销事件 Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_RELATION_REDIS_RETRY_CONSUMER_CONCURRENCY` | relation Redis 补偿 Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_MSG_PUSH_CONSUMER_CONCURRENCY` | msg.push Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_REALTIME_PUSH_CONSUMER_CONCURRENCY` | realtime.push Pool 的 Reader 数，默认 `3`。 |
| `KAFKA_CONNECT_URL` | Kafka Connect REST 地址。 |
| `DEBEZIUM_CONNECTOR_NAME` | Debezium 连接器名称。 |
| `DEBEZIUM_TOPIC_PREFIX` | Debezium topic 前缀。 |

所有 `*_CONCURRENCY` Kafka 配置都只表示本进程独立 Reader 数，不表示 partition 绑定；显式值必须为 `1～64`，非法值导致服务初始化失败。partition 由 Consumer Group rebalance 自动分配，多余 Reader 正常 idle。
| `DEBEZIUM_SCHEMA_HISTORY_TOPIC` | schema history topic。 |
| `DEBEZIUM_MYSQL_HOST` / `PORT` / `USER` / `PASSWORD` | Debezium 监听 MySQL 的连接信息。 |
| `DEBEZIUM_OUTBOX_TABLE` | Outbox 表，默认 `chat_server.outbox_events`。 |

`scripts/cdc/register_outbox_connector.sh` 先用 status GET 明确区分 connector 存在与不存在。更新已有 connector 时会调用 stop，并等待 `STOPPED` 且 tasks 清空，再 PUT 配置并 resume；已确认存在却无法调用 stop（包括 stop 返回 404）会直接失败，不猜测为旧 API 并绕过屏障。这个屏障防止 PUT 后把 status topic 中短暂残留的旧 generation `RUNNING` 误认成新配置已启动。之后只有 connector 和 task 0 都为 `RUNNING` 才返回成功。HTTP 200 但任一状态为 `FAILED` 会立即失败，超时则打印最后一次状态，不能把“REST 可访问”误判为 CDC 已就绪。

## 5. Group 缓存对账配置

| 变量 | 说明 |
| --- | --- |
| `GROUP_CACHE_RECONCILE_INTERVAL` | 全量群缓存对账的基准等待时间，默认 `6h`；每轮完成后按该基准加入 ±20% 抖动（默认实际等待 `4h48m`～`7h12m`）。只接受带单位且大于 0 的 Go duration。 |
| `GROUP_CACHE_RECONCILE_BATCH_SIZE` | ID keyset 扫描每批群数量，默认 `100`；显式配置必须为正整数。 |

服务启动后会立即执行首轮全量对账，后续轮次在上一轮结束后再等待抖动后的时间，因此不会因单轮耗时过长而重叠或积压固定 tick。两项显式配置非法时 group-service 启动失败，不接受裸秒数、旧变量名或非正数回退。

用户群 READY 缓存命中后的语义对账使用代码内固定 1 小时 Redis 租约，不提供旧变量或环境变量覆盖；修改该 TTL 时须同步更新 Redis Key 与投影架构文档。

## 9. 修改配置时的同步要求

以下变更必须同步更新文档：

1. 新增环境变量：更新 `chatserver.env.example`、本文、必要的服务文档；
2. 修改默认 topic / 端口：更新 `data/Kafka事件.md`、`ops/本地运行与手工测试.md`；
3. 修改 WebSocket 白名单或路由 TTL：更新 `api/06-WebSocket协议.md` 与相关链路文档；
4. 修改邮件、MinIO、Debezium 配置：更新对应 `ops/` 文档。
