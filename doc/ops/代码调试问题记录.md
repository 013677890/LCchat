# 代码调试问题记录

日期：2026-05-22

本文记录本轮阅读代码和 debug 时发现的问题。这里把“明确代码问题”和“业务/设计待确认问题”分开，避免把可能属于系统设计特性的行为直接改掉。

## 已直接修复的问题

### 1. go vet 报告 protobuf 测试日志复制锁值

- 位置：`pkg/realtimepush/producer_test.go`
- 现象：`t.Fatalf("payload = %#v", decodedPayload)` 会复制 protobuf 消息内部的 `protoimpl.MessageState`，`go vet ./...` 报告 `copies lock value`。
- 处理：失败日志改为只打印 `GroupUuid` 和 `Version` 字段，避免复制整个 protobuf 消息。

### 2. message-push 初始化缺失时可能静默跳过或 panic

- 位置：`apps/message-push/internal/consumer/consumer.go`
- 现象：`EventHandler` 在 `routes == nil` 时，P2P/已读回执路径会把可投递消息当作“无在线路由”直接返回 nil；外层消费者随后提交 offset，可能导致消息丢失。`sender == nil` 且已解析到路由时会空指针 panic。
- 处理：缺失路由仓储或发送器时返回 `errRetriable`，由消费重试逻辑处理；补充对应单测。

- 位置：`apps/message-push/internal/consumer/realtime_handler.go`
- 现象：`RealtimeHandler` 在 `sender == nil` 且已解析到路由时会空指针 panic。
- 处理：返回 `errRetriable`，补充对应单测。

### 3. relation 好友申请终态后待处理缓存未移除

- 位置：`apps/relation/internal/repository/apply_repository.go`
- 现象：好友申请被同意或拒绝后，MySQL 中 `apply_requests.status` 已进入终态，但 Redis `user:apply:pending:{target_uuid}` 仍保留申请人。`ExistsPendingRequest` 命中 Redis 后会继续判断“已有待处理申请”，拒绝后再次申请会被误拦截，列表也可能出现 total 与 items 不一致。
- 处理：`UpdateStatus` 和 `AcceptApplyAndCreateRelation` 成功后同步执行 patch-if-exists 的 `ZREM`，并补充同意/拒绝两个缓存一致性单测。

### 4. Snowflake 全局节点懒初始化存在并发竞争

- 位置：`pkg/util/snowflake.go`
- 现象：`GenID` / `GenIDString` 在 `node == nil` 时会懒初始化全局 `node`，但读写没有加锁。未显式初始化的服务在首批并发请求下可能触发数据竞争。
- 处理：为全局节点初始化和读取加互斥锁，保留默认 node=1 的懒初始化行为，并补充并发生成 ID 的单测。

### 5. grpcx.Run 在优雅停机时可能返回假错误

- 位置：`pkg/grpcx/runtime.go`
- 现象：收到 `ctx.Done()` 后内部会调用 `GracefulStop`，但 `server.Serve` 随后返回的 `grpc.ErrServerStopped` 会被包装成错误传给各服务 App，导致正常停机被记录为运行失败。
- 处理：`Run` 对 `grpc.ErrServerStopped` 返回 nil，并补充优雅停机单测。

### 6. gateway 消息 HTTP 入口校验比 msg proto 更松

- 位置：`apps/gateway/internal/dto/msg_dto.go`、`apps/gateway/internal/router/v1/msg_handle.go`
- 现象：`SendMessage` 允许非法 `convType`、超长 `content/clientMsgId` 继续下游；`PullMessages` 允许超过 proto 上限的 `limit`；`GetMessagesByIds` 允许空列表或空 msg_id；`UpdateConversationSettings` 在既没有 `mute` 也没有 `pin` 时会被当作成功 no-op。
- 处理：补齐 HTTP DTO binding，使其与现有 msg proto 上限和会话设置语义对齐；会话设置空补丁直接返回参数错误；新增 msg handler 单测覆盖这些入口校验。

### 7. auth 仓储写操作未检查 0 行命中

- 位置：`apps/auth/internal/repository/auth_repository.go`
- 相关位置：`apps/auth/internal/service/internal_auth_service.go`
- 现象：`UpdatePassword`、`UpdateEmail`、`UpdateLoginDisplay`、`Delete` 和 `DeleteWithOutboxEvent` 只检查 SQL 错误，没有检查 `RowsAffected`。当账号在查询与写入之间被并发注销或不存在时，调用方可能收到成功结果；其中 `DeleteWithOutboxEvent` 还会在账号未被删除时写出 `account_deleted` outbox 事件。
- 处理：这些写操作在 0 行命中时返回 `ErrRecordNotFound`；`DeleteWithOutboxEvent` 只有真实软删除账号后才写 outbox；内部登录展示回写属于异步投影，账号已不存在时按幂等成功处理，避免历史 `profile_display_changed` 事件永久重试；补充 sqlite 仓储和 service 单测覆盖缺失账号及正常写入路径。

### 8. user 资料仓储在 Redis 未注入时会 panic

- 位置：`apps/user/internal/repository/user_repository.go`
- 现象：资料读路径注释和实现意图都是“Redis 异常降级到 MySQL”，但 `GetByUUID` / `BatchGetByUUIDs` 直接调用 `r.redisClient.Get/MGet/Pipeline`。当本地测试、降级启动或依赖注入异常导致 Redis client 为 nil 时，读取资料会空指针 panic，而不是按数据库回源降级。
- 处理：资料读缓存改为 Redis client 为 nil 时直接走 MySQL；缓存回填也只在 Redis 可用时执行。二维码 token 属于强依赖 Redis 的短期映射能力，Redis 未注入时明确返回 `ErrRedis`，由 service 映射为内部错误；补充仓储单测覆盖 nil Redis 下的单查、批量查询和二维码错误。

## 业务/设计待确认问题

### 1. Gateway HTTP 鉴权不校验 Redis 中的当前 AccessToken

- 位置：`apps/gateway/internal/middleware/auth.go`
- 相关位置：`apps/connect/internal/svc/auth.go`、`apps/auth/internal/repository/device_repository.go`
- 现象：auth 服务登录/刷新会把 AccessToken 摘要写入 Redis，登出/踢设备会删除对应 token；connect 的 WebSocket 鉴权会读取 Redis 并校验当前 token 摘要。但 gateway 的 HTTP JWT 中间件只校验 JWT 签名和过期时间，然后写入 `user_uuid` / `device_id`，没有校验 Redis 中 `auth:at:{user_uuid}:{device_id}` 是否仍是当前 token。
- 影响：同一设备刷新 AccessToken 或登出后，旧 AccessToken 仍可访问 HTTP 认证接口，直到 JWT 自身过期。目前 `AccessExpire = 2h`。
- 待确认：如果这是“HTTP 入口保持无状态、只依赖 JWT 过期”的设计，需要在认证架构文档中明确；如果目标是“刷新/登出/踢设备后立即失效”，gateway 需要增加当前 token 校验，并明确 Redis 不可用时 fail-open 还是 fail-close。

### 2. JWT 签名密钥是代码常量

- 位置：`pkg/util/jwt.go`
- 现象：`JWTSecret` 固定为代码常量，未从环境变量或密钥配置读取。
- 影响：不同环境默认共享同一个签名密钥；如果默认值进入生产，任意环境签发的 token 可能在其他环境被接受。
- 待确认：是否要引入统一 `JWT_SECRET` 配置，并同步更新 auth/gateway/connect 的启动配置、部署清单和测试。

### 3. RefreshToken 存储实现、文档与辅助函数不一致

- 位置：`pkg/util/jwt.go`
- 相关位置：`apps/auth/internal/repository/device_repository.go`、`doc/architecture/账号认证与设备会话架构.md`、`doc/datas/Redis-Key设计.md`
- 现象：`RefreshAccessToken(refreshToken string)` 假设 refresh token 本身是 JWT；当前业务链路中 refresh token 是 `util.GenIDString()` 生成的 opaque token。代码里的 `StoreRefreshToken` 当前按明文写入 Redis，并在刷新时做字面量比较；但架构和 Redis Key 文档写的是 `auth:rt:{user_uuid}:{device_id}` 保存 RefreshToken MD5 摘要。
- 影响：实现和文档对安全边界的描述不一致；如果运维或安全评审按“Redis 只存摘要”理解，实际泄漏风险会被低估。未使用的 `RefreshAccessToken` 也容易被后续误接入。
- 待确认：是改代码为摘要存储并同步刷新比对，还是承认当前明文存储模型并更新文档；同时删除或重命名 JWT 刷新辅助函数。

### 4. refresh-token 接口身份字段来自请求体

- 位置：`apps/gateway/internal/router/v1/auth_handle.go`
- 相关位置：`apps/gateway/internal/dto/auth_dto.go`
- 现象：`POST /api/v1/public/user/refresh-token` 是公开接口，请求体需要传 `uuid`、`device_id` 和 `refreshToken`；gateway 将 `uuid` / `device_id` 写入 context，auth 服务再用该 context 定位 Redis 中的 refresh token 做比对。
- 影响：只要 refresh token 本身高熵、存储策略清晰且不泄漏，这个模型可以成立；但当前代码按明文存 Redis，它把身份定位能力暴露给请求体，接口日志、客户端存储和风控策略需要配套清晰。
- 待确认：是否保持当前契约，或改成 refresh token 自描述/绑定设备，减少客户端传身份字段的必要性。

### 5. 根目录存在已跟踪的大型二进制文件

- 位置：`cmd`
- 现象：根目录 `cmd` 是约 43MB 的二进制文件，并且已被 git 跟踪；同目录还有未跟踪的 `cmd.exe`。`.gitignore` 已忽略 `*.exe`，但未忽略无扩展名的 `cmd`。
- 影响：仓库体积和代码审查噪音增加，也容易把本地构建产物提交进历史。
- 待确认：是否从版本库移除该二进制，并补充忽略规则或调整构建输出目录。

### 6. 踢设备没有和 connect 断连/路由清理形成闭环

- 位置：`apps/auth/internal/service/device_service.go`
- 相关位置：`apps/connect/internal/grpc/server.go`、`apps/connect/internal/manager/connection_manager.go`、`apps/connect/internal/svc/lifecycle.go`
- 现象：auth 的 `KickDevice` 会删除 token 并把设备会话状态置为 kicked，但当前未看到它主动调用 connect-service 的 `KickConnection`。connect 侧虽然有 `KickConnection` RPC，但白名单里目前只允许 `message-push` 调用；即使调用成功，`ConnectionManager.KickDevice` 会先从 map 删除连接，再关闭连接，后续 WebSocket `onClose` 调 `Unregister` 时可能返回 false，从而跳过 `OnDisconnect` 的路由删除和状态更新。
- 影响：被踢设备的 HTTP token 立即失效与否取决于第 1 项的 gateway 设计；WebSocket 连接是否立即断开、Redis 路由是否清理也不是完整闭环。残留路由可能等待 TTL 到期，消息推送会经历一次失败/重试。
- 待确认：踢设备是否要求“立即断开在线连接”；如果要求，需要明确 auth -> connect 的调用方白名单、断连后 `OnDisconnect` 是否仍应执行，以及 route cleanup 的幂等位置。

### 7. auth HTTP / proto / service 入参契约不一致

- 位置：`apps/gateway/internal/dto/auth_dto.go`
- 相关位置：`proto/auth/auth_service.proto`、`apps/auth/internal/service/auth_service.go`
- 现象：gateway 的密码登录 DTO 中 `deviceInfo` 不是必填；auth service 也写了 nil 时补默认设备信息的逻辑。但 proto 的 `LoginRequest.device_info` 标记为 required，且 gRPC validate 在 handler 前执行，因此缺少 `deviceInfo` 的 HTTP 请求会在下游被参数校验拒绝，service 里的默认逻辑实际不可达。验证码登录的 proto 又未标记 required，行为不一致。另一个同类问题是 `RegisterRequest.nickname/telephone` 在 gateway DTO 标记为可选，但 auth proto 分别要求 `min_len=2` 和 `len=11`；`DeviceInfo.platform` 的 proto 只允许 `iOS/Android/Web/Windows/Mac`，现有 gateway 测试和客户端示例里存在小写 `ios`。
- 影响：HTTP API 表面看允许省略部分字段，实际可能被下游 gRPC validate 拒绝；不同登录方式对 `deviceInfo` 的要求不同；平台枚举大小写也容易导致客户端联调失败。
- 待确认：统一为“gateway 按 proto 做强校验”，还是由 gateway/auth 补默认值或放宽 proto；若补默认值，`platform` 默认值也要满足 proto 枚举。

### 8. msg.SendMessage 的身份字段由 handler 覆写，但 proto validate 先要求非空（已解决）

- 位置：`proto/msg/msg_service.proto`
- 相关位置：`apps/msg/internal/handler/msg_handler.go`、`apps/gateway/internal/dto/msg_dto.go`
- 现象：`SendMessageRequest.from_uuid` 和 `device_id` 在 proto 中要求非空；msg handler 又会从 gRPC metadata 中读取认证身份并覆盖这两个字段。由于 `ValidateUnaryInterceptor` 在 handler 前执行，直接 gRPC 调用方即使已带 metadata，也仍必须在请求体里填非空 `from_uuid/device_id`。gateway 当前会填，所以 HTTP 链路没问题。
- 影响：这是一个内部调用契约陷阱；未来如果有其他服务直接调用 msg-service，可能误以为 metadata 足够，结果在业务 handler 前被参数校验挡住。
- 解决（2026-07-02）：统一为 metadata 传身份。msg proto 全部请求消息移除鉴权主体字段（`from_uuid`/`device_id`/`operator_uuid`/`owner_uuid`，字段号 reserved），handler 统一从 `ctxmeta` 解析并显式传参给 usecase/domain；gateway 侧 DTO 转换不再填充身份字段。

### 9. 手机号账号能力在文档/API 描述中仍像可用能力，但服务实现显式未完成

- 位置：`apps/auth/internal/service/auth_service.go`、`apps/auth/internal/service/internal_auth_service.go`、`apps/auth/internal/service/account_service.go`
- 相关位置：`apps/gateway/internal/dto/auth_dto.go`、`apps/gateway/internal/router/v1/auth_handle.go`、`doc/api/01-认证与账号接口.md`、`doc/flows/登录注册与Token.md`
- 现象：HTTP 登录 DTO 和接口文档描述 `account` 为“邮箱或手机号”，登录流程文档也写 auth 按邮箱或手机号定位账号；但 `authService.Login` 当前只调用 `GetByEmail`，`FindAccountByTelephone` 与 `ChangeTelephone` 都显式返回 `MethodNotAllowed`。注册侧又存在 gateway 认为 `telephone` 可选、proto 认为必填、repository 注释认为迁移阶段允许为空的三方差异。
- 影响：客户端按文档使用手机号登录/换绑会失败；注册入参是否必须手机号也不清晰。
- 待确认：手机号账号能力是本阶段暂停能力，还是需要补齐查询、换绑、注册唯一性与登录路径；确认后同步 HTTP DTO、proto 与 API/流程文档。

### 10. 修改密码的 gateway 与 auth proto 长度规则不一致

- 位置：`apps/gateway/internal/dto/user_dto.go`
- 相关位置：`proto/auth/account_service.proto`
- 现象：gateway `ChangePasswordRequest` 要求旧/新密码长度 `8..16`，auth proto `ChangePasswordRequest` 要求 `6..20`；注册、登录、重置密码链路则基本是 `6..20`。
- 影响：同一个账号体系里，6-7 位或 17-20 位密码可以注册/登录/重置，但不能通过修改密码接口设置，规则不一致。
- 待确认：以 `6..20` 作为统一规则，还是提高所有密码入口到 `8..16`，并同步文档与客户端校验。

### 11. 群聊会话列表的读扩散策略与增量同步过滤条件需要明确

- 位置：`apps/msg/internal/domain/conversation/repository_impl.go`
- 相关位置：`apps/msg/internal/usecase/send_message_workflow.go`
- 现象：群消息发送时只更新 `group_conversation` 热表，并通过 `EnsureGroupMembersConv` 兜底初始化成员的个人 `conversation` 行；不会在每条群消息上更新所有成员的 `conversation.updated_at`。但 `ListGroup` 做增量同步时使用 `c.updated_at > updatedSince` 过滤，再把 `gc.last_msg_at` 映射为返回的 `updated_at`。
- 影响：如果客户端依赖“会话列表增量同步”发现离线期间群聊活跃变化，仅更新 `group_conversation` 可能不会命中个人 `conversation.updated_at` 过滤；新建但尚无消息的群、刚被加入但没有后续消息的群，也可能因为 `INNER JOIN group_conversation` 或个人 conversation 行初始化时机而不出现在 msg 会话列表里。这可能是当前“群消息读扩散 + 实时推送 + 其他群接口补偿”的设计取舍。
- 待确认：群聊会话列表是否要求离线增量完整反映群活跃变化；如果要求，需要调整增量过滤条件、增加成员级索引/事件投影，或明确客户端进入群列表后按群服务与消息拉取做补偿。

### 12. user.UpdateProfile 的 proto 校验像必填，service 却按局部更新处理

- 位置：`proto/user/user_service.proto`
- 相关位置：`apps/user/internal/service/user_service.go`、`apps/gateway/internal/dto/user_dto.go`
- 现象：gateway DTO 和 user service 都把更新资料当成“至少一个字段”的局部更新：可以只改签名、生日或性别。但 proto 中 `UpdateProfileRequest.nickname` 使用 `min_len=2`，`gender` 使用 `in: [1,2,3]`；如果 gRPC validate 对默认空串和 0 生效，请求在进入 handler 前就会被拒绝，导致 service 里的局部更新逻辑不可达。
- 影响：HTTP 层看起来允许 `omitempty` 的局部更新，实际可能被下游 proto validate 拒绝；不同入口对“字段未传”和“传空值”的语义不一致。
- 待确认：是否把 proto 改成 optional/ignore_empty 语义并重新生成 pb/validate 文件，还是把 gateway 和 service 收紧为所有资料字段必填。
