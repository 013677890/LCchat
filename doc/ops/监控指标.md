# 监控指标

本文整理当前项目对外暴露的健康检查、Prometheus 指标入口和建议关注的运行指标。事实来源为 `docker-compose.yml`、gateway/connect 服务路由以及各服务 healthcheck 配置。

## 1. 健康检查入口

### 1.1 HTTP 健康接口

| 服务 | 地址 | 说明 |
| --- | --- | --- |
| gateway | `GET /health` | 返回基础存活状态。 |
| connect | `GET /health` | 返回存活状态和在线连接数。 |
| message-push | `GET /health` | 返回桥接服务存活状态。 |

### 1.2 metrics 入口

| 服务 | 地址 |
| --- | --- |
| gateway | `GET /metrics` |
| auth | `GET :9190/metrics` |
| user | `GET :9194/metrics` |
| relation | `GET :9193/metrics` |
| group | `GET :9195/metrics` |
| msg | `GET :9192/metrics` |
| connect | `GET /metrics` |

## 2. 当前已明确的指标能力

### 2.1 gateway

gateway 使用 Prometheus 中间件和 `/metrics` 暴露 HTTP 指标，建议重点关注：

| 维度 | 说明 |
| --- | --- |
| 请求量 | 总请求数、按路由/方法聚合。 |
| 响应耗时 | P50 / P95 / P99。 |
| 错误率 | 业务错误与系统错误分开看。 |
| 超时 | 是否出现请求预算耗尽。 |
| 限流 | IP 限流、用户限流命中情况。 |

### 2.2 connect

connect 当前明确暴露：

| 指标 | 说明 |
| --- | --- |
| `connect_online_connections` | 当前在线 WebSocket 连接数。 |

健康接口 `/health` 也会返回：

```json
{
  "status": "ok",
  "online_connections": 12
}
```

## 3. 建议重点观察项

### 3.1 API 层

| 关注项 | 风险 |
| --- | --- |
| gateway HTTP 5xx 激增 | 下游 gRPC、Redis、MinIO、服务超时异常。 |
| 某路由 P95 / P99 飙高 | 依赖抖动、索引缺失、下游服务慢。 |
| `/api/v1/public/user/send-verify-code` 错误升高 | SMTP、限流、Redis 异常。 |
| `/api/v1/auth/messages/send` 超时升高 | relation/group 校验、msg 落库或 Kafka 抖动。 |

### 3.2 Kafka / 最终一致

| 关注项 | 风险 |
| --- | --- |
| `message-push-consumer-group` lag 增长 | 下行堆积，实时消息延迟。 |
| `group-cache-projector-group` lag 增长 | 群缓存投影延迟，读侧不一致时间变长。 |
| Kafka Connect connector 异常 | Outbox 事件不再入 Kafka。 |
| `outbox_events` 堆积 | Debezium 或 Connect 停滞。 |

### 3.3 connect / WebSocket

| 关注项 | 风险 |
| --- | --- |
| `connect_online_connections` 突降 | connect 宕机、批量断线、网络异常。 |
| 握手失败增多 | Token、Redis、Origin 配置异常。 |
| ACK 写 Redis 失败 | Redis 可用性异常，可能影响短期可靠同步。 |
| 路由残留过多 | 断连清理异常或节点异常退出。 |

### 3.4 数据与缓存

| 关注项 | 风险 |
| --- | --- |
| MySQL 慢查询 | 会话、群成员、关系列表查询退化。 |
| Redis 命中率下降 | 回源压力上升。 |
| Redis 连接池耗尽 | 限流、Token、缓存、在线路由全部受影响。 |

## 4. 典型排障顺序

### 4.1 用户反馈“消息发送成功但对端没收到”

按顺序检查：

1. gateway `/api/v1/auth/messages/send` 是否成功；
2. msg 是否已成功落库；
3. Kafka `msg.push` 是否产生；
4. message-push consumer lag 是否堆积；
5. Redis `user:routing:{user_uuid}` 是否存在；
6. connect 节点是否在线；
7. 对端客户端是否已建立 WebSocket；
8. 客户端是否通过 `PullMessages` 自愈。

### 4.2 用户反馈“建群成功但列表没更新”

按顺序检查：

1. group 写事务是否成功；
2. `outbox_events` 是否写入 `group.cache`；
3. Kafka Connect connector 是否正常；
4. `group-cache-projector-group` lag；
5. Redis `group:user_groups:{user_uuid}` 与 `group:user_group_versions:{user_uuid}` 是否同时存在且版本 Hash 有 `__READY__=1`；
6. `group:info:{group_uuid}` 是否为当前 v2，成员/申请 Hash 是否同时具有当前 schema、正 version 与 `__COMPLETE__=1`；
7. group-service 的 `Group cache reconcile` 单轮日志是否持续成功，以及 `dead_events` 中 `group-service:group.cache` 是否增长。

### 4.3 用户反馈“WebSocket 连不上”

按顺序检查：

1. connect `/health` 是否正常；
2. `auth:at:{user_uuid}:{device_id}` 是否存在；
3. 握手返回是 `17001/17002/20002/30001` 中哪一种；
4. `CONNECT_ALLOWED_ORIGINS` 是否允许当前页面来源；
5. Redis 是否可用。

## 5. 告警建议

建议最少配置以下告警：

1. gateway 5xx 比例持续升高；
2. connect 在线连接数短时间大幅下降；
3. Kafka Connect connector 非 RUNNING；
4. `message-push` 或 `group-cache-projector` consumer lag 持续增长；
5. 任一核心服务 `/metrics` 或 `/health` 不可达。

## 6. 维护规则

1. 新增 metrics 或 healthcheck 时，必须同步更新本文。
2. 若某服务改了 metrics 端口，必须同步更新 `ops/配置说明.md` 和 `ops/本地运行与手工测试.md`。
3. 若新增异步链路，必须新增对应 consumer lag 监控说明。
