# 代码错误审查报告

更新时间：2026-03-25  
范围：`Gateway`、`User`、`Connect`、`Msg` 及其直接相关仓储、处理器、用例层代码

## 说明

- 本文档汇总了本轮静态代码扫描与行级复扫中已确认的问题。
- 仅记录能够明确落到代码位置、且具有真实错误行为或明显风险的问题。
- 本文档主要用于后续修复排期，不代表已经覆盖所有运行时问题。

## 严重级别说明

- `阻塞`：会直接导致越权、核心链路失真或主功能不成立。
- `高风险`：会导致对外行为错误、数据一致性问题或能力“假可用”。
- `中风险`：短期可能不一定立即炸，但会引发错误分页、同步失真、审计缺失等问题。
- `低风险`：当前轮次未单独列出；后续若发现更多可补充。

## Gateway

### 阻塞

#### GATEWAY-001 越权查询黑名单关系

- 文件：`apps/gateway/internal/router/v1/blacklist_handle.go`
- 符号：`BlacklistHandler.CheckIsBlacklist`
- 问题描述：接口直接绑定请求体中的 `userUuid` 与 `targetUuid`，随后原样转发给 service，没有强制使用当前登录用户身份。
- 为什么会出错：任意已登录用户都可以伪造 `userUuid`，查询“别人是否拉黑了某人”或“某人是否拉黑了别人”，接口语义被放大成任意关系探测。
- 修复方向：在 Gateway 层忽略请求体中的 `userUuid`，统一用上下文中的当前用户 UUID 覆盖；若该接口设计为内部接口，应下沉到内网服务而不是公网路由。

### 高风险

#### GATEWAY-002 JWT 校验未回查会话状态

- 文件：`apps/gateway/internal/middleware/auth.go`
- 符号：`JWTAuthMiddleware`
- 问题描述：中间件只验证本地 JWT，并把 claims 写入上下文，没有回查 Redis 中的 access token 或设备会话状态。
- 为什么会出错：如果 Redis 中 token 已被删除，或者设备已被服务端踢下线，但 JWT 自身仍未过期，请求仍可能继续通过，导致“立即失效”语义不成立。
- 修复方向：在统一鉴权层增加 Redis token 存在性校验，或通过 user-service 提供轻量鉴权校验接口。

### 中风险

#### GATEWAY-003 登录服务签名携带 `deviceId` 参数但内部未使用

- 文件：`apps/gateway/internal/service/auth_service.go`
- 符号：`AuthServiceImpl.Login`、`AuthServiceImpl.LoginByCode`
- 问题描述：方法签名接收 `deviceId string`，但内部完全没有用这个参数构建 gRPC 请求。
- 为什么会出错：当前逻辑实际上依赖上下文透传 device_id。一旦上下文链路漏传，这层代码不会兜底，问题也很难从服务层直接看出来。
- 修复方向：删除无效参数，或显式把 `deviceId` 注入 DTO/Proto 请求，避免职责分裂。

## User

### 阻塞

#### USER-001 服务层允许越权查询黑名单关系

- 文件：`apps/user/internal/service/blacklist_service.go`
- 符号：`blacklistServiceImpl.CheckIsBlacklist`
- 问题描述：服务端直接信任 `req.UserUuid` / `req.TargetUuid`，不从上下文读取当前登录用户，也不做主体一致性校验。
- 为什么会出错：即使 Gateway 之后补上身份覆盖，这个 service 仍允许其他调用方绕过主体约束，直接查询任意两人的黑名单关系。
- 修复方向：对公网语义的接口统一从 context 读取当前用户；如果确实需要任意主体查询，应拆成内部接口并加调用边界说明。

### 高风险

#### USER-002 邮箱存在性校验是空实现

- 文件：`apps/user/internal/repository/auth_repository.go`
- 符号：`authRepositoryImpl.ExistsByEmail`
- 问题描述：函数直接 `return false, nil`。
- 为什么会出错：所有邮箱占用检查都会被误判为“未占用”，导致注册、改邮箱等逻辑前置校验失真。
- 修复方向：补全真实查询逻辑，并统一返回 `WrapDBError` 风格错误。

#### USER-003 手机号查询是空实现

- 文件：`apps/user/internal/repository/auth_repository.go`
- 符号：`authRepositoryImpl.GetByPhone`
- 问题描述：函数直接 `return nil, nil`。
- 为什么会出错：手机号查询路径会得到“假空结果”，调用方难以区分“用户不存在”和“仓储未实现”。
- 修复方向：补全 `telephone` 查询逻辑，并与 `GetByEmail` 保持一致的错误包装行为。

#### USER-004 手机号存在性校验是空实现

- 文件：`apps/user/internal/repository/auth_repository.go`
- 符号：`authRepositoryImpl.ExistsByPhone`
- 问题描述：函数直接 `return false, nil`。
- 为什么会出错：手机号唯一性或存在性判断全部失效，后续绑定、注册、查重逻辑会出现假通过。
- 修复方向：补全 DB 查询逻辑，并统一返回布尔值与错误。

#### USER-005 设备仓储存在多项空实现，导致能力表面可用但底层残缺

- 文件：`apps/user/internal/repository/device_repository.go`
- 符号：`UpdateLastActive`、`DeleteSession`、`GetOnlineDevices`、`UpdateToken`、`DeleteAllSessions`
- 问题描述：这些方法仍是 TODO 或直接空返回。
- 为什么会出错：多端踢下线、全端登出、token 轮换、最近活跃时间刷新等能力会表现为“接口存在但行为不完整”。
- 修复方向：优先补齐被 service 真正依赖的方法，再补全其余生命周期方法。

#### USER-006 用户资料仓储部分方法未实现

- 文件：`apps/user/internal/repository/user_repository.go`
- 符号：`GetByPhone`、`Update`
- 问题描述：相关方法仍为空实现。
- 为什么会出错：手机号相关资料查询、通用更新逻辑若被后续调用，会直接返回错误结果或假空结果。
- 修复方向：补齐真实 DB 行为，避免未来调用时踩到“死坑”。

### 中风险

#### USER-007 最后登录时间更新是空实现

- 文件：`apps/user/internal/repository/auth_repository.go`
- 符号：`authRepositoryImpl.UpdateLastLogin`
- 问题描述：函数直接 `return nil`，但没有任何更新动作。
- 为什么会出错：调用方会误以为登录审计已成功刷新，实际数据库仍是旧值，后续风控、设备管理、审计展示都会读到过期数据。
- 修复方向：补齐更新语句，并考虑登录成功流程里是否已可靠调用该方法。

#### USER-008 黑名单列表缓存分页总数会漂移

- 文件：`apps/user/internal/repository/blacklist_repository.go`
- 符号：`blacklistRepositoryImpl.GetBlacklistList`
- 问题描述：Redis 命中路径下把当前缓存 ZSet 的基数直接当总数返回；而回填缓存时，非空场景只写入本次查询页的 `relations`，不是全量黑名单集合。
- 为什么会出错：缓存命中后，分页总数、页数、是否还有下一页都可能错误；不同页请求还可能互相覆盖缓存，表现为列表缺页和总数漂移。
- 修复方向：缓存全量集合再分页，或缓存分页结果而不是复用单个 ZSet 承担全量分页语义。

## Connect

### 阻塞

#### CONNECT-001 WebSocket 来源校验完全放开

- 文件：`apps/connect/internal/handler/ws_handler.go`
- 符号：`wsUpgrader.CheckOrigin`
- 问题描述：`CheckOrigin` 恒返回 `true`。
- 为什么会出错：浏览器环境下，任意站点都可以发起跨站 WebSocket 连接；只要拿到 token 和 device_id，就能建立在线连接，接入边界完全失守。
- 修复方向：在生产环境按白名单校验 Origin；本地调试可通过配置开关放宽。

### 中风险

#### CONNECT-002 上行消息返回假成功 ACK

- 文件：`apps/connect/internal/handler/ws_handler.go`
- 符号：`WSHandler.handleMessage`
- 问题描述：收到 `type="message"` 的上行帧时，没有接入 `msg-service`，只返回 `message_ack` 占位回执。
- 为什么会出错：客户端会误以为消息已经被系统确认，但实际上既没有持久化，也没有路由和投递，属于假成功语义。
- 修复方向：在真正接入消息链路前，至少返回明确的未实现错误，而不是 ACK。

## Msg

### 阻塞

#### MSG-001 拉取历史消息忽略 `clear_seq`

- 文件：`apps/msg/internal/handler/msg_handler.go`
- 符号：`MsgHandler.PullMessages`
- 问题描述：`clearSeq` 被硬编码为 `0`，未根据 `owner_uuid` 查询删除位点。
- 为什么会出错：用户删除会话后，设计上应只看到 `seq > clear_seq` 的消息；当前实现会把删除前历史继续拉出来，造成“删除无效”的错误行为。
- 修复方向：从上下文或请求主体拿到 `owner_uuid`，查出对应会话的 `clear_seq` 后再传入领域层。

### 中风险

#### MSG-002 发送消息事件忽略 Proto 序列化错误

- 文件：`apps/msg/internal/usecase/send_message_workflow.go`
- 符号：`SendMessageWorkflow.Execute`
- 问题描述：`proto.Marshal(msgItem)` 的错误被直接忽略：`msgItemData, _ := proto.Marshal(msgItem)`。
- 为什么会出错：一旦消息体序列化失败，Kafka 事件仍会继续发，下游消费方会拿到损坏或空载荷，出现“消息已落库但推送数据坏掉”的不一致问题。
- 修复方向：显式检查 `Marshal` 错误，并决定是否阻断投递或降级记录告警。

#### MSG-003 已读同步事件忽略 Proto 序列化错误

- 文件：`apps/msg/internal/usecase/mark_read_workflow.go`
- 符号：`MarkReadWorkflow.Execute`
- 问题描述：`proto.Marshal(notice)` 的错误同样被忽略：`noticeData, _ := proto.Marshal(notice)`。
- 为什么会出错：本端已读状态可能已经写库成功，但发给其他设备的同步事件损坏，导致多端红点状态不一致。
- 修复方向：对已读通知的序列化失败进行显式错误处理或告警，并明确同步失败后的补偿方案。

## 建议优先修复顺序

1. `GATEWAY-001` 与 `USER-001`：先封堵黑名单越权查询。
2. `CONNECT-001`：补上 WebSocket Origin 校验边界。
3. `MSG-001`：修正 `clear_seq`，避免消息删除语义失真。
4. `USER-002`、`USER-003`、`USER-004`：补齐认证仓储空实现。
5. `CONNECT-002`：避免客户端收到假成功 ACK。
6. `USER-008`：修正黑名单缓存分页逻辑。
7. `MSG-002`、`MSG-003`：补上消息事件与已读事件的序列化错误处理。

## 残余风险

- 本文档基于静态只读扫描，不包含运行态、数据库约束、真实 Redis/Kafka 数据流验证。
- 仍可能存在仅在特定配置、并发场景或跨服务联调中触发的问题。
- 建议在修复过程中同步补充单测、集成测试与必要的链路回归测试。
