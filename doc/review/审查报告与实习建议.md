## 一、总评

**这是一个水准明显高于普通实习生项目的 Go IM 微服务后端。** 它没有停留在"调库 CRUD"，而是在分布式消息可靠性这条最难的路上认真走了很远：事务性 outbox + Debezium CDC、发送三层幂等、Kafka 累积提交防静默丢、熔断器按错误语义分类、WebSocket 路由 TTL 与心跳协同、自研贯穿全链路的 trace。这些设计在代码里都**真实落地**，注释里写清了"为什么这么选"，git log 里能看到真实的踩坑-修复演进。68 个测试文件、1.6 万行测试实测全绿，`go vet`/`go build`/`go test ./...` 干净通过。

但它也有**与这份功力不匹配的硬伤**：一个默认部署下会让实时推送整体失效的端到端契约断裂（critical，已验证）、43MB 二进制和 AI 记忆文件被提交进 git、零 CI、生成代码不入库导致干净克隆无法构建、没有任何压测数据。这些是面试官翻仓库前几分钟就会撞见、且会显著拉低第一印象的问题，恰恰也是最容易修的。

## 二、核心结论：先看这一个

### 🔴 CRITICAL（已对抗验证确认）：默认部署下，每一条聊天消息的实时推送都被静默丢弃

**位置**：[scripts/cdc/register_outbox_connector.sh](../../scripts/cdc/register_outbox_connector.sh#L50) + [docker-compose.yml:86](../../docker-compose.yml#L86) + [pkg/msgevent/events.go:38](../../pkg/msgevent/events.go#L38)

Kafka Connect 配的是 `JsonConverter` + `schemas.enable=false`，而 Debezium EventRouter **没有开** `transforms.outbox.table.expand.json.payload=true`。在这个组合下，`outbox_events.payload`（LONGTEXT 字符串列）被路由进 Kafka 时是一个**被 JSON 转义的字符串字面量**（形如 `"{\"event_id\":...}"`），不是裸 JSON 对象。

铁证在仓库内部就有：同一个 connector 路由的 **account/group 事件的消费端都写了"解套"逻辑**（`pkg/accountevent/events.go:107`、`pkg/groupevent/events.go:139` 先 `json.Unmarshal` 拆一层字符串）——说明作者在联调中**确实观测到了这层转义包裹**。唯独主推送链路的 `msgevent.DecodeMsgPush` 是严格 protojson 解码、没有解套，遇到字符串字面量必然报错；而 message-push 把解码失败归为"永久错误"，仅打一条 **Warn 日志**就提交 offset 跳过（[consumer.go:76](../../apps/message-push/internal/consumer/consumer.go#L76)）。

**后果**：用仓库自带的 docker-compose 起服务，所有聊天消息/撤回/已读的**在线实时推送整体失效**，只剩客户端轮询拉取兜底，且没有任何报错——典型的"每个组件单测都过、端到端契约断裂"事故。

**为什么严重度是 critical**：消息本体已 outbox 持久化（不是永久丢数据，客户端补拉能恢复），但实时下行通道在默认配置下整条静默断掉，符合"线上事故"定义。

**修复**（任选/都做）：
1. connector 配置加 `"transforms.outbox.table.expand.json.payload": "true"`；
2. 给 `DecodeMsgPush` 补上与 accountevent 一致的字符串解套兜底；
3. **关键**：补一条 docker-compose 起真实 Debezium+Kafka 的端到端集成测试（发消息 → 断言 msg.push 的 value 能被 `DecodeMsgPush` 解出），否则 connector 配置与 Go 解码契约还会再次漂移。

## 三、按严重度排序的问题清单

> 标 ✅ 的是经过对抗性二次验证**确认成立**的；标 ⚠️ 的是单审查者发现、证据较强但未走二次验证（可信但建议自查）。补审后仅剩 #12（Snowflake node ID）一条 ⚠️——它由 3 个维度独立指出，证据强。括号内为原始严重度调整说明。

### 🔴 Critical
1. ✅ **CDC 双重转义导致推送链路整体静默失效** —— 见上文第二节。

### 🟠 High（已验证）
2. ✅ **seq 仅靠 Redis INCR 分配，且 `(conv_id, seq)` 不是唯一索引** [repository_impl.go:41](../../apps/msg/internal/domain/message/repository_impl.go#L41)
   写路径 `AllocSeq` 只有裸 `INCR`，无 TTL、无"key 缺失时从 DB `MAX(seq)` 重建"的对账（而读路径 `GetMaxSeq` 反而有 DB 降级——说明作者意识到了 key 会丢，唯独最危险的写侧没防）。Redis 一旦丢数据（AOF everysec 崩溃窗口、主从切换、maxmemory 驱逐、误 FLUSH），INCR 从头计数 → seq 重复，而 `idx_conv_seq` 是普通索引，**重复 seq 会静默落库**，破坏排序/去重/gap 检测。验证还发现更重一层：seq 回退会把会话 `max_seq` 写小，删除会话时 `clear_seq` 取 max_seq，拉历史过滤 `seq > clear_seq` → 新消息可能被永久过滤，对用户等价丢消息。
   **修**：`AllocSeq` 改 Lua：key 不存在时先 `SELECT MAX(seq)` 回填再 INCR；把 `idx_conv_seq` 升级为 UNIQUE，让重复在 DB 层硬失败。

3. ✅ **Validate/Timeout 拦截器位于 ErrorNormalize 之外，错误退化为 `codes.Unknown`** [runtime.go:94](../../pkg/grpcx/runtime.go#L94)
   唯一负责 apperr→gRPC status 转换的 ErrorNormalize 在第 7 层，而 Validate（返回裸 `apperr.Wrap`）和 Timeout（返回裸 `apperr.New`）在它外层；`*apperr.Error` 未实现 `GRPCStatus()`，被 gRPC 框架兜底成 `Unknown`。连锁后果：① 客户端默认重试含 UNKNOWN 且 MaxAttempts=5 → 参数校验失败的请求被重试 5 次；② 熔断器把 Unknown 计为失败 → 可能误熔断健康下游（与该函数注释声明的设计意图直接矛盾）；③ gateway 拿不到业务码 → 参数错误兜底成 HTTP 500；④ PGV 校验原文（含字段名）写进 status message 绕过脱敏；⑤ Timeout 还会把内层已正确归一化的 DeadlineExceeded 替换回裸 apperr，主动破坏正确语义。
   **修**：让 `*apperr.Error` 实现 `GRPCStatus()`；或把 ErrorNormalize 提到最外二层；并从默认可重试码移除 UNKNOWN。

4. ✅ **十余个业务错误码缺失 gRPC 映射，正常业务拒绝被当作 Internal 计入熔断** [code_map.go:62](../../pkg/apperr/code_map.go#L62)
   `grpcCodeForBizCode` 的 switch 未覆盖 `CodeQRCodeFormatError/Expired`、`CodeInvalidEmail`、`CodeMessageTypeNotSupport`、`CodeMessageSendFail` 等有真实返回路径的码，全落 default→`Internal`。被踢出群的用户持续发消息，错误码经 `mapMsgDomainError` 包装为同样未映射的 `CodeMessageSendFail(13002)` → Internal → gateway 熔断器（15s 窗口 ≥5 请求且失败率≥50%）可被这类**正常业务流量**打开 45 秒，期间该实例所有用户的发消息请求被拒。漏过测试是因为测试 helper 把期望的 gRPC code 参数写成了 `_` 从未断言。
   **修**：补全映射（14002→PermissionDenied、格式类→InvalidArgument…）；加一个遍历所有 `Code*` 常量、断言每个都有显式映射的单测。

5. ✅ **Kafka Producer 未设 `RequiredAcks`，默认 acks=0（fire-and-forget）静默丢消息** [producer.go:18](../../pkg/kafka/producer.go#L18)
   segmentio/kafka-go 的 Writer 默认 `RequireNone`，`WriteMessages` 返回 nil 不代表 broker 已确认。主消息链路走 outbox/CDC 不受影响，但 **relation/group 的好友申请、群通知等 realtime.push 提醒**、以及 **auth/user 的 redisretry 补偿队列**都用这个 Producer，broker 抖动/重启/leader 切换期间消息无感知丢失——与 redisretry"可靠补偿"的设计初衷直接矛盾，且 `realtime_notify.go` 对发送失败本就只 Warn 不阻断，acks=0 时连 Warn 都不会有。
   **修**：补偿/事件类设 `RequiredAcks: RequireAll`（至少 RequireOne）；带 key 的有序消息把 Balancer 从 `LeastBytes` 换成 `Hash`（否则"同 key 同分区有序"的注释不成立）。

6. ✅ **跨实例重连竞态：旧 connect 节点会误删设备重连到新节点后写入的路由** [lifecycle.go:82](../../apps/connect/internal/svc/lifecycle.go#L82)
   `OnDisconnect` 无条件 `RemoveUserRoute`，而后者只做 `HDEL` 不校验该 field 是否还指向本节点（连接管理器的指针一致性校验只能防同实例竞态）。设备经 connect-lb 重连到 connect-2 后，旧节点 connect-1 最迟约 60s 检测到死连接并删掉指向 connect-2 的新路由；而新节点心跳刷新被节流 180s、WebSocket Pong 又不触发路由刷新 → 该在线设备约 **2~3 分钟对 message-push 不可见**（被按离线处理），实时推送黑洞。讽刺的是仓库里 `RemoveRoutesByConnectAddr`（停机清理）已有"按地址前缀校验归属"的正确模式，唯独单设备断开路径漏了。
   **修**：`RemoveUserRoute` 改 Lua CAS：仅当 value 以本节点地址为前缀时才 HDEL；或在路由 value 里加连接纪元校验。

7. ✅ **生成的 `*.pb.go` 不入库，干净克隆无法 `go build`** [.gitignore:29](../../.gitignore#L29)
   `.gitignore` 忽略 `*.pb.go`，仓库零跟踪生成代码，而 101 个 Go 文件 import pb 包。忽略生成码本身合理，真正的缺陷是**没有任何自动生成兜底**：Dockerfile `COPY . .` 后直接 build、builder 未装 protoc；无 CI；README"快速启动"直接让人 `docker compose up --build` 却没提 `make proto` 前置步骤——新成员/CI/新机器按官方文档操作第一步即失败。另外 `scripts/` 下并存 `gen-proto.sh` 和硬编码个人路径的 `gen_proto.sh`。
   **修**：要么把 pb 代码入库（配 CI 校验 diff），要么在 Dockerfile builder 阶段装 protoc 并生成；删掉重复脚本，建议引入 buf。

8. ✅ **服务间身份信任未认证的明文 metadata，且 compose 把业务 gRPC 端口映射到宿主机** [metadata.go:26](../../pkg/grpcx/metadata.go#L26)（2026-06-13 已二次验证确认，见第七节）
   服务端直接把 incoming metadata 里的 `x-user-uuid` 当已认证身份用（msg 的 SendMessage 以此作发送者），传输层默认 insecure，内部接口的 `x-internal-caller` 也是任何客户端可伪造的明文 header。而 docker-compose 把 auth/user/relation/group/msg 的 gRPC 端口**全映射到宿主机**（`19090:9090`…`19095:9095`、`19091:9091`，均已核实）——任何能访问这些端口的进程都能携带任意 `x-user-uuid` 冒充任意用户发消息、删好友、解散群。注意：各服务的业务授权（如群成员管理）本身实现严密，但全部建立在"metadata 身份可信"这个被本条打破的前提上。
   **修**：生产编排移除业务 gRPC 端口的宿主机映射；服务间引入 mTLS 或网关签发的内部签名 token（HMAC user_uuid+exp）。

9. ✅ **RefreshToken / 二维码 token 用可预测的雪花 ID 生成** [auth_service.go:225](../../apps/auth/internal/service/auth_service.go#L225)（2026-06-13 已二次验证确认）
   长期续期凭据用 `util.GenIDString()`（41 位毫秒时间戳+硬编码节点 1+12 位序列）生成（auth_service.go:225/342、user_service.go:268），攻击者若知道大致登录时间，搜索空间仅数千量级；refresh-token 在公开路由，校验是**非常数时间**的字面比较 `storedRefreshToken != req.RefreshToken`（auth_service.go:472），且 token 在 Redis 中**明文存储**（device_repository.go:639-640，注释自承"按明文保存"）。配合可枚举的 user_uuid/device_id 存在被暴力猜测续签出 AccessToken 的现实风险。
   **修**：安全凭据必须用 `crypto/rand`；比较改 `subtle.ConstantTimeCompare`；对 refresh-token 接口加按 user 维度的失败次数限制。

### 🟡 Medium（已验证 / 多维度交叉印证）
10. ✅ **群聊部分推送失败的设备被直接丢弃，且 ACK 位点只写不读、无服务端补偿闭环**（原 high，验证后降为 medium：消息本体已持久化、是文档化的"阶段一"取舍）[consumer.go:309](../../apps/message-push/internal/consumer/consumer.go#L309)。注意部分失败连丢弃指标都不计入，存在观测盲区；`msg:ack` key 全仓库无任何读取方。
11. ✅ **重试 ServiceConfig 的 service 级 2s 超时静默钳制了按方法配置的 5s 预算**（原 high，验证后降为 medium：实际只影响验证码发送/资料更新 2 个方法）[client_builder.go:77](../../pkg/grpcx/client_builder.go#L77)。`SendVerifyCode: 5s` 的意图从未生效，SMTP 慢于 2s 时发验证码必然超时。
12. ⚠️ **Snowflake 节点 ID 硬编码为 1，与 `docker-compose.scale.yml` 的 replicas:3 冲突**（concurrency/api/resume 三处独立指出）[app.go:176](../../apps/auth/cmd/app.go#L176)。多副本共享 machineID，同毫秒并发生成重复 ID；EventID 碰撞会让消费端幂等表误判重复而丢事件，refreshToken 碰撞更危险。
13. ✅ **幂等命中路径跳过会话 Upsert，P2P 会话元数据可能永久不一致**（7.3 已二次验证）[send_message_workflow.go:73](../../apps/msg/internal/usecase/send_message_workflow.go#L73)。首次请求落库后、Upsert 前崩溃，重试命中幂等缓存直接返回 → 接收方 unread_count 永久少 1、会话列表停在旧值，无补偿（群成员会话行有补偿，P2P 没有）。
14. ✅ **会话 `max_seq`/`last_msg_*` 直接覆盖无单调保护，并发下回退**（7.3 验证后**降为 low**：仅 last-msg 预览/排序瞬时抖动、下一条消息自愈；unread 用 DB 层 `+1` 是安全的）[repository_impl.go:132](../../apps/msg/internal/domain/conversation/repository_impl.go#L132)。
15. ✅ **redisretry 补偿无退避，且 CommitAlways 模式下 re-publish 失败即永久丢任务**（7.3 已二次验证）[consumer.go:67](../../pkg/redisretry/consumer.go#L67)。Redis 未恢复时 3 次重试在几十毫秒内烧完；re-publish 失败仅打日志、offset 照常提交，缓存与 DB 长期不一致。
16. ✅ **发送失败后 Redis `PROCESSING` 幂等锁不释放，10 秒内重试被误报"重复消息"**（7.3 已二次验证）[service.go:148](../../apps/msg/internal/domain/message/service.go#L148)。一次瞬时 DB 抖动会让弱网重发在 10s 窗口内全被 `CodeMessageDuplicate` 拒绝。
17. ✅ **connect 停机 `close(statusQueue)` 与并发 send 存在 send-on-closed-channel panic 竞态**（7.3 已二次验证，窄窗口）[connect_service.go:133](../../apps/connect/internal/svc/connect_service.go#L133)。
18. ✅ **gateway 对非幂等写接口开启 service 级全方法重试（含 UNKNOWN，MaxAttempts=5）**（7.3 已二次验证）[client_connection.go:52](../../apps/gateway/internal/pb/client_connection.go#L52)。加好友/建群等响应超时被自动重放可能产生重复副作用。
19. ✅ **完全没有 CI，Makefile 缺 test/lint/build 目标**（原 high，降 medium：流程缺失非代码 bug）[Makefile:3](../../Makefile#L3)。68 个测试无任何机制保证每次提交都跑。
20. ✅ **43MB ELF 二进制 `cmd` 被提交进 git**（原 high，降 medium：仓库卫生非运行时缺陷）[cmd](../../cmd)。占整个 pack 约 94%，clone 体积膨胀约 5 倍；`cmd.exe`、`__pycache__`、`_achieve/`、空 `package-lock.json`、`.codex/`、`.claude/settings.local.json` 也一并入库。
21. **指标只埋不采**：8 服务都暴露 /metrics 且埋了高质量业务指标（含明确标注"应作为告警信号"的 `dropped_after_retry_total`），但 compose/k8s 里没有任何 Prometheus/Grafana/Alertmanager，无人消费。
22. **message-push 消费侧 trace_id 未注入 ctx**：跨 Kafka 边界后日志丢 trace_id，链路追踪在最关键的异步段断链。
23. **connect /metrics 手写文本只有 1 个 gauge，gRPC 无指标拦截器**：作为长连接核心服务，下行推送 QPS/耗时、ACK 超时率、握手失败率全缺失。
24. **大群扇出逐设备串行 RPC，未按节点聚合**：万人群 = 在线设备数 × 150ms RPC，且 Kafka 按 conv_id 分区会队头阻塞同分区其他会话；connect 端已有 `BroadcastToUsers` 却没被 message-push 用。
25. **身份跨服务传递方式不统一**：msg 走请求体显式字段，user/relation 走 metadata 隐式传递，两套约定并存。

### 🟢 Low（节选，完整见原始材料）
- `outbox_events` 无清理机制、表无限增长；`snapshot.mode=when_needed` 下 offset 丢失会全量重放、而 message-push 没接幂等表 → 重放时重复推送。
- GORM 模型列宽与真实 SQL 漂移（`conv_id char(40)` 装不下 45 字符的 p2p 会话 ID），AutoMigrate 会爆雷。
- `isDuplicateKeyError` 用字符串包含 "1062" 判断、`MaskUUID` 对 20 字符 ULID 会切片越界 panic（当前是死代码）。
- `ctxmeta` 用裸 string 作 context key（SA1029）；`logger.ErrorField` 的 key 参数被忽略。
- friend 模块全用 POST（含查询语义），与 groups 的资源化 REST 风格不一致。
- 会话分页游标解析吞错（非法 cursor 静默当 0，可致客户端重复拉同一页）。
- mock 生成头注释指向已改名的旧项目路径、用已归档的 golang/mock，不可复现。
- 默认发件邮箱硬编码个人 QQ 邮箱。

### 被验证「证伪 / 显著修正」的发现
- "群聊丢弃"和"重试 2s 钳制"被从 high **下调为 medium**（见上）；"重试 2s 钳制"中"DEADLINE_EXCEEDED 会触发自动重试导致验证码重复发送"的子论断被**证伪**（methodConfig timeout 作用于整体 RPC ctx，客户端 deadline 到期后 grpc-go 不再重试，实际是用户手动重试才会重复发）。这类修正提醒：简历/面试里别把"理论风险"说成"必然后果"。

## 四、项目亮点（面试可重点讲，每条都已确认代码真实落地）

1. **事务性 Outbox + Debezium CDC**：消息与 outbox_events 严格同一本地事务（`CreateWithOutbox`），CDC 读 binlog、EventRouter 按 event_type 路由 topic、entity_id=conv_id 作 Kafka key 保序。业务侧零 Kafka 依赖，连 outbox 表都没有 status 字段（复杂度全外移给 Debezium）。
2. **发送三层幂等**：Redis SETNX 三态锁（处理中/命中缓存/获锁）→ DB `(sender,device,client_msg_id)` 唯一索引兜底 → 消费端 `idempotent_events` 表。每层降级路径都考虑了，幂等键含 device_id 避免多端撞车。
3. **Kafka 累积提交防静默丢**：注释精确指出 kafka-go「FetchMessage 不重投 + offset 累积提交」的组合陷阱，改为失败就地退避重试、绝不前进；panic 视为毒消息提交跳过防卡死分区。这是全仓库最能体现"踩过坑"的点。
4. **路由 TTL 与心跳节流协同**：TTL = 2×节流间隔的显式约束（修复了撞车导致在线误判离线的 bug），写侧 TTL + 读侧 activeMs cutoff 双保险，节点下线用 SCAN 而非 KEYS 清理。
5. **熔断器只对基础设施故障计失败**：把 InvalidArgument/Unauthenticated/客户端取消等业务码排除在失败率外，注释写明"错误密码风暴会误熔断健康下游（自伤）"。超出大多数人对 gobreaker 的默认套用。
6. **自研轻量链路追踪**：trace_id/span_id/parent_span_id 贯穿 HTTP→gRPC→Kafka→WS，日志自动附加，未引入 OTel 也达到了小型自研链路追踪的完成度。
7. **RedisBloom 工程化封装**：定下"先 Add 再写 DB"的方向性纪律防 false negative，三态返回值 `(exists, usable, err)` 让布隆不可用时降级回源 DB。
8. **gorilla/websocket 并发写纪律完全正确**：所有写收敛到唯一 writeLoop，每连接固定 2 goroutine，Close 用 sync.Once 幂等；ACK 水位只在真正写入 socket 后记录，Lua 保证位点只前进。

## 七、安全与数据层补审（2026-06-13 补完）

> 上一轮工作流的安全/数据层维度因 API 限流（429）未产出；本节由主审查直接读代码完成，每条均带 `file:line` 证据。多智能体并行补审两次都被 429 整批拒绝（详见续做指南），故改为内联核实。

### 7.1 安全维度（评分 6/10）

**基本功扎实，但有几处真实的认证体系弱点。**

**新发现（按严重度）：**

- 🟠 **[high] 无 AccessToken 吊销机制：登出/踢设备对已签发的 token 在 2 小时内无效**
  [auth.go:40](../../apps/gateway/internal/middleware/auth.go#L40) 的 `JWTAuthMiddleware` 是**纯无状态**校验——只调 `util.ParseToken` 验签，从不查 Redis 的 `auth:at:{uuid}:{device}` key。而登出/踢设备（[auth_service.go:522](../../apps/auth/internal/service/auth_service.go#L522)，注释自称"先删 Token，确保该设备马上失去继续访问接口的能力"）只删了 Redis 里的 token。由于校验路径根本不读 Redis，**被盗或已登出的 AccessToken 在其 2 小时有效期内仍然全程可用**，账号失陷无法及时止血，注释与实际行为矛盾。`auth:at:` 这个 Redis key 写了但鉴权路径不读，近乎无效投入。
  **修**：要么 AccessToken 改短时效（如 15min）+ 靠 RefreshToken 续期，要么在网关校验时查 Redis 黑名单/版本号（牺牲一次 Redis RTT 换可吊销性）。

- 🟠 **[high] JWT_SECRET 缺失时回退到源码中公开的硬编码密钥，仅告警不 fail-fast**
  [jwt.go:31-37](../../pkg/util/jwt.go#L31)：未设 `JWT_SECRET` 时回退到 `devJWTSecret = "your-secret-key-change-in-production"`（值就在源码里）并只打一条 `Warn`。生产环境一旦漏配环境变量，服务照常启动，但**任何人都能用这个公开密钥伪造任意用户的 token**。
  **修**：生产环境（非 dev）缺 `JWT_SECRET` 应直接 fail-fast 终止启动。

- 🟡 **[medium] 验证码校验无尝试次数限制，可被暴力枚举**
  [auth_repository.go:197-207](../../apps/auth/internal/repository/auth_repository.go#L197) 的 `VerifyVerifyCode` 只是 `Get` + 字面比较 `value == verifyCode`，**错误猜测既不计数也不使验证码失效**。限流 `CheckAndIncrementVerifyCodeRateLimit` 只作用在**发送侧**（按 email/IP），校验侧没有任何独立节流。6 位验证码（10⁶）的唯一爆破刹车就是网关的 IP 令牌桶，而验证码登录是公开端点（只有 IP 维度限流）。
  **修**：给验证码加"连续错误 N 次即失效"计数器；校验改常量时间比较。

- 🟡 **[medium] 内部 gRPC 接口治理不一致，叠加端口暴露形成无鉴权内部能力**
  group/relation/msg 的 gRPC Server 未挂 `InternalCallerInterceptor`（仅 auth/connect/user 挂了，已知），叠加第 8 条的端口宿主机映射，`GetGroupMemberIds`、`BatchCheckIsFriend` 等本应内部专用的能力可被任意外部进程直连调用，用于批量探测社交关系图谱。
  **修**：内部查询方法补齐 `InternalCallerInterceptor`；配合移除端口映射。

- 🟢 **[low] 缓存删除吞错 + 验证码/限流 key 用 email 明文拼接**：`_ = r.redisClient.Del(...)` 大量忽略错误（删除失败则脏缓存留到 TTL）；Redis key 直接拼接用户可控的 email。

**安全维度的亮点（值得在面试主动讲，证明不是无意识）：**
- ✅ **JWT 校验了签名算法**（[jwt.go:81](../../pkg/util/jwt.go#L81) 断言 `*jwt.SigningMethodHMAC`），正确防御 `alg=none` 和 RS256/HS256 算法混淆攻击——这是很多人会漏的点。
- ✅ **验证码用 `crypto/rand`** 生成（[verify_code.go:52](../../pkg/util/verify_code.go#L52) `rand.Int(rand.Reader, ...)`），不可预测。
- ✅ **WebSocket `CheckOrigin` 安全默认**（[ws_handler.go:31-63](../../apps/connect/internal/handler/ws_handler.go#L31)）：未配置时默认只允许同源，`"*"` 仅限本地开发——正确防御跨站 WebSocket 劫持（CSWSH）。
- ✅ **CORS 仅回显白名单内的具体 Origin**，不无脑 `*`。
- ✅ **群成员管理授权严密**（[group_member_management.go:161-314](../../apps/group/internal/repository/group_member_management.go#L161)）：每个管理操作都在事务行锁内 `ensureOperatorRoleAtLeast` 校验操作者角色 + `canMuteGroupMember`/`canUpdateGroupMemberNickname` 校验目标角色兼容性，操作者身份取自认证上下文而非请求体。
- ✅ **SQL 全参数化**：无 `.Raw(`/字符串拼接 SQL 注入面（`.Exec(` 命中全是 Redis pipeline）。

### 7.2 数据层维度（评分 7.5/10）

**索引、事务、缓存三块设计都成熟，问题集中在已知项和若干 low。**

**新发现：**
- 🟢 **[low] `group_members` 冗余索引**：`idx_group_members_group_uuid (group_uuid)` 被唯一键 `uidx_group_user (group_uuid, user_uuid)` 的最左前缀完全覆盖，可删除（[001_schema.sql:99-100](../../config/mysql/001_schema.sql#L99)）。
- 🟢 **[low] 缓存删除式失效吞错致 stale 到 TTL**：写操作后 `_ = r.redisClient.Del(cacheKey)` 忽略错误（friend/group/blacklist repo 数十处），删除失败则脏数据留到 TTL（profile 1h、friend/group 24h）。属可接受的 best-effort，但应至少记录失败指标。
- （已知项不重复：seq 无对账/无 `(conv_id,seq)` 唯一索引【high】、`outbox_events` 无清理、GORM 列宽漂移 `char(40)`、OnConflict 列与真实唯一键不一致——schema 已确认 `conversation` 唯一键是 `(owner_uuid, target_uuid)` 而代码 OnConflict 写的是 `(owner_uuid, conv_id)`，仅因 MySQL 方言忽略该列而偶然正确。）

**数据层的亮点：**
- ✅ **索引设计成熟**（[001_schema.sql](../../config/mysql/001_schema.sql)）：群申请/好友关系/申请表都用了 `(业务列, status, deleted_at, created_at, id)` 形态的覆盖索引，末列带 `id` 支持 keyset 深分页；唯一约束都落在正确的业务键上。这在实习项目里非常少见。
- ✅ **事务干净**：核查了 group/msg/conversation 的所有 `db.Transaction` 块，**事务内只有 DB 操作，没有 gRPC/Redis/Kafka 网络 IO**；缓存更新（`upsertGroupMemberCacheAsync`）一律在事务 commit **之后**异步执行，不持锁做网络操作。
- ✅ **行锁用对了地方**：群成员管理用 `clause.Locking{Strength: "UPDATE"}`（[group_repository.go:949](../../apps/group/internal/repository/group_repository.go#L949) 等）在事务内串行化并发管理操作。
- ✅ **缓存防护到位**：Cache-Aside 删除式失效 + **空值缓存**（`*EmptyTTL` 5min，防穿透）+ relation 侧 **TTL 随机抖动 ±10%**（[util.go:49](../../apps/relation/internal/repository/util.go#L49) `getRandomExpireTime`，防雪崩）+ RedisBloom 挡注册查重穿透。
- ✅ **无 `dbresolver` 读写分离**：单库读写，因此不存在"写后读从库旧数据"的一致性问题（该担忧不适用）。

### 7.4 完备性 critic（前 9 维度未覆盖的盲区）

按重要度排序，部分已实际读码确认：

1. **【已确认 medium】用户资料/群资料缓存 TTL 无随机抖动**：relation 侧有 `getRandomExpireTime` 抖动，但 `UserProfileTTL`/`GroupInfoTTL` 是固定 1h（[keys.go:21,41](../../consts/redisKey/keys.go#L21)）。大量同时签发的资料缓存会在整点附近集中过期，存在局部雪崩点。建议统一走带抖动的过期时间。
2. **【需查证 / 面试高频】Kafka 扩分区破坏会话保序**：msg.push 用 conv_id 作 key 做 hash 分区保序，但一旦给 topic **增加分区数**，同一 conv_id 的 hash 落点会变，迁移期间同会话消息可能跨分区导致消费端短暂乱序。当前单分区/固定分区不触发，但这是"按 key 保序"方案的固有约束，面试可能被追问，建议想清楚应对（如按 conv_id 取模固定分区数、或扩分区时停写迁移）。
3. **【需查证】雪花时钟回拨处理**：用 `bwmarrin/snowflake`，NTP 校时或宿主机时钟回拨时该库会返回重复/异常 ID 或阻塞，未见专门处理。叠加已知的硬编码 node ID，分布式 ID 的健壮性是薄弱环节。
4. **【需查证】群成员人数上限**：数据层探查到"成员上限"相关代码但未确认是否真有 `maxMember` 限制。若无上限，超大群会直接打爆 message-push 的逐成员扇出（已知的下行性能问题）和 `group:members:` 大 key。
5. **【需查证】消息撤回/已读回执的时间窗与权限**：撤回是否有"2 分钟内"时限、能否撤回他人消息、已读回执是否有频率上限，未系统核实。
6. **【需查证】多端 seq/已读位点一致性**：同账号多设备的已读位点合并、seq gap 在多端下的去重，边界场景未覆盖。

**critic 结论**：以上多为"防御纵深不足"或"固有约束未文档化"，没有发现新的 critical/high；最值得补的是缓存 TTL 抖动统一化（1.1）和把 Kafka 扩分区保序约束（1.2）写进文档并准备面试说法。
