### 亮点: Outbox + Debezium CDC 的可靠事件投递（含 EventRouter SMT 路由）
证据: pkg/outbox/store.go:14-22 InsertEvent 在业务事务内只负责落盘、无进程内分发循环；apps/msg/internal/domain/message/repository_impl.go:176-196 CreateWithOutbox 把 message 与 outbox_events 放在同一个 GORM Transaction；scripts/cdc/register_outbox_connector.sh:50-57 注册 Debezium MySQL connector 并用 io.debezium.transforms.outbox.EventRouter 按 event_type 路由 topic、entity_id 作 Kafka key；docker-compose.yml 含 kafka-connect 与 cdc-init 服务。
面试话术: 讲三层：①问题——「先写库再发 Kafka」存在双写不一致窗口，进程在两步之间崩溃就丢事件；②方案对比——本地轮询 outbox 表（实现简单但有扫表延迟和 DB 压力）、RocketMQ 事务消息（半消息+回查，引入新组件且回查逻辑侵入业务）、CDC（伪装成 MySQL slave 读 binlog，零侵入、延迟低，但引入 Kafka Connect 运维面）；③本项目的取舍——选 CDC 后业务代码只剩「同事务插一行」，pkg/outbox 里连状态机都删掉了，复杂度全部外移给 Debezium；同时要主动说出代价：语义是 at-least-once，所以下游必须幂等（这正好引出第二个亮点），且 entity_id=conv_id 作 key 保证了同会话事件在同分区内有序。能把「为什么 outbox 表里没有 status 字段」讲清楚，就赢了大部分背八股的候选人。
### 亮点: 发送链路三层幂等：Redis SETNX 三态锁 → DB 唯一索引兜底 → 消费端 idempotent_events
证据: apps/msg/internal/domain/message/repository_impl.go:62-118 TryAcquireIdempotent 用 SETNX(PROCESSING,10s) 实现「获锁/处理中/命中缓存」三态，并画了 ASCII 决策树；service.go:185-199 落库撞 uidx_sender_client 唯一索引时回查首次结果按幂等成功返回（SETNX 降级路径）；pkg/outbox/store.go:26-43 消费端 CheckIdempotent/MarkIdempotent 配 OnConflict DoNothing；apps/group/internal/consumer/cache_projector.go:85-104 展示 decode→查幂等→投影→标记 的标准消费样板。
面试话术: 按「客户端重试、服务端降级、消息重投」三个故障源分别讲对应防线：客户端断网重发由 (from,device,client_msg_id) 的 Redis 三态锁拦截，首次结果回写成 JSON 缓存直接返回；Redis 挂了走 DB 唯一索引兜底，冲突时查回原消息而不是报错——这体现「幂等要返回首次结果，不是拒绝」；Kafka at-least-once 重投由消费端 idempotent_events 表挡。要敢于自曝边界：消费端是 check→do→mark 三步非原子，Redis 投影这种天然幂等操作可以接受重复执行，但如果业务动作不幂等就需要把 mark 和业务写放进同一事务——说明你知道这个模式的适用范围，而不是当万能药。
### 亮点: Kafka 累积提交语义下的防静默丢消息消费器
证据: pkg/kafka/consumer.go:119-158 consumeOnSuccess 的注释明确写出根因：「segmentio/kafka-go 的 FetchMessage 不会重投未提交消息，而 Kafka 的 offset 提交是累积的，若失败后直接拉下一条并在其成功时提交，会把这条失败的 offset 一并提交，造成静默丢失」，因此失败时退避后就地重试同一条；panic 视为确定性毒消息，提交跳过防止崩溃循环卡死分区（136-141 行）；git log 08ee63e 是对应的修复 commit。
面试话术: 这是全仓库最能体现「踩过坑」的点，建议当成事故复盘来讲：现象（少量消息没推送、无报错）→ 排查（消费失败后跳过继续拉，下一条成功提交时把失败那条的 offset 一并带过线）→ 根因（Kafka offset 提交是水位线语义不是单条 ACK）→ 修复（CommitOnSuccess 模式失败就地重试，绝不前进）→ 新问题（毒消息会卡死分区怎么办？）→ 约定（handler 对解码失败等永久错误返回 nil 自行跳过，panic 按永久错误提交跳过并告警）。再对比 message-push 的另一套策略（apps/message-push/internal/consumer/consumer.go:358-381：有限重试 3 次后提交丢弃+打 MessagesDroppedAfterRetry 指标，靠客户端按 seq 拉取兜底）——同一个系统里两条链路用不同的丢弃策略，能讲出「推送可丢、状态投影不可丢」的差异化取舍就非常出彩。
### 亮点: seq 连续性体系：Redis INCR 分配 + ACK 位点只前进 Lua + 客户端 gap 检测兜底
证据: apps/msg/internal/domain/message/repository_impl.go:41-48 AllocSeq 用 Redis INCR 按 conv_id 原子分配会话内严格递增 seq；apps/connect/internal/svc/ack.go:29-45 storeMessageAckScript Lua 脚本保证 ACK 位点并发下只前进不回退；message-push 丢弃事件后注释明确「依赖客户端按 seq 拉取兜底」（consumer.go:366）。
面试话术: 先讲为什么 IM 需要会话内连续 seq：排序、多端同步、丢消息检测三件事都靠它。再讲分配方案对比：DB 自增（强一致但热点会话锁竞争）、号段（高吞吐但崩溃浪费号段导致 gap，gap 检测就失效）、Redis INCR（低延迟、严格 +1，但 Redis 持久化策略决定了宕机可能回退）。关键是主动答出软肋：Redis AOF everysec 下宕机最多丢 1 秒 INCR，seq 回退会导致新消息 seq 与已落库消息重复——缓解手段是恢复时用 MAX(seq) FROM message 校准、或对 seq 键用 WAIT/持久化更强的配置。能把「我知道 INCR 不是免费午餐」讲出来，比答「用 Redis 原子性保证」深一个层级。
### 亮点: 在线路由 TTL 与心跳节流的协同设计（TTL = 2×节流间隔）
证据: apps/connect/internal/svc/connect_service.go:113-117 注释「路由 Key TTL 必须 >= 2×UpdateInterval：心跳刷新被节流到每 UpdateInterval 一次」并按此派生 routeTTL；lifecycle.go:46-84 OnConnect 强刷路由/OnHeartbeat 节流刷新/OnDisconnect 删除；routing.go:63-129 节点下线用 SCAN（非 KEYS）按 connect 地址清理残留路由；git log 08ee63e 记录了「路由 TTL 与心跳节流撞车」的修复。
面试话术: 讲一个真实 bug 故事：心跳本身 30 秒一次，但为了减少 Redis 写入做了本地节流，结果节流间隔逼近路由 TTL，一次心跳被节流吞掉后路由就过期了——在线用户被判离线、消息走了离线链路。修复思路是把两个本来独立配置的参数绑定成约束：TTL 恒等于 2 倍节流间隔，容忍丢一次刷新。延伸讲故障矩阵：正常断开走 OnDisconnect 主动删路由；kill -9 没机会清理，靠 TTL 自然过期（最坏 2×interval 内推送会失败，message-push 重试后丢弃靠拉取兜底）；节点重启用 SCAN 扫 user:routing:* 清理本节点残留——为什么用 SCAN 不用 KEYS 也是必考点。这个点的精髓是「分布式系统里两个超时参数之间必须有显式约束关系，不能各配各的」。
### 亮点: 熔断器只对基础设施故障计失败的精细化错误分类
证据: pkg/grpcx/client_circuit_breaker.go:14-51 BreakerIsSuccessful 把 Unavailable/DeadlineExceeded/Internal/Unknown/DataLoss 计为失败，InvalidArgument/Unauthenticated/NotFound/AlreadyExists 等业务码与 context.Canceled 计为成功，注释写明「错误密码风暴、批量校验失败等正常流量就会拖垮失败率并误触熔断（自伤）」；git log f56ef00 对应该修复；pkg/grpcx 下另有超时、限流、重试归一化等 13 个带测试的拦截器文件。
面试话术: 大多数候选人只会背「熔断三状态」，这个项目能讲一层罕见的细节：熔断器的输入信号必须先做错误分类，否则一波撞库攻击（全是 Unauthenticated）会把健康的 auth 服务熔断、殃及正常用户登录——这就是「自伤型熔断」。再主动讨论两个灰色地带体现思辨：①ResourceExhausted 本项目定义为业务限流所以算成功，但如果下游真因过载返回它，熔断器就感知不到压力——前提是项目内限流语义统一；②context.Canceled 是调用方放弃不是下游故障，但 DeadlineExceeded 算失败，因为超时大概率反映下游慢。能讲清「熔断器保护的是调用方资源，不是惩罚下游」这个本质，就到位了。
### 亮点: RedisBloom 存在性过滤器的工程化封装（false negative 防御纪律）
证据: pkg/redisbloom/redis_bloom.go:14-16 注释定下纪律「业务写入新实体时必须先 Add 再写 DB，避免出现 DB 已存在但 Bloom 判不存在的 false negative」；29-56 Ensure 用 sync.Map 做进程内一次性 BF.RESERVE 并把『已存在』视为成功；61-103 Exists/MExists 返回三态 (exists, usable, err)，RedisBloom 不可用时 usable=false 让读路径回源 DB；git log 8ffad4f 对应落地 commit。
面试话术: 布隆过滤器是面试高频题，但这个实现有三个超出八股的点可讲：①方向性纪律——布隆只能保证「判不存在一定不存在」，所以写顺序必须是先 Add 再写 DB，一旦反过来就会把真实存在的用户当不存在挡掉（这是大多数人会写反的地方）；②三态返回值设计——exists/usable/err 分离，让「布隆不可用」降级回源 DB 而不是误判，体现对降级路径的显式建模；③为什么用 RedisBloom 模块而不是自己拿 bitmap+多个 hash 实现——BF.RESERVE 支持容量与误判率声明式配置且可扩展子过滤器。再补一句使用场景（注册手机号/账号查重挡穿透）和误判率与容量的容量规划公式，就是完整答案。
