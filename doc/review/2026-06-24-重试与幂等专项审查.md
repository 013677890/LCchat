# 重试与幂等专项审查（2026-06-24）

## 1. 背景与范围

从微服务设计视角，系统性审查 LCChat 后端的**重试（retry）**与**幂等（idempotency）**机制，覆盖：

- 基础设施层：`pkg/kafka`、`pkg/outbox`、`pkg/redisretry`、`pkg/grpcx`、`pkg/async`、`pkg/realtimepush`
- 消息主链路：msg-service 发送/撤回、CDC outbox、message-push 下行、connect 推送
- 非消息链路：auth/user/relation/group 的事件发布与消费、账号注销 saga、connect 路由注册/ACK

## 2. 审查方法（含对抗性验证）

每一条疑似问题都经过**对抗性验证**：尽力去**证伪**它——读真实代码路径、配置、唯一索引、并发守卫，确认问题在当前代码下确实可触发，才列为「确认」。被证伪的疑似项单列在第 5 节，作为「已排除」记录，避免误报。

证据以 `file:line` 标注，可点击跳转。

## 3. 结论摘要

总体评价：**消息发送主链路（msg→outbox→CDC→message-push）的幂等设计扎实**（三层防御 + 同事务 outbox）；但**跨服务重试在全局层面存在放大风险**，且**消费端幂等是「伪 exactly-once」**，非消息链路（realtime 通知、好友申请）的可靠性与幂等明显弱于消息链路。

|---|---|---|---|---|

| R2 | 高 | 重试 | 整 service 级重试把 `UNKNOWN`/`DEADLINE_EXCEEDED` 作用于全部方法（含非幂等写） | 确认 |

## 4. 详细发现

### R1（高）嵌套重试相乘放大，内部连接无熔断、无 retryThrottling

**现象**：各层重试相乘，没有全局预算；只有网关出站连接注入了熔断器，服务间内部连接只有重试没有熔断，且 service config 里没有 `retryThrottling`。

**证据**：
- 默认重试骨架 `MaxAttempts=5`：`pkg/grpcx/client_builder.go:75-85`
- 网关注入熔断器：`apps/gateway/internal/pb/client_connection.go:41-43`
- msg→group/relation 连接**只有重试无熔断**：`apps/msg/cmd/providers.go:94-98`、`108-115`
- message-push→connect **只有重试无熔断**：`apps/message-push/internal/connectcli/manager.go:41-48`
- message-push handler 自身重试 3 次：`apps/message-push/internal/consumer/consumer.go:28`、`386-422`
- service config 无 `retryThrottling` 字段：`pkg/grpcx/client_builder.go:170-237`

**链路放大举例**：
- message-push 推一条消息 = handler 3 次 × connect gRPC 5 次 = 最多 **15 次/设备**，群聊再乘成员数。
- 网关发一条消息 5 次重试，每次又触发 msg→relation+group 各 5 次。

**对抗性验证**：确认内部连接 provider 未传 `ExtraUnaryInterceptors`/breaker；`buildClientServiceConfig` 生成的 JSON 不含 `retryThrottling`。下游真正宕机时，重试会把下游「重试到死」，与重启风暴叠加。**问题成立**。

**建议**：service config 增加 `retryThrottling`（令牌桶）；内部 mutating 连接接熔断器；按层设置递减重试预算（越靠近底层越少）。

---

### R2（高）整 service 级重试 + `UNKNOWN`/`DEADLINE_EXCEEDED` 作用于非幂等写

**现象**：`RetryableStatusCodes = [UNAVAILABLE, DEADLINE_EXCEEDED, UNKNOWN]`，且按整个 service 名匹配，该 service 所有方法（含非幂等写）共用同一套重试。

**证据**：
- 重试码：`pkg/grpcx/client_builder.go:83`
- service 级（非方法级）匹配：`pkg/grpcx/client_builder.go:221-237`（`name: [{service: ...}]`）
- 网关对 relation 整体重试：`apps/gateway/internal/pb/client_connection.go:69-72`
- `UNKNOWN` 曾真实出现：git log `c675f06 修复 apperr 在归一化层外退化为 codes.Unknown`

**对抗性验证**：
- gRPC service-config 重试是**顺序**的（收到上一 attempt 的可重试码后才重试），所以「检查-再读」类写在顺序重试下大多被吸收成 AlreadyExists（前次写已提交、对重试可见）。
- 但 `DEADLINE_EXCEEDED` 场景下**服务端可能仍在执行第一次**（客户端先放弃），重试与在途请求**并发**，二者都可能越过前置检查 → 双重副作用。对没有唯一约束/幂等键的写（见 I3）会产生重复行。`UNKNOWN` 作为「未归一化错误」兜底码尤其危险：一个本应是业务失败的 Unknown 会被重试 5 次。**问题成立**（对非幂等写）。

**建议**：重试按**方法**声明，仅对幂等方法（读 + 带幂等键的写）开启；默认从可重试码中移除 `UNKNOWN`。

---

### I1（高）消费端 `Check→业务→Mark` 非原子，「伪 exactly-once」

**现象**：所有领域事件消费者都是「查幂等表 → 业务处理 → 写幂等表」三步，业务处理与 `MarkIdempotent` **不在同一事务**。在第 2 步成功、第 3 步前崩溃/重平衡时，消息重投会**再执行一次业务**。

**证据**（同一模式遍布）：
- `pkg/outbox/store.go:26-43`（Check/Mark 是各自独立的 DB 调用）
- group 缓存投影：`apps/group/internal/consumer/cache_projector.go:85-104`
- user 资料初始化：`apps/user/internal/consumer/user_created_consumer.go:66-83`
- user 注销清理：`apps/user/internal/consumer/account_deleted_consumer.go:60-74`
- relation 注销清理：`apps/relation/internal/consumer/account_deleted_consumer.go:68-85`
- auth 展示字段同步：`apps/auth/internal/consumer/profile_display_changed_consumer.go:66-83`

**对抗性验证**：逐个检查现有业务操作是否**碰巧幂等**：
- `CreateProfile`「已存在直接复用」→ 幂等（`apps/user/internal/service/internal_profile_service.go:42`）✅
- group 缓存投影 Redis（LWW）→ 幂等 ✅
- user/relation 注销清理（delete 语义）→ 幂等 ✅

结论：**当前能正确，纯粹因为业务操作恰好都幂等，而不是因为幂等表**。幂等表只降低重复概率，不提供 exactly-once。该模式给人「有幂等表=exactly-once」的错觉——一旦有人往这个模板塞一个**非幂等**操作（计数+1、发邮件、给用户加钱），立即双花。**问题成立**（设计脆弱性）。`doc/review/2026-06-12-审查原始材料.md:63` 团队自己也提过这个点。

**建议**：业务写与幂等记录同库时，把 `MarkIdempotent` 收进业务写的**同一事务**（真正 exactly-once）；跨库（如 Redis 投影）时必须在代码注释/约定中**显式声明「依赖业务操作幂等」**。可参考消息链路的 `CreateWithOutbox`（`apps/msg/internal/domain/message/repository_impl.go:234-254`）——业务事实 + outbox 同事务，正是该学习的范式。

### I3（中）`SendFriendApply` 检查-再插入，无唯一约束/幂等键 → 重复待处理申请

**现象**：`SendFriendApply` 先 `ExistsPendingRequest`（检查）再 `Create`（插入新行），既无 DB 唯一约束、也无幂等键。

**证据**：
- 检查-再插入：`apps/relation/internal/service/friend_service.go:94-100`、`131`
- `apply_requests` 只有**非唯一**索引 `idx_applicant_target`：`model/ApplyRequest.go:15-16`
- 模型注释本身规定的语义是「找到旧的 Status=0 记录并更新」，但代码却是插入新行：`model/ApplyRequest.go:31-34`
- 而 `relation.FriendService` 被网关按 `UNKNOWN`/`DEADLINE_EXCEEDED` 重试：`apps/gateway/internal/pb/client_connection.go:69-72`

**对抗性验证**：
- 对照 `UserRelation` 有唯一索引 `uidx_user_peer`（`model/UserRelation.go:13-14`）能挡住重复好友关系——但 `apply_requests` **没有**对应约束。
- 触发路径：① 用户双击/并发两次申请；② R2 描述的 `DEADLINE_EXCEEDED` 下重试与在途首次请求并发，二者都越过 `ExistsPendingRequest` → 两条 `Create`。无唯一索引兜底 → **两条 Status=0 重复申请落库**，正是模型注释警告的「B 的列表里 10 条全是 A 发来的申请」。**问题成立**。

**建议**：二选一——
1. 给 `apply_requests` 加唯一约束（如 `(apply_type, applicant_uuid, target_uuid)` 限定 status=0 的部分唯一 / 生成列）；
2. 把 `Create` 改成 upsert：命中既有 pending 行则 `UpdatedAt` 刷新 + `IsRead=0`，与模型注释的既定意图一致。

### I4（中）realtime 通知走直发 Kafka（双写、异步 fire-and-forget），可静默丢失

**现象**：与消息走「事务 outbox + CDC」不同，relation/group 的实时通知（好友申请、好友关系变化、群状态变化、入群申请/审批、踢人、解散、禁言）是 DB 提交后**直接 publish 到 Kafka**，且丢进异步协程池 fire-and-forget，错误只打 Warn。

**证据**：
- 直发生产者（非 outbox）：`pkg/realtimepush/producer.go:47-63`（`SendWithKey`）
- relation 异步发布、错误吞掉：`apps/relation/internal/service/realtime_notify.go:104-129`
- group 同样：`apps/group/internal/service/realtime_notify.go:140-165`
- 协程池**非阻塞**（满即丢，仅计数）：`pkg/async/pool.go:131`（`WithNonblocking(true)`）、`353-357`
- 发布在 DB 写成功之后：`apps/relation/internal/service/friend_service.go:131→135`

**对抗性验证**：
- 是否「幻象通知」（写回滚了却发通知）？——发布在 `Create` 成功后调用，**仅丢失、不幻象**。✅ 排除幻象。
- 是否真会丢？丢失窗口确认存在：① 协程池满 → `Submit` 失败任务被丢（`submitRejected` 计数）；② Kafka 持续不可达，kafka-go writer 内部重试耗尽/2s 超时 → 仅 Warn；③ 进程在「DB 提交后、协程执行前」崩溃 → 丢。**问题成立**（弱于消息链路的可靠性）。
- 影响边界：这些是「提醒」，客户端可通过拉取（好友申请列表、群信息）对账，因此多为**一致性延迟**而非永久不一致——**前提是客户端确有拉取对账**。对没有拉取兜底的事件（如「你被踢出群/群已解散」）丢失体验更差。

**建议**：明确分级并文档化「消息=可靠 outbox，提醒=尽力直发 + 客户端拉取对账」；对无拉取兜底的关键提醒（踢人/解散）考虑纳入 outbox 或补对账接口；监控 `SubmitRejectedTotal()` 并告警。

### R3（中）message-push 对 `seq==0` 事件重试耗尽即丢，无拉取兜底

**现象**：本地重试（3 次）耗尽后提交 offset 丢弃事件，注释称「依赖客户端按 seq 拉取兜底」。但撤回/已读/realtime 事件 `seq==0`，客户端无 seq 可拉。

**证据**：
- 丢弃逻辑：`apps/message-push/internal/consumer/consumer.go:366-374`
- 撤回事件 `Seq: 0`：`apps/msg/internal/domain/message/service.go:421`
- ack 仅对 `MSG_PUSH && seq>0` 要求：`apps/message-push/internal/consumer/ack.go:3-5`

**对抗性验证**：`MSG_PUSH` 有 seq，客户端 gap 补拉可兜底 ✅；`MSG_RECALL`/`MSG_MARK_READ`/`MSG_READ_RECEIPT`/realtime 无 seq，确认**无拉取兜底**，connect 持续抖动 >~1.2s 即永久丢失撤回/已读。**问题成立**。

**建议**：无 seq 类事件不能走「丢弃+依赖 seq 拉取」；引入 DLQ/重投，或客户端提供撤回/已读独立对账接口。

### A1（中）手动提交消费者无 DLQ/最大重试，毒消息永久阻塞分区

**现象**：`consumeOnSuccess` 对 handler 返回的非 nil 错误**就地无限重试**（仅退避），没有最大重试次数、没有 DLQ。约定靠 handler「永久错误返回 nil 自行跳过」，但 DB 写失败等**确定性非解码错误**返回的是非 nil。

**证据**：
- 无限就地重试：`pkg/kafka/consumer.go:129-158`
- 各消费者对清理/写库失败返回非 nil（会进入无限重试）：如 `apps/relation/internal/consumer/account_deleted_consumer.go:77-85`

**对抗性验证**：解码错误确实 `return nil` 跳过（`account_deleted_consumer.go:62-66`）✅；但一个确定性失败的清理（如某行触发约束、schema 不一致、下游恒返回错误）会让该分区**永久卡在这条消息**，阻塞后续所有事件，且无告警出口。**问题成立**。

**建议**：增加最大重试次数 + DLQ（或死信表）；区分「可重试 vs 永久」失败到达上限后旁路并告警。

---

### R4（中）redisretry 补偿队列：静默丢弃 + 重试丢失顺序

**现象**：
1. `SendRedisTask` 在全局 producer 为 nil 时**直接返回 nil**，上层却记日志「已发送到重试队列」，实际什么都没入队。
2. 重试用 `producer.Send`（无 key）→ 轮询分区 → 跨任务无序；同 key 的 `DEL` 与稍后 `SET` 可能乱序执行，把已删脏缓存复活。
3. `RedisRetryConsumer` 用 `CommitAlways`，handler 错误被吞，重试完全靠重投，重投 `Send` 再失败任务即丢。

**证据**：
- 静默 nil：`pkg/redisretry/manager.go:31-43`
- 无 key 发送：`pkg/redisretry/manager.go:42`、重投同样无 key：`pkg/redisretry/consumer.go:69-70`
- 消费者用 `NewConsumer`(=CommitAlways)：`pkg/redisretry/consumer.go:30`、`pkg/kafka/consumer.go:55-64`、`104-108`

**对抗性验证**：单命令（DEL/SET/HSET 等）各自幂等 ✅，但**相互之间不保序**，对「先 SET 后 DEL」「DEL 后又被旧 SET 覆盖」的缓存清理场景确有脏读风险。producer 未注入时（`SetGlobalProducer` 漏调）补偿全部静默丢失且无告警。**问题成立**。

**建议**：`SendRedisTask` 在 producer 为空时返回错误/告警而非静默 nil；补偿任务按 key 发送保序；或对同 key 操作引入版本号/时间戳防回退。

---

### I2（中）message-push 无服务端去重，重投即重推

**现象**：Kafka 至少一次 + CDC 至少一次 + offset 提交失败重处理，message-push 仅做单批次内路由去重，无跨消息幂等，重投时对所有在线设备重推。

**证据**：
- 仅批内去重：`apps/message-push/internal/consumer/consumer.go:243-253`
- 提交失败仅日志后继续：`apps/message-push/internal/consumer/consumer.go:376-381`
- kafka 生产者非幂等（仅 RequireAll）：`pkg/kafka/producer.go:40-49`

**对抗性验证**：`MSG_PUSH` 客户端按 seq 去重 ✅；但 recall/已读类无 seq，客户端会收到重复撤回/已读提醒。整链「不重复」压在客户端行为上。**问题成立**（与 R3 同源，互为补充）。

**建议**：与 R3 一并解决无 seq 事件的去重（客户端按 event_id 去重，或服务端 ack 位点去重）。

---

### A2（低）connect 设备状态 RPC 队列满即丢 + 失败仅日志 → 状态漂移

**现象**：上线/下线时通过有界队列（8192）异步调 auth `UpdateDeviceStatus`，队列满即丢（仅 Warn），RPC 失败也仅 Warn，无重试无对账。

**证据**：
- 队列满丢弃：`apps/connect/internal/svc/lifecycle.go:90-113`
- RPC 失败仅日志：`apps/connect/internal/svc/lifecycle.go:117-139`

**对抗性验证**：丢弃/失败后 `device_session.status` 不再被纠正，确认**无对账**。影响：设备在线/离线状态可能与真实长期不一致。但这是展示态而非路由态（路由走 Redis，由 message-push 按 `activeAt` 过滤，见第 5 节），影响面有限。**问题成立**（低）。

**建议**：状态 RPC 失败/丢弃计入指标并告警；或周期性以 connect 在线索引为准对账 DeviceSession。

| **同节点重连误删新路由** | `Unregister` 指针相等校验 + handler `removed` 守卫：旧连接 teardown 时 map 已指向新 client，`Unregister` 返回 false → 不触发 `OnDisconnect` → 不删路由。`apps/connect/internal/manager/connection_manager.go:107`、`apps/connect/internal/handler/ws_handler.go:151-154` |

| **gRPC 顺序重试导致好友申请重复** | 顺序重试下前次写已提交且对重试可见，多被吸收为 AlreadyExists；真正风险是 `DEADLINE_EXCEEDED` 下的**并发**在途+重试（已并入 I3，且根因是缺唯一约束，而非重试本身） |

## 6. 修复优先级建议

1. **R2 + R1（改 service config）**：重试按方法声明、移除 `UNKNOWN`、加 `retryThrottling`、内部连接补熔断——当前最大的「重试正确性 + 雪崩」风险，且改动集中、收益最高。
2. **I3**：给 `apply_requests` 加唯一约束或改 upsert——小改动，直接消除已确认的重复申请。
3. **I1**：同库场景把 `MarkIdempotent` 收进业务同事务；跨库场景显式声明依赖幂等——根治「伪 exactly-once」脆弱性。
4. **A1 + R3 + I2**：消费侧引入 DLQ/最大重试，并为无 seq 事件设计去重与兜底对账。
5. **R4 / I4 / A2**：补静默丢弃的告警与按 key 保序，明确并文档化「提醒=尽力 + 客户端对账」的可靠性分级。
