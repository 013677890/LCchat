# 好友与黑名单

本文描述用户搜索、发送好友申请、处理申请、同步好友列表、备注标签和黑名单对关系与消息权限的影响。接口定义见 [关系接口](../api/03-关系接口.md)。

## 1. 参与组件

| 组件 | 职责 |
| --- | --- |
| gateway | HTTP 入站、分页参数、DTO 转换。 |
| user | 提供搜索和资料展示字段。 |
| relation | 好友、黑名单、申请事实。 |
| msg | 发送单聊消息前做关系权限判断。 |
| Redis | 好友/黑名单缓存、申请未读数。 |

## 2. 用户搜索链路

入口：`GET /api/v1/auth/user/search`

步骤：

1. gateway 校验 `keyword/page/pageSize`。
2. user 根据关键字查询资料域。
3. 若需要展示 `isFriend`，由 user / gateway 结合关系能力补充。
4. 前端展示搜索结果并根据 `isFriend` 决定按钮文案。

注意：搜索只是发现目标用户，不代表可以直接建立关系。

## 3. 发送好友申请

入口：`POST /api/v1/auth/friend/apply`

请求关键字段：

| 字段 | 说明 |
| --- | --- |
| `targetUuid` | 目标用户 UUID。 |
| `reason` | 申请理由。 |
| `source` | 来源，如搜索、二维码。 |

处理规则：

1. 不能添加自己为好友。
2. 已经是好友时直接拒绝。
3. 已存在待处理申请时直接拒绝。
4. 若对方已将你拉黑，通常不允许继续申请。
5. 成功后返回 `applyId`，并更新对方未读申请计数。

## 4. 收到申请与处理申请

### 4.1 收到申请列表

接口：`GET /api/v1/auth/friend/apply-list`

前端常见用法：

- `status=0`：待处理；
- `status=-1`：全部；
- 打开申请页时同步调用未读数接口。

### 4.2 发出申请列表

接口：`GET /api/v1/auth/friend/apply/sent`

适合在“我的申请记录”中展示审核中、已通过、已拒绝状态。

### 4.3 处理申请

接口：`POST /api/v1/auth/friend/apply/handle`

处理动作：

| `action` | 说明 |
| --- | --- |
| `1` | 同意。 |
| `2` | 拒绝。 |

同意时关系事实变化：

1. relation 为双方各写入一条正常好友关系；
2. 好友列表版本号递增；
3. 申请状态改为已同意；
4. 相关缓存失效或刷新。

拒绝时：

- 只更新申请状态，不创建好友关系。

## 5. 申请已读与未读数

接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/auth/friend/apply/unread` | 拉取未读数量。 |
| `POST /api/v1/auth/friend/apply/read` | 批量标记已读。 |

典型前端流程：

1. 进入通讯录或申请页前先拉未读数；
2. 打开申请页后将当前可见申请批量标记为已读；
3. 本地同步清零角标或递减。

## 6. 好友列表与增量同步

### 6.1 全量好友列表

接口：`GET /api/v1/auth/friend/list`

适用场景：

- 冷启动首次进入通讯录；
- 本地缓存不可用；
- 增量同步逻辑需要重置时。

返回关键字段：

| 字段 | 说明 |
| --- | --- |
| `items` | 当前页好友。 |
| `pagination` | 分页信息。 |
| `version` | 当前好友关系版本号。 |

### 6.2 增量同步

接口：`POST /api/v1/auth/friend/sync`

关键字段：

| 字段 | 说明 |
| --- | --- |
| `version` | 客户端当前持有版本。 |
| `limit` | 单次最多拉取多少条变更。 |

返回：

- `changes`：`add/update/delete` 变更；
- `hasMore`：是否还有后续变更；
- `latestVersion`：最新版本号。

推荐策略：

1. 首次用全量列表拿到 `version`；
2. 后续页面恢复、应用重启后先做 `sync`；
3. `hasMore=true` 时持续拉取直到 false；
4. 同步失败时可回退到全量列表。

## 7. 备注与标签

接口：

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/auth/friend/remark` | 设置备注。 |
| `POST /api/v1/auth/friend/tag` | 设置标签。 |
| `GET /api/v1/auth/friend/tags` | 获取标签列表和数量。 |

语义：

- 备注和标签都属于“当前用户视角”的关系字段；
- 不会影响对端看到的资料；
- 变更后好友版本也可能推进，便于多端同步。

## 8. 删除好友

接口：`POST /api/v1/auth/friend/delete`

影响：

1. 双方好友关系被移除或标记删除；
2. 好友列表和版本号更新；
3. 备注、标签等附加信息失效；
4. 单聊发消息权限可能发生变化，取决于业务规则是否要求必须为好友。

## 9. 黑名单链路

### 9.1 拉黑

接口：`POST /api/v1/auth/blacklist`

影响：

1. relation 记录黑名单状态；
2. 好友关系展示可能变为黑名单关系；
3. 后续单聊发消息权限会受影响；
4. 前端应刷新关系状态、好友按钮和会话页提示。

### 9.2 取消拉黑

接口：`DELETE /api/v1/auth/blacklist/:userUuid`

影响：

- 解除黑名单限制，但不会自动恢复已删除的好友关系。

### 9.3 黑名单列表与判断

接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/auth/blacklist` | 黑名单列表。 |
| `POST /api/v1/auth/blacklist/check` | 判断是否已拉黑。 |

## 10. 关系状态查询

接口：`POST /api/v1/auth/friend/relation`

返回：

| 字段 | 说明 |
| --- | --- |
| `relation` | `none/friend/blacklist/deleted`。 |
| `isFriend` | 是否好友。 |
| `isBlacklist` | 是否存在黑名单关系。 |
| `remark` | 当前用户对对端的备注。 |
| `groupTag` | 当前用户对对端的标签。 |

前端适用场景：

- 用户详情页决定展示“加好友 / 发消息 / 解除拉黑”等按钮；
- 会话页显示关系状态提示；
- 搜索结果页更新按钮状态。

## 11. 对消息发送权限的影响

relation 与单聊消息存在直接协作：

1. msg 发送单聊消息前会调用 relation 检查关系；
2. 若不是好友、已被对方拉黑、你已拉黑对方，可能直接返回业务错误；
3. 因此前端关系按钮与消息发送入口应共享同一份关系状态缓存。

## 12. 前端实现建议

1. 通讯录首页优先使用 `friend/list + version`，后续用 `sync` 增量刷新。
2. 处理申请成功后，不要只改申请页状态，也要同步更新用户详情页和会话页关系按钮。
3. 拉黑成功后应主动关闭会话输入框，直到关系状态刷新完成。
4. `userUuid` 字段在部分接口中虽然与当前登录用户重复，但当前 DTO 仍要求显式传入，前端不要省略。
