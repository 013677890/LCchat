# 群组创建申请与成员变更
本文描述群创建、加群申请、审批、成员增删、群主转让、角色调整和禁言变更的完整链路。接口定义见 [群组接口](../api/04-群组接口.md)，缓存投影见 [Group-Outbox与缓存投影](../architecture/Group-Outbox与缓存投影.md)。

## 1. 参与组件
| 组件 | 职责 |
| --- | --- |
| gateway | HTTP 入站、路径参数与 DTO 校验。 |
| group | 群事实写入、权限校验、入群申请、成员管理。 |
| Redis | 群资料、成员、用户群列表、待审批申请缓存。 |
| Kafka / Debezium | 传播 `group.cache` 事件。 |
| msg | 群消息发送前调用 group 校验权限，并独立消费 `group.cache` 维护成员会话投影。 |
| message-push | 群聊下行时依赖群成员缓存或成员能力做扩散。 |
## 2. 创建群链路
入口：`POST /api/v1/auth/groups`

请求关键字段：
| 字段 | 说明 |
| --- | --- |
| `name` | 群名称。 |
| `avatar` | 群头像 URL。 |
| `memberUuids` | 初始邀请成员列表。 |
处理步骤：
1. gateway 校验请求体，透传当前登录用户身份。
2. group 生成新的 `group_uuid`。
3. group 写入 `groups` 表：群名称、头像、群主、加群方式、初始人数等。
4. group 为创建者写入 `group_members`，角色为群主。
5. 若请求中带 `memberUuids`，group 按当前规则插入成员关系。
6. group 在同一事务内递增 `groups.cache_version` 并写 `outbox_events`；事件为严格 `schema_version=2`，action 通常为 `group_created`。
7. HTTP 返回 `groupUuid`。

同步返回成功的判定点是 MySQL 事务提交成功，不等待 Redis 缓存投影完成。

## 3. 建群后的缓存投影
建群成功后，`group.cache` 事件会异步更新：
| Key | 作用 |
| --- | --- |
| `group:info:{group_uuid}` | 群资料缓存。 |
| `group:members:{group_uuid}` | 群成员缓存。 |
| `group:user_groups:{user_uuid}` + 版本 Hash | 用户已加入群列表及逐群版本 tombstone。 |

所有状态更新由版本感知 Lua 原子执行。写请求提交后不再直接异步 patch Redis；读 miss 会回源，并用重新读取的数据库完整快照做版本化修复。
因此前端可能遇到短暂现象：建群接口已成功，但紧接着读取群列表或成员列表时，缓存视图尚未完全更新。此时应允许短暂重试或做本地乐观更新。

同一事件还会被 msg 的独立 consumer group 完整消费：`group_created/member_added`
激活对应成员 `conversation`，`member_removed` 写目标成员退出 tombstone，
`group_dismissed` 更新一条共享群状态。message-push 不参与该投影链路。

## 4. 加群申请链路
入口：`POST /api/v1/auth/groups/:groupUuid/apply`

### 4.1 直接入群模式
当 `addMode=0` 时：
1. group 校验群存在且用户未在群内。
2. 直接写入 `group_members`。
3. 写 `group.cache` 事件，action 通常为 `member_added`。
4. 返回 `joinedDirectly=true`。

### 4.2 审批入群模式
当 `addMode=1` 时：
1. group 校验群存在、用户未在群内、没有重复待审批申请。
2. 写入 `group_join_requests`，状态为待处理。
3. 写 `group.cache` 事件，action 通常为 `join_request_created`。
4. 返回 `applyId` 和 `joinedDirectly=false`。

## 5. 我的申请与管理员审批
### 5.1 用户侧
用户可调用：
| 接口 | 作用 |
| --- | --- |
| `GET /api/v1/auth/groups/:groupUuid/my-join-application` | 看某个群的最新申请状态。 |
| `GET /api/v1/auth/groups/join-applications` | 查看自己发起的申请列表。 |
| `DELETE /api/v1/auth/groups/:groupUuid/apply` | 撤销自己的待审批申请。 |
撤销成功后 group 会写 `join_request_canceled` 事件，缓存中的待审批列表会被异步移除。

### 5.2 管理员侧
管理员或群主可调用：
| 接口 | 作用 |
| --- | --- |
| `GET /api/v1/auth/groups/:groupUuid/join-requests` | 查看待审批申请。 |
| `GET /api/v1/auth/groups/:groupUuid/join-requests/pending-count` | 查看待审批数量。 |
| `GET /api/v1/auth/groups/:groupUuid/join-requests/reviewed` | 查看历史审批记录。 |
| `POST /api/v1/auth/groups/:groupUuid/join-requests/:applyId/review` | 审批。 |
审批动作：
| `action` | 含义 | 结果 |
| --- | --- | --- |
| `1` | 同意 | 新增成员，申请状态改为通过，投影成员缓存。 |
| `2` | 拒绝 | 申请状态改为拒绝，仅更新申请投影。 |
## 6. 成员变更链路
### 6.1 添加成员
入口：`POST /api/v1/auth/groups/:groupUuid/members`

步骤：
1. group 校验操作者权限。
2. 校验待添加用户是否已在群内、人数是否超限。
3. 写入 `group_members`。
4. 写 `member_added` 事件。

### 6.2 主动退群
入口：`POST /api/v1/auth/groups/:groupUuid/leave`

规则：
- 普通成员、管理员可退群；
- 群主不能直接退群，必须先转让群主或解散群。

成功后写 `member_removed` 事件，用户群列表和成员缓存会异步更新。

### 6.3 移除成员
入口：`DELETE /api/v1/auth/groups/:groupUuid/members/:userUuid`

规则：
- 必须校验操作者权限；
- 不能踢群主；
- 管理员不能越权移除不允许操作的目标。

## 7. 群资料与权限字段变更
### 7.1 更新群资料
接口：
| 接口 | 作用 |
| --- | --- |
| `PATCH /api/v1/auth/groups/:groupUuid` | 修改群名称、头像、加群方式。 |
| `PUT /api/v1/auth/groups/:groupUuid/notice` | 修改群公告。 |
| `PATCH /api/v1/auth/groups/:groupUuid/mute-setting` | 修改全员禁言。 |
这些接口成功后都会写 `group.cache` 事件，更新 `group:info:{group_uuid}` 投影。

### 7.2 群主转让与成员角色
接口：
| 接口 | 作用 |
| --- | --- |
| `POST /api/v1/auth/groups/:groupUuid/transfer-owner` | 转让群主。 |
| `PATCH /api/v1/auth/groups/:groupUuid/members/:userUuid/role` | 设置/取消管理员。 |
转让群主后会同时影响：
1. 群资料中的 `ownerUuid`；
2. 群成员角色缓存；
3. 后续审批、禁言、移除成员等权限边界。

### 7.3 群名片与禁言
接口：
| 接口 | 作用 |
| --- | --- |
| `PATCH /api/v1/auth/groups/:groupUuid/my-nickname` | 修改自己的群名片。 |
| `PATCH /api/v1/auth/groups/:groupUuid/members/:userUuid/nickname` | 管理员或群主修改指定成员群名片。 |
| `PATCH /api/v1/auth/groups/:groupUuid/members/:userUuid/mute` | 设置单人禁言。 |
单人禁言的 `muteUntil` 会直接影响群消息发送权限校验。

管理员修改成员群名片时，group 会在事务内同时：
1. 更新 `group_members.remark`；
2. 刷新群资料 `updated_at`；
3. 写入 `member_profile_updated` 事件，驱动成员缓存投影更新。

权限边界：群主可修改管理员和普通成员；管理员只能修改普通成员；修改自己的群名片仍应走 `/my-nickname` 自助入口。

## 8. 解散群链路
入口：`DELETE /api/v1/auth/groups/:groupUuid`

步骤：
1. 校验当前操作者是否为群主。
2. 更新群状态为解散。
3. 清理或失效成员关系视图。
4. 写 `group_dismissed` 事件。

结果：
- 群资料读取应逐步显示为已解散或不可访问；
- 消息发送权限检查会失败；
- 成员缓存和用户群列表缓存会异步移除。

## 9. 对消息发送权限的影响
msg 在发送群消息前会调用 group 权限能力检查：
1. 当前用户是否仍是群成员；
2. 群是否已解散或禁用；
3. 当前用户是否被单人禁言；
4. 群是否开启全员禁言，以及当前角色是否豁免。

当校验失败时，msg 会按拒绝原因映射稳定错误码：
- 非群成员：`14002`；
- 全员禁言：`14017`；
- 单人禁言：`14018`。

因此前端在群资料页看到的按钮状态，只是体验优化，最终权限以 group 服务实时判断为准。

## 10. 前端实现建议
1. 建群、加人、退群、转让群主成功后，立即乐观更新本地群列表和成员列表，同时允许短暂回源重试。
2. 入群申请页应区分“我的申请”和“管理员审批”两个视角，不要混用状态字段。
3. 收到群已解散、非成员、被禁言等错误时，应立即刷新群资料和成员状态。
4. 群名片、管理员、禁言变更后，消息发送入口和群设置入口要同步刷新。
