# 账号注销与异步清理

本文描述账号注销从 HTTP 请求、auth 同步处理，到 `account.deleted` 异步清理下游的完整链路。相关接口见 [认证与账号接口](../api/01-认证与账号接口.md)。

## 1. 参与组件

| 组件 | 职责 |
| --- | --- |
| gateway | HTTP 入站、JWT 鉴权、参数校验。 |
| auth | 校验密码、标记账号状态、清理 Token、生产 `account.deleted`。 |
| user | 清理或标记资料域数据。 |
| relation | 清理好友关系、黑名单和申请关系。 |
| group | 清理群成员、申请或相关投影。 |
| Kafka / Debezium | 承接最终一致清理事件。 |

## 2. 入口与同步返回

接口：`POST /api/v1/auth/user/delete-account`

请求字段：

| 字段 | 说明 |
| --- | --- |
| `password` | 当前账号密码。 |
| `reason` | 注销原因，可为空。 |

响应字段：

| 字段 | 说明 |
| --- | --- |
| `deleteAt` | 注销受理时间。 |
| `recoverDeadline` | 恢复截止时间。 |

注意：接口成功返回并不代表所有下游数据都已经同步清理完成，只代表 auth 侧主事实已经进入“已注销”状态。

## 3. auth 同步处理链路

1. gateway 校验请求体并透传登录上下文。
2. auth 根据 JWT 定位当前 `user_uuid`。
3. auth 校验密码哈希。
4. auth 将 `user_account.status` 更新为已注销状态，并写 `deleted_at`。
5. auth 清理该用户所有设备的 RefreshToken；AccessToken 按自身 `exp` 自然失效。
6. auth 更新相关设备会话状态。
7. auth 在同一事务内写 `outbox_events`：
   - `event_type = account.deleted`
   - `entity_id = user_uuid`
8. HTTP 返回 `deleteAt` 和 `recoverDeadline`。

## 4. 为什么要拆成同步 + 异步

注销涉及的数据域很多：

- auth：账号和设备；
- user：资料和二维码；
- relation：好友、黑名单、申请；
- group：成员关系、申请、缓存；
- message 侧通常还会受关系与资料展示影响。

如果把所有动作都放进一个同步事务：

1. 耦合高；
2. 请求耗时不可控；
3. 任一下游故障都会让注销接口失败；
4. 不符合当前微服务边界。

因此当前策略是：

- auth 同步完成主事实切换；
- 其他服务按 `account.deleted` 事件最终一致清理。

## 5. `account.deleted` 异步链路

```text
delete-account HTTP
  -> auth 更新 user_account + 清理 RefreshToken
  -> auth 事务内写 outbox_events(account.deleted)
  -> Debezium 监听 outbox_events
  -> Kafka topic: account.deleted
  -> user / relation / group 等服务消费
  -> 各自清理本域数据与缓存
```

## 6. 下游清理职责

### 6.1 user

目标：处理 `user_profile` 和二维码相关状态。

可能动作：

- 删除或标记资料；
- 失效二维码 token；
- 清理 `user:profile:*`、`user:qrcode:*` 缓存。

### 6.2 relation

目标：处理好友、黑名单、申请关系。

可能动作：

- 删除或标记 `user_relations`；
- 清理 `apply_requests` 中相关记录；
- 删除好友和黑名单缓存；
- 清理未读申请计数。

### 6.3 group

目标：处理群成员身份和相关申请。

可能动作：

- 从群成员表移除该用户；
- 清理其发起的入群申请；
- 触发 `group.cache` 投影更新群成员缓存和用户群列表缓存。

## 7. 对前端的可见语义

### 7.1 注销成功后立即发生的事

1. 当前登录态应立刻失效。
2. 本地 Token 应立即清理。
3. 当前页面不应继续允许访问需要认证的接口。
4. 若当前设备上仍有 WebSocket，后续重连或心跳会失效。

### 7.2 注销成功后稍后发生的事

1. 资料卡、好友关系、群成员关系等可能在短时间内逐步消失。
2. 其他用户视角下，搜索、资料查看、好友/群关系展示可能存在秒级到更长的最终一致延迟。

## 8. 失败与补偿

| 场景 | 结果 | 处理方式 |
| --- | --- | --- |
| 密码错误 | 注销失败 | 返回业务错误，前端提示重试。 |
| auth 本地事务失败 | 注销失败 | 不会发出 `account.deleted`。 |
| Outbox 未写入 | 注销失败 | 与本地事务一起回滚。 |
| Debezium / Kafka 延迟 | 下游清理滞后 | 监控 lag，等待最终一致完成。 |
| 某下游消费失败 | 局部域清理滞后 | 消费者重试或人工排障。 |

## 9. 排障重点

排查“用户已注销但下游仍可见”时，按顺序检查：

1. auth `user_account.status` 和 `deleted_at` 是否已更新；
2. Redis `auth:rt:*` 是否已清理；
3. `outbox_events` 中是否有 `account.deleted` 事件；
4. Kafka `account.deleted` 是否已生成；
5. user / relation / group 消费组 lag；
6. 目标域自己的缓存是否仍未失效。

## 10. 前端实现建议

1. 注销接口成功后立即清理本地登录态，不要等待后端“完全清理完所有域”。
2. 注销成功后跳转到登录页或欢迎页，避免保留旧业务上下文。
3. 若产品需要展示“可恢复截止时间”，直接使用返回的 `recoverDeadline`。
4. 若随后出现 401、资料不存在、关系不存在等错误，按正常已注销用户状态处理，不视为异常。
