# 消息下行推送与多端同步

本文描述消息从 Kafka `msg.push` 事件，到 message-push 扩散、connect 投递、客户端 ACK 和发送方多端同步的完整链路。架构说明见 [Connect与下行推送架构](../architecture/Connect与下行推送架构.md)。

## 1. 参与组件

| 组件 | 职责 |
| --- | --- |
| msg | 写入 `msg.push` outbox 事件。 |
| Debezium CDC | 将 `outbox_events` 路由到 Kafka `msg.push`。 |
| Kafka | 缓冲下行事件，解耦发送与实时投递。 |
| message-push | 消费事件、查群成员、查在线路由、调用 connect。 |
| Redis | 保存在线路由 `user:routing:{user_uuid}`。 |
| group | 提供群成员能力或缓存投影。 |
| connect | 向本节点在线设备写 WebSocket Binary 帧。 |
| 前端客户端 | 接收 `MSG_PUSH`、`MSG_RECALL`、`MSG_MARK_READ` 等下行帧。 |

## 2. 下行事件来源

msg 生产的核心事件类型：

| type | 来源操作 | payload |
| --- | --- | --- |
| `MSG_PUSH` | 发送消息成功 | `MsgItem` |
| `MSG_RECALL` | 撤回成功 | `RecallNotice` |
| `MSG_MARK_READ` | 标记已读成功 | `MarkReadNotice` |
| `MSG_READ_RECEIPT` | P2P 对端已读 | `MarkReadNotice` |

这些事件都写入 MySQL `outbox_events`，由 Debezium CDC 路由到 Kafka `msg.push` 后，再由 message-push 统一消费。

## 3. P2P 消息与撤回下行流程

1. message-push 从 Kafka 读取 `MsgPushEvent`。
2. 判断 `conv_type=1`，`receiver_uuid` 表示对端用户 UUID。
3. 读取 Redis 在线路由：`user:routing:{receiver_uuid}`。
4. 解析每个设备对应的 `connectGrpcAddr|lastActiveMs`。
5. 同时读取发送方 `from_uuid` 的在线路由，对发送方“其他设备”做多端同步，排除当前 `device_id`。
6. 对 `(user_uuid, device_id)` 去重并按 `connectGrpcAddr` 分组，组装共享的 connect `MessageEnvelope`。
7. 不同 connect 节点在配置上限内并发处理；同一节点内按用户串行处理。
8. 接收方是完整用户目标，在对应节点调用一次 `PushToUser`；发送方存在设备排除，仍逐设备调用 `PushToDevice`。
9. connect 将消息写入对应设备的 WebSocket 连接。

## 4. 群聊下行流程

1. message-push 读取 `MsgPushEvent`，判断 `conv_type=2`。
2. `receiver_uuid` 在群聊场景下表示群 UUID。
3. 调用 group 服务 gRPC 查询群成员列表。
4. 群成员扩散阶段排除发送方用户；随后单独查询发送方路由，并排除当前发送设备后同步其余设备。
5. 为每个目标用户查询在线路由。
6. 对 `(user_uuid, device_id)` 去重，避免重复投递。
7. 按 `connectGrpcAddr` 分组，不同节点在配置上限内并发执行。
8. 同一节点内按用户串行：群成员属于完整用户目标，调用 `PushToUser`；发送方其他设备属于排除目标，逐设备调用 `PushToDevice`。

## 5. 多端同步与设备排除

多端同步的目标是让同一账号的其他设备及时看到本设备完成的消息或已读动作，同时避免当前设备收到重复下行。

规则：

1. `MSG_PUSH` / `MSG_RECALL` 使用 `from_uuid` 查询发送方在线路由，排除当前发送设备 `device_id`。
2. `MSG_MARK_READ` 使用 `receiver_uuid` 查询已读发起用户的在线路由，同样排除当前设备。
3. 上述目标都包含设备级排除，因此必须使用 `PushToDevice` 精确投递。
4. `MSG_READ_RECEIPT` 只通知对端全部在线设备，不做设备排除，可以在各节点使用 `PushToUser`。
5. 当前设备已经完成本地动作，不应被多端同步逻辑重复渲染。

## 6. connect 投递阶段

message-push 不直接管理 WebSocket，而是通过 connect gRPC：

| RPC | 说明 |
| --- | --- |
| `PushToDevice` | 精确投递到用户某个设备；用于发送方其他设备、已读同步等需要排除当前设备的目标。 |
| `PushToUser` | 当前节点内广播到某用户全部设备；用于接收方、群成员、已读回执接收方等完整用户目标。 |

message-push 的调用策略：

1. 先按 `connectGrpcAddr` 分组，每个节点形成一个独立执行单元。
2. 节点级并发由 `MESSAGE_PUSH_MAX_FANOUT_CONCURRENCY` 限制；未配置时默认 32，显式配置必须是正整数，否则 message-push 初始化失败；节点少于上限时按实际节点数并发。
3. 每个节点内部按用户串行调用，避免对同一 gRPC 连接制造无界并发。
4. 完整用户目标必须使用 `PushToUser` 压缩同用户多设备的 RPC 次数；存在设备排除时使用 `PushToDevice`。`EventHandler` 强制要求 sender 同时实现两种 RPC，不做能力探测，也不回退到旧的逐设备路径。
5. 处理预算到期或服务关停时停止调度新节点，已启动节点也会通过同一 `ctx` 停止后续用户或设备调用。

connect 收到后：

1. `PushToDevice` 定位单个连接；`PushToUser` 获取该用户在本节点的全部在线连接。
2. 序列化 `MessageEnvelope` 为 Binary Frame。
3. 入队到目标 client 的写队列；`PushToUser` 返回成功入队的设备数量 `DeliveredCount`。
4. 写成功后记录各连接已下发的最大 `seq`，供后续 ACK 校验。

message-push 按设备数量汇总结果：`PushToUser` 零投递按失败处理，部分投递记录成功数和差额失败数。所有已尝试设备都失败时返回可重试错误；只要部分设备成功，整体仍按成功处理，保持原有重试语义。

## 7. 客户端 ACK

当下行 `MessageEnvelope.ack_required=true` 时：

1. 客户端在消息真正处理完成后发送 `MSG_ACK`；
2. ACK payload 包含 `conv_id` 和已处理的最大连续 `seq`；
3. connect 校验 ACK 不得超过本连接已成功下发的最大位点；
4. connect 将 ACK 位点写入 Redis：
   `msg:ack:{user_uuid}:{device_id}:{conv_id}`；
5. connect 回包 `MSG_ACK_ACK`，告诉客户端服务端已接受该位点。

ACK 只保证“设备级短期处理位点”，不是会话权威已读状态。

## 8. 离线与自愈

### 8.1 用户离线

如果目标用户没有有效在线路由：

- message-push 按正常离线场景处理，不报业务失败；
- 实时投递直接跳过；
- 客户端后续通过 HTTP `PullMessages` 自愈。

如果 Redis 路由存在但 connect 已找不到对应连接，则属于脏路由投递失败：只有全部已尝试设备都失败时才进入本地短重试。

### 8.2 路由脏数据

如果 Redis 里仍有过期路由：

- message-push 可能短暂尝试投递；
- connect 不可达或目标连接不存在时会失败；
- 路由 TTL 或断连清理后会恢复正常。

### 8.3 Kafka 或 connect 临时失败

| 场景 | 策略 |
| --- | --- |
| Kafka payload 非法 | 永久跳过。 |
| Redis 路由临时失败 | 可重试。 |
| connect gRPC 临时失败 | 本地最多 3 次短重试。 |
| 最终仍失败 | 让客户端通过补拉恢复。 |

## 9. 前端接收动作建议

| 下行类型 | 前端动作 |
| --- | --- |
| `MSG_PUSH` | 插入消息、推进会话 `lastMsg`、处理 seq gap。 |
| `MSG_RECALL` | 将目标消息替换为撤回展示。 |
| `MSG_MARK_READ` | 更新同账号其他设备的未读红点。 |
| `MSG_READ_RECEIPT` | 更新发送消息的已读状态。 |
| `MSG_ACK_ACK` | 清理本地 ACK 待确认队列。 |

## 10. 前端实现建议

1. 不要依赖“实时下行必达”，任何关键消息列表都必须支持 HTTP 补拉。
2. `MSG_PUSH` 处理时优先按 `convId + seq` 去重，不要只按 `msgId` 去重。
3. 多端同步场景下，当前发送设备本地已经有消息，不应被其他设备同步逻辑重复插入。
4. 如果 ACK 上报失败，可以暂存本地 ACK 队列，待连接恢复后重试。
