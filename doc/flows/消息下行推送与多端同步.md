# 消息下行推送与多端同步

本文描述消息从 Kafka `msg.push` 事件，到 message-push 扩散、connect 投递、客户端 ACK 和发送方多端同步的完整链路。架构说明见 [Connect与下行推送架构](../architecture/Connect与下行推送架构.md)。

## 1. 参与组件

| 组件 | 职责 |
| --- | --- |
| msg | 生产 `msg.push` 事件。 |
| Kafka | 缓冲下行事件，解耦发送与实时投递。 |
| message-push | 消费事件、查群成员、查在线路由、调用 connect。 |
| Redis | 保存在线路由 `user:routing:{user_uuid}`。 |
| group | 提供群成员能力或缓存投影。 |
| connect | 向本节点在线设备写 WebSocket Binary 帧。 |
| 前端客户端 | 接收 `MSG_PUSH`、`MSG_RECALL`、`MSG_MARK_READ` 等下行帧。 |

## 2. 下行事件来源

msg 生产的核心事件类型：

| type | 来源操作 | payload |
| --- | --- | --- |
| `MSG_PUSH` | 发送消息成功 | `MsgItem` |
| `MSG_RECALL` | 撤回成功 | `RecallNotice` |
| `MSG_MARK_READ` | 标记已读成功 | `MarkReadNotice` |
| `MSG_READ_RECEIPT` | P2P 对端已读 | 业务约定 payload |

这些事件都写入 Kafka `msg.push`，由 message-push 统一消费。

## 3. P2P 下行流程

1. message-push 从 Kafka 读取 `MsgPushEvent`。
2. 判断 `conv_type=1`，`receiver_uuid` 表示对端用户 UUID。
3. 读取 Redis 在线路由：`user:routing:{receiver_uuid}`。
4. 解析每个设备对应的 `connectGrpcAddr|lastActiveMs`。
5. 组装 connect `MessageEnvelope`。
6. 调用目标 connect 节点 `PushToDevice`，将消息写入对应设备连接。
7. 同时读取发送方 `from_uuid` 的在线路由，对发送方“其他设备”做多端同步，排除当前 `device_id`。

## 4. 群聊下行流程

1. message-push 读取 `MsgPushEvent`，判断 `conv_type=2`。
2. `receiver_uuid` 在群聊场景下表示群 UUID。
3. 查询群成员列表，来源可能是：
   - group 服务 gRPC；
   - `group:members:{group_uuid}` 缓存投影。
4. 排除当前发送设备本人；根据事件类型决定是否向发送方其他设备同步。
5. 为每个目标用户查询在线路由。
6. 对 `(user_uuid, device_id)` 去重，避免重复投递。
7. 逐个设备调用对应 connect 节点 `PushToDevice`。

## 5. 发送方多端同步

多端同步的目标是：用户在 A 设备发消息后，B、C 设备也能实时看到自己刚发送的消息。

规则：

1. 使用 `from_uuid` 查发送方在线路由；
2. 排除当前发送设备 `device_id`；
3. 向其余在线设备投递同一条 `MSG_PUSH` / `MSG_RECALL` / `MSG_MARK_READ` 等事件；
4. 不应造成当前设备本地重复渲染。

## 6. connect 投递阶段

message-push 不直接管理 WebSocket，而是通过 connect gRPC：

| RPC | 说明 |
| --- | --- |
| `PushToDevice` | 精确投递到用户某个设备。 |
| `PushToUser` | 当前节点内广播到某用户全部设备。 |

connect 收到后：

1. 查本节点内存连接管理器是否存在目标设备；
2. 序列化 `MessageEnvelope` 为 Binary Frame；
3. 入队到对应 client 的写队列；
4. 写成功后记录该连接已下发的最大 `seq`，供后续 ACK 校验。

## 7. 客户端 ACK

当下行 `MessageEnvelope.ack_required=true` 时：

1. 客户端在消息真正处理完成后发送 `MSG_ACK`；
2. ACK payload 包含 `conv_id` 和已处理的最大连续 `seq`；
3. connect 校验 ACK 不得超过本连接已成功下发的最大位点；
4. connect 将 ACK 位点写入 Redis：
   `msg:ack:{user_uuid}:{device_id}:{conv_id}`；
5. connect 回包 `MSG_ACK_ACK`，告诉客户端服务端已接受该位点。

ACK 只保证“设备级短期处理位点”，不是会话权威已读状态。

## 8. 离线与自愈

### 8.1 用户离线

如果目标设备没有在线路由或 connect 未找到连接：

- message-push 不会报业务失败；
- 实时投递直接跳过；
- 客户端后续通过 HTTP `PullMessages` 自愈。

### 8.2 路由脏数据

如果 Redis 里仍有过期路由：

- message-push 可能短暂尝试投递；
- connect 不可达或目标连接不存在时会失败；
- 路由 TTL 或断连清理后会恢复正常。

### 8.3 Kafka 或 connect 临时失败

| 场景 | 策略 |
| --- | --- |
| Kafka payload 非法 | 永久跳过。 |
| Redis 路由临时失败 | 可重试。 |
| connect gRPC 临时失败 | 本地最多 3 次短重试。 |
| 最终仍失败 | 让客户端通过补拉恢复。 |

## 9. 前端接收动作建议

| 下行类型 | 前端动作 |
| --- | --- |
| `MSG_PUSH` | 插入消息、推进会话 `lastMsg`、处理 seq gap。 |
| `MSG_RECALL` | 将目标消息替换为撤回展示。 |
| `MSG_MARK_READ` | 更新同账号其他设备的未读红点。 |
| `MSG_READ_RECEIPT` | 更新发送消息的已读状态。 |
| `MSG_ACK_ACK` | 清理本地 ACK 待确认队列。 |

## 10. 前端实现建议

1. 不要依赖“实时下行必达”，任何关键消息列表都必须支持 HTTP 补拉。
2. `MSG_PUSH` 处理时优先按 `convId + seq` 去重，不要只按 `msgId` 去重。
3. 多端同步场景下，当前发送设备本地已经有消息，不应被其他设备同步逻辑重复插入。
4. 如果 ACK 上报失败，可以暂存本地 ACK 队列，待连接恢复后重试。
