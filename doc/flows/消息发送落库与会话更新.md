# 消息发送落库与会话更新

本文描述消息从 HTTP 发送入口，到 msg 服务落库、分配 seq、更新会话和异步投递 `msg.push` 事件的主链路。接口定义见 [消息与会话接口](../api/05-消息与会话接口.md)。

## 1. 参与组件

| 组件 | 职责 |
| --- | --- |
| gateway | HTTP 入站、DTO 校验、JWT 与 `X-Device-ID` 注入。 |
| msg | 权限校验、幂等、消息落库、会话更新、事件生产。 |
| relation | 单聊发送前关系权限检查。 |
| group | 群聊成员与禁言权限检查。 |
| Redis | 会话 seq 分配、发送幂等缓存。 |
| Kafka | 承载 `msg.push` 下行事件。 |

## 2. 发送入口

接口：`POST /api/v1/auth/messages/send`

关键请求字段：

| 字段 | 说明 |
| --- | --- |
| `clientMsgId` | 客户端幂等 ID。 |
| `convType` | 1 单聊，2 群聊。 |
| `targetUuid` | 单聊为对端 UUID，群聊为群 UUID。 |
| `msgType` | 消息类型。 |
| `content` | JSON 字符串内容。 |
| `replyToMsgId` | 回复目标消息 ID。 |
| `atUsers` | 被 @ 用户列表。 |

gateway 不要求前端传 `fromUuid` 和 `deviceId`，而是从 JWT 与 `X-Device-ID` 中注入给 msg。

## 3. 权限校验阶段

### 3.1 单聊

单聊发送前，msg 会检查：

1. 是否存在好友关系；
2. 是否被对方拉黑；
3. 当前用户是否已拉黑对方；
4. 目标账号是否仍可用。

### 3.2 群聊

群聊发送前，msg 会检查：

1. 当前用户是否仍在群内；
2. 群是否已解散或不可发送；
3. 是否被单人禁言；
4. 群是否开启全员禁言，以及当前用户是否有豁免角色。

权限校验失败时，消息不会进入落库阶段。

## 4. 幂等与 seq 分配

### 4.1 幂等三元组

msg 使用以下三元组防止弱网重试重复落库：

```text
from_uuid + device_id + client_msg_id
```

对应 Redis Key：

```text
msg:idempotent:{from_uuid}:{device_id}:{client_msg_id}
```

TTL 为 10 分钟。

### 4.2 会话 seq

消息通过 Redis `INCR` 生成会话内严格递增 `seq`：

```text
msg:seq:{conv_id}
```

设计要点：

- `seq` 仅在单个会话内有意义；
- 同一会话内可用于排序、补拉缺口和 ACK；
- 不能跨会话比较两个 `seq` 的大小。

## 5. 消息落库阶段

落库内容通常包含：

| 字段 | 说明 |
| --- | --- |
| `msg_id` | 服务端生成的全局消息 ID。 |
| `client_msg_id` | 客户端幂等 ID。 |
| `conv_id` | 会话 ID。 |
| `seq` | 会话内序号。 |
| `from_uuid` | 发送者 UUID。 |
| `msg_type` | 消息类型。 |
| `content` | JSON 字符串内容。 |
| `reply_to_msg_id` | 回复消息 ID。 |
| `at_users` | 被 @ 用户列表。 |
| `send_time` | 服务端发送时间。 |

消息一旦成功落库，就视为“发送成功”。后面的会话更新或实时投递都不影响这个主判定。

## 6. 会话更新阶段

### 6.1 发送方会话

conversation domain 会更新发送方视角会话：

- `last_msg_id`；
- `last_msg_preview`；
- `last_msg_at`；
- `max_seq`；
- `updated_at`。

### 6.2 单聊接收方会话

单聊时，还会尝试更新对端用户的会话：

- 更新最后消息；
- 推进 `max_seq`；
- 增加未读数；
- 更新排序时间。

### 6.3 群聊会话

群聊时，msg 会：

1. 更新群会话热数据；
2. 尝试为群成员初始化或刷新各自会话行；
3. 允许部分会话更新失败后由后续消息覆盖自愈。

## 7. Kafka `msg.push` 生产阶段

消息落库成功后，msg usecase 会异步构造 `MsgPushEvent` 并写入 Kafka：

| 字段 | 说明 |
| --- | --- |
| `receiver_uuid` | 单聊为对端 UUID，群聊为群 UUID。 |
| `device_id` | 当前发送设备 ID，用于多端同步排除本设备。 |
| `type` | `MSG_PUSH`。 |
| `conv_type` | 1 单聊，2 群聊。 |
| `data` | `MsgItem` Protobuf bytes。 |
| `from_uuid` | 发送方 UUID。 |
| `seq` | 当前消息 seq。 |

Kafka key 使用 `conv_id`，保证同一会话尽量在同一分区有序消费。

## 8. 非阻断策略

以下阶段失败时，不回滚已落库消息：

| 步骤 | 失败处理 |
| --- | --- |
| 发送方会话更新 | Warn。 |
| 接收方会话更新 | Warn。 |
| 群成员会话初始化 | Warn。 |
| Kafka `msg.push` 投递 | Warn。 |

原因：

1. 消息主事实已经成立；
2. 客户端后续可以通过 `PullMessages` 拉取权威消息；
3. 会话预览、未读数可以在下一条消息或增量同步时覆盖修正。

## 9. 返回前端的成功语义

发送接口成功返回时，前端可立即：

1. 将本地临时消息与服务端 `msgId`、`seq`、`convId` 合并；
2. 更新会话最后消息预览；
3. 等待 WebSocket 的自己其他设备同步和接收方投递。

返回成功并不代表：

- 接收方已经在线收到；
- message-push 已成功投递；
- 所有会话缓存已经完全更新。

## 10. 常见异常与自愈

| 场景 | 结果 | 自愈方式 |
| --- | --- | --- |
| 网络重试重复提交 | 命中幂等 | 复用首次消息结果。 |
| Kafka 投递失败 | 实时下行缺失 | 客户端后续 PullMessages。 |
| 会话更新失败 | 会话列表短暂不准 | 下次消息或会话同步覆盖。 |
| 群权限变化 | 直接发送失败 | 刷新群资料和成员状态。 |

## 11. 前端实现建议

1. `clientMsgId` 必须在重试时复用，不要重新生成。
2. `content` 统一作为 JSON 字符串提交，便于多端一致解析。
3. 发送成功后若迟迟未收到 WebSocket 自己其他端同步，不应重复插入消息，只需等待补拉或会话同步。
4. 群聊发送失败后，应优先刷新群资料、成员身份和禁言状态。
