 # 群组写链路与缓存投影实施方案
 > 文档状态：可执行开发计划
 > 适用范围：`apps/group` 写链路 MVP + Redis 缓存投影 + `msg` 高频群权限链路优化
 > 对齐基线：当前仓库已存在的 `pkg/outbox`、`pkg/kafka`、`pkg/redisretry`、`pkg/grpcx`、`relation/user/auth` 服务实现风格
 ---
 ## 一、目标与本轮范围
 本轮目标不是单纯补齐 group-service 的写接口，而是一次性完成以下三件事：
 1. 落地 `group-service` 的最小写闭环；
 2. 建立 `MySQL -> Outbox -> CDC -> Kafka -> Redis` 的群缓存投影链路；
 3. 优化 `msg-service` 当前高频群权限校验路径，避免发送群消息或查询群角色时拉取全量成员列表。
 ### 1.1 本轮必须交付
 - `CreateGroup`
 - `AddMember`
 - `RemoveMember`
 - `DismissGroup`
 - `UpdateGroupInfo`
 - `CheckGroupMember`（新增内部轻量 RPC，用于 `msg` 高频权限校验与角色查询）
 - 群缓存投影：
   - 群资料缓存
   - 群成员 ID 缓存
   - 群成员角色缓存
   - 用户所在群列表缓存
 - `msg` 高频链路改造：
   - `PermissionChecker.checkGroup` 改为走 `CheckGroupMember`
   - `groupcli.QueryMemberRole` 改为走 `CheckGroupMember`
### 1.2 本轮明确不做
- 不新增群审批流完整闭环；
- 不新增群禁言、群名片、群内昵称等扩展能力；
- 不新增更细粒度的资料编辑权限矩阵；
- 不引入新的通用 DLQ/重试框架；
- 不修改 `message-push` 的群扩散接口，仍使用 `GetGroupMemberIds`。
 ---
 ## 二、已确认的现有仓库约束
 本方案必须严格对齐以下现状，不能另起炉灶：
 ### 2.1 分层与职责边界
 当前仓库服务风格统一为：
 ```text
 handler（薄适配层）
   -> service / usecase（业务编排、错误码映射）
     -> repository（DB/Redis/事务/缓存）
 ```
 约束：
 - `handler` 不放业务规则；
 - `service` 负责参数校验、权限校验、错误码映射；
 - `repository` 负责事务、MySQL、Redis、缓存 patch / rebuild；
 - gRPC 错误统一走 `apperr` + `grpcx` 拦截器链。
 ### 2.2 Outbox / CDC 已经存在统一实现
 已有能力：
 - `pkg/outbox.InsertEvent(tx, eventType, entityID, payload)`
 - `outbox_events` 表
 - `idempotent_events` 表
 - `scripts/cdc/register_outbox_connector.sh`
 - Debezium `EventRouter`：
   - Kafka topic = `event_type`
   - Kafka key = `entity_id`
   - Kafka value = `payload`
 因此：
 - **不能新建 `group_event_outbox` 表**；
 - group 事件必须复用 `outbox_events`；
 - 事件 topic 的路由方式必须兼容当前 Debezium 配置。
 ### 2.3 Kafka 消费的统一可靠模式
 `auth/user/relation` 的跨服务事件消费统一采用：
 - `kafka.NewManualCommitConsumer(...)`
 - `outbox.CheckIdempotent(...)`
 - `outbox.MarkIdempotent(...)`
 这意味着 group 缓存投影消费者也应采用同样模式，而不是复用 `message-push` 那套“失败也提交 offset”的实时投递策略。
 ### 2.4 Redis 缓存风格
 参考 `relation-service` 现有实现，本仓库 Redis 读写风格是：
 1. **读路径优先查缓存，miss 回源 MySQL；**
 2. **回源后异步全量重建缓存；**
 3. **写路径只在 key 已存在时做增量补丁（patch-if-exists）；**
 4. 空值缓存使用 `{}` 或 `__EMPTY__`；
 5. TTL 使用随机抖动；
 6. Redis `WRONGTYPE` 视为脏 key，直接删除，等待后续重建；
 7. Redis 失败默认 `Warn` 降级；必要时可投递 `redisretry` 补偿任务。
 ### 2.5 gRPC 元数据与内部调用约束
 当前 `grpcx` 已统一支持：
 - metadata 透传：`trace_id / user_uuid / device_id / client_ip`
 - internal caller：`x-internal-caller`
 - service 级 retry
 - 方法级 timeout
 所以 group 新增内部轻量 RPC 后，应直接复用现有 `grpcx.NewClient(...)`、`InternalCallerInterceptor(...)` 和 `DefaultClientMethodTimeouts()`。

 ## 三、核心设计决策
 ### 3.1 群缓存事件统一使用单一 topic：`group.cache`
 当前 Debezium 会把 `event_type` 直接映射为 Kafka topic。
 如果为 `CreateGroup / AddMember / RemoveMember / DismissGroup / UpdateGroupInfo` 分别使用不同 `event_type`，则同一个群的事件会进入不同 topic，无法天然保证顺序。
 因此本轮统一约定：
 - **所有群缓存投影事件都写入一个统一 topic：`group.cache`**；
 - 事件具体动作通过 payload 里的 `action` 字段区分；
 - `entity_id = group_uuid`，确保同一群事件在 Kafka 中按 key 聚合。
 这样可以在不改 Debezium connector 的前提下，最大限度保持同群事件顺序。
 ### 3.2 新增轻量 RPC：`CheckGroupMember`
 当前 `msg` 高频链路存在两个明显问题：
 1. 发送群消息时，`PermissionChecker.checkGroup` 调 `GetGroupMemberIds` 拉全量成员；
 2. 撤回/角色判断时，`groupcli.QueryMemberRole` 调 `GetMemberList` 拉全量成员。
 这两条链路都不适合高频调用。
 因此本轮新增：
 ```proto
 rpc CheckGroupMember(CheckGroupMemberRequest) returns (CheckGroupMemberResponse);
 message CheckGroupMemberRequest {
   string group_uuid = 1;
   string user_uuid = 2;
 }
 message CheckGroupMemberResponse {
   bool is_member = 1;
   int32 role = 2;
 }
 ```
 语义约定：
 - 群不存在：返回 `CodeGroupNotFound`
 - 群已解散：返回 `CodeGroupAlreadyDismiss`
 - 群存在且用户不在群内：返回成功响应，`is_member=false, role=-1`
 - 群存在且用户在群内：返回 `is_member=true, role=0/1/2`
 这样：
 - `msg` 发群消息权限判断可降为 O(1)；
 - `msg` 群角色查询也可降为 O(1)；
 - `message-push` 仍然保留 `GetGroupMemberIds` 做群扩散。
 ### 3.3 本轮缓存一致性策略
 本轮统一采用：
 ```text
 MySQL 为权威事实源
 Outbox + CDC + Kafka 负责传播写事实
 Group Cache Projector 负责投影 Redis
 读路径 miss 时再做 MySQL 回源 + 异步重建
 ```
 与现有仓库风格对齐后的具体原则：
 1. group 主缓存（群资料、成员集合、成员角色）允许在 `group.created` 事件中直接初始化；
 2. 反向索引缓存（用户所在群列表）遵循 `patch-if-exists`；
 3. 群缓存投影消费者失败时返回 error，不提交 offset；
 4. 幂等由 `idempotent_events` 保证；
 5. 读路径回填缓存失败只 `Warn`，不阻塞请求；
 6. 不新增新一套 retry topic / DLQ 基础设施，本轮沿用现有手动提交重试模式。
 ---
 ## 四、业务规则
 ### 4.1 角色与状态
 沿用当前模型：
 - 成员角色：
   - `0` 普通成员
   - `1` 管理员
   - `2` 群主
 - 群状态：
   - `0` 正常
   - `1` 禁用
   - `2` 解散
 - 成员状态：
   - `0` 正常
   - `1` 退出
   - `2` 踢出
   - `3` 待审核
 ### 4.2 写链路规则
 #### CreateGroup
 - 当前登录用户必须存在；
 - `name` 去首尾空格后不能为空；
 - 群主自动入群；
 - `member_uuids` 去空、去重、自动排除群主重复项；
 - `groups` 与群主/初始成员记录必须在同一事务内提交；
 - `member_cnt` 直接写有效成员数量。
 #### AddMember
 - 只有群主和管理员可加人；
 - 群已解散时拒绝；
 - 已经是有效成员时幂等成功；
 - 退出/踢出成员可恢复为正常成员；
 - 恢复或新增后 `member_cnt` 累加；
 - 新成员默认角色为普通成员。
 #### RemoveMember
 - 普通成员只能移除自己（退群）；
 - 管理员只能移除普通成员；
 - 群主可移除管理员与普通成员；
 - 不能移除群主；
 - 群主不能以“退群”方式离开；
 - 已经不是有效成员时幂等成功；
 - 成功后 `member_cnt` 递减。
 #### DismissGroup
 - 只有群主可解散；
 - 已解散重复调用按幂等成功处理；
 - 解散后所有写接口与 `CheckGroupMember` 都应返回 `CodeGroupAlreadyDismiss`；
 - 本轮不批量更新所有成员状态，避免大群长事务。
#### UpdateGroupInfo
- 群主、管理员可更新；
- 群已解散时拒绝；
- 只更新请求中显式传入的字段；
- 没有实际变更则直接成功；
- 当前支持 `name / avatar / notice / add_mode`。

 ## 五、Redis 缓存设计
 ## 5.1 key 规划
 所有 key 放入 `consts/redisKey/keys.go`。
 | Key | 类型 | 说明 |
 |---|---|---|
 | `group:info:{group_uuid}` | String(JSON) | 群资料缓存 |
 | `group:members:{group_uuid}` | Set | 群成员 UUID 集合 |
 | `group:member_roles:{group_uuid}` | Hash | `user_uuid -> role` |
 | `group:user_groups:{user_uuid}` | ZSet | 用户所在群 UUID 列表 |
 ### 5.2 TTL 规划
 建议新增常量：
 - `GroupInfoTTL = 1h`
 - `GroupInfoEmptyTTL = 5m`
 - `GroupMembersTTL = 24h`
 - `GroupMembersEmptyTTL = 5m`
 - `GroupMemberRolesTTL = 24h`
 - `GroupMemberRolesEmptyTTL = 5m`
 - `UserGroupListTTL = 24h`
 - `UserGroupListEmptyTTL = 5m`
 非空缓存统一走 `getRandomExpireTime(baseTTL)` 做抖动。
 ### 5.3 读路径策略
 #### GetGroupInfo
 - 优先读 `group:info:{group_uuid}`；
 - 命中 `{}` 视为不存在；
 - miss 时查 MySQL；
 - 查询成功后异步回填。
 #### GetGroupMemberIds
 - 优先读 `group:members:{group_uuid}`；
 - key 存在时，过滤 `__EMPTY__` 后直接返回；
 - key 缺失时查 MySQL 全量成员；
 - 异步重建 `group:members` 与 `group:member_roles`。
 #### CheckGroupMember
 高频路径优先级最高：
 1. 先确认群状态（优先 `group:info`）；
 2. 再查 `group:member_roles:{group_uuid}` 的 `HGET user_uuid`；
 3. 若角色缓存 miss，但成员集合存在，可用 `SISMEMBER` 判断是否在群内；
 4. 若仍无法确认，再回源 MySQL 点查 `(group_uuid, user_uuid)`；
 5. 回源后异步 patch 或重建对应缓存。
 #### GetGroupList
 - 优先读 `group:user_groups:{user_uuid}`；
 - 批量取出群 UUID 后，再批量读取 `group:info:*`；
 - info 缺失时回源 MySQL 并异步补齐；
 - `user_groups` 整体 miss 时回源 MySQL join，再异步重建 ZSet。
 ### 5.4 写路径缓存策略
 与 relation 的现有风格对齐：
 - **主缓存**：允许在 `group.created` 时完整创建；
 - **反向索引**：只在 key 已存在时 patch；
 - **key 不存在**：不强行“半重建”，交由下一次读路径全量重建。
 ### 5.5 Redis 错误处理
 - 读路径 Redis 失败：`Warn`，回源 MySQL；
 - 读路径异步回填失败：`Warn`，不阻塞响应；
 - 缓存投影消费者写 Redis 失败：返回 error，不提交 Kafka offset；
 - `WRONGTYPE`：删除 key，等待下次读路径重建；
 - 本轮不要求为 group 单独接入 `RedisRetryConsumer`，先以 Kafka 手动提交重试为主。
 ---
 ## 六、事件协议设计
 ## 6.1 单一 topic
 所有群缓存投影事件统一写到：
 ```text
 group.cache
 ```
 对应 `event_type = "group.cache"`。
 `entity_id = group_uuid`，作为 Kafka key。
 ## 6.2 payload 结构
 新增 `pkg/groupevent/events.go`，风格对齐 `pkg/accountevent/events.go`。
```go
const EventTypeGroupCache = "group.cache"
const (
    ActionGroupCreated       = "group_created"
    ActionMemberAdded        = "member_added"
    ActionMemberRemoved      = "member_removed"
    ActionGroupDismissed     = "group_dismissed"
    ActionGroupInfoUpdated   = "group_info_updated"
    ActionOwnerTransferred   = "owner_transferred"
    ActionMemberRoleUpdated  = "member_role_updated"
)
```
统一 payload：
```go
type GroupCacheEventPayload struct {
     EventID      string                 `json:"event_id"`
     Action       string                 `json:"action"`
     GroupUUID    string                 `json:"group_uuid"`
     OperatorUUID string                 `json:"operator_uuid,omitempty"`
     Group        *GroupSnapshot         `json:"group,omitempty"`
    Members      []GroupMemberSnapshot  `json:"members,omitempty"`
    UserUUID     string                 `json:"user_uuid,omitempty"`
    UserUUIDs    []string               `json:"user_uuids,omitempty"`
    JoinedAtUnixMs int64                `json:"joined_at_unix_ms,omitempty"`
}
```
说明：
- `EventID` 用于幂等；
- `Action` 决定 projector 如何更新缓存；
- `Group` 用于 `group_created / group_info_updated / owner_transferred` 等需要携带群最终态快照的场景；
- `Members` 用于 `group_created`；
- `UserUUIDs` 用于 `member_added`；
- `UserUUID` 用于 `member_removed / member_role_updated`；
- `JoinedAtUnixMs` 用于 projector 在 patch 单成员缓存时保留稳定排序信息。

 ## 七、Group Cache Projector 设计
 ### 7.1 消费模式
 新增：
 ```text
 apps/group/internal/consumer/cache_projector.go
 ```
 采用：
 - `kafka.NewManualCommitConsumer(...)`
 - `outbox.CheckIdempotent(...)`
 - `outbox.MarkIdempotent(...)`
 projector 流程：
 ```text
 consume group.cache
   -> decode payload
   -> CheckIdempotent(group-cache-projector, event_id)
   -> apply cache patch / build
   -> MarkIdempotent(...)
   -> return nil (commit)
 ```
 ### 7.2 重试策略
 本轮严格对齐现有仓库，不额外新建 retry topic / DLQ 基础设施。
 采用当前仓库已有且可落地的可靠策略：
 - projector 使用 `ManualCommitConsumer`；
 - handler 返回 error 时不提交 offset；
 - `errorBackoff` 控制消费重试节奏；
 - 幂等表保证重试安全。
 这意味着本轮的“Kafka 重试”语义是：
 ```text
 消费失败 -> 不提交 offset -> 下次继续消费 -> 幂等保护
 ```
 而不是引入一套新的 retry topic / DLQ 体系。
 ### 7.3 各 action 的缓存投影规则
 #### group_created
 - 直接写入 `group:info:{group_uuid}`
 - 直接构建 `group:members:{group_uuid}`
 - 直接构建 `group:member_roles:{group_uuid}`
 - 对 `group:user_groups:{user_uuid}` 做 `patch-if-exists`
 #### member_added
 - `group:members` key 存在时 `SADD`
 - `group:member_roles` key 存在时 `HSET role=0`
 - `group:info` key 存在时更新 `member_count`
 - `group:user_groups:{user_uuid}` key 存在时 `ZADD`
 #### member_removed
 - `group:members` key 存在时 `SREM`
 - `group:member_roles` key 存在时 `HDEL`
 - `group:info` key 存在时更新 `member_count`
 - `group:user_groups:{user_uuid}` key 存在时 `ZREM`
 #### group_dismissed
 - 若 `group:info` 存在，更新 `status=2`
 - 删除 `group:members`
 - 删除 `group:member_roles`
 - `group:user_groups` 只做 `patch-if-exists`
#### group_info_updated
- 若 `group:info` 存在，更新 `name / avatar / notice / add_mode`
- 不主动重建 `group:user_groups`
#### owner_transferred
- 若 `group:info` 存在，更新 `owner_uuid`
- 若 `group:members` / `group:member_roles` 存在，同步把原群主降级为成员、目标成员升级为群主
- 不强制重建用户群列表，因为群归属未变化
#### member_role_updated
- 若 `group:member_roles` 存在，按事件把目标成员角色更新为普通成员或管理员
- 若 `group:members` 存在，按需 patch 单成员快照，保持角色读取与成员列表排序一致
- `group:info` 只刷新 `updated_at`，不改 `member_count`
 ---
 ## 八、`msg` 高频权限链路优化方案
 ### 8.1 发送群消息权限校验
 当前：
 - `apps/msg/internal/usercli/permission_checker.go`
 - 通过 `GetGroupMemberIds` 拉全量成员，再遍历判断是否在群内。
 本轮改为：
 - 调 `GroupService.CheckGroupMember`
 - 只判断：
   - 群是否存在
   - 群是否已解散
   - 当前用户是否在群内
 新行为：
 - `CodeGroupNotFound`：群不存在
 - `CodeGroupAlreadyDismiss`：群已解散
 - `CodeNotGroupMember`：群存在但用户不在群内
 ### 8.2 群角色查询
 当前：
 - `apps/msg/internal/groupcli/client.go`
 - `QueryMemberRole` 通过 `GetMemberList` 拉全量成员，再找到目标角色。
 本轮改为：
 - `QueryMemberRole` 直接调用 `CheckGroupMember`
 - `is_member=false` 时返回 `-1, nil`
 - `is_member=true` 时返回 `role`
 ### 8.3 `message-push` 保持不变
 `message-push` 仍然用：
 - `GetGroupMemberIds`
 原因：
 - 群扩散本身需要全量成员；
 - 高频瓶颈在 `msg` 权限判断，不在 `message-push` 的 fanout 读取。

 ## 九、数据库与事务实现方案
 ### 9.1 repository 新增能力
 在 `apps/group/internal/repository/interface.go` 新增最小写接口：
 - `RunInTx(...)`
 - `GetGroupInfoForUpdate(...)`
 - `GetGroupMemberForUpdate(...)`
 - `ListGroupMembersByUserUUIDsForUpdate(...)`
 - `CreateGroup(...)`
 - `BatchCreateGroupMembers(...)`
 - `UpdateGroupFields(...)`
 - `UpdateGroupStatus(...)`
 - `UpdateGroupMemberStatus(...)`
 - `AdjustGroupMemberCount(...)`
 - `InsertCacheEvent(...)`（内部可直接调用 `outbox.InsertEvent`）
 - `CheckGroupMember(...)`
 说明：
 - 事务由 repository 封装；
 - 业务规则仍放 service，不放 repository；
 - repository 内部持有 `db + redisClient`，读缓存与写 MySQL 都在同一实现中完成。
 ### 9.2 事务边界
 #### CreateGroup
 同一事务内：
 1. 插入 `groups`
 2. 批量插入 `group_members`
 3. 写 `outbox_events(event_type=group.cache, entity_id=group_uuid, payload=...)`
 #### AddMember
 同一事务内：
 1. 锁群行
 2. 锁操作者成员行
 3. 查目标成员行
 4. 恢复或插入成员
 5. 更新 `member_cnt`
 6. 写 `outbox_events`
 #### RemoveMember
 同一事务内：
 1. 锁群行
 2. 锁操作者成员行
 3. 锁目标成员行
 4. 更新目标成员状态
 5. 更新 `member_cnt`
 6. 写 `outbox_events`
 #### DismissGroup
 同一事务内：
 1. 锁群行
 2. 校验群主
 3. 更新 `groups.status=2`
 4. 写 `outbox_events`
 #### UpdateGroupInfo
 同一事务内：
 1. 锁群行
 2. 锁操作者成员行
 3. 更新字段
 4. 写 `outbox_events`

 ## 十五、执行建议
 建议按以下顺序落地，降低返工概率：
 1. **先改 proto + `msg` 高频权限链路**，先把收益最高的热路径收敛；
 2. 再补 repository 写能力和 5 个写接口；
 3. 写链路稳定后再接 `group.cache` projector；
 4. 最后做 Redis 读缓存与 compose/env 对接。
 这样做的好处是：
 - 每一步都能独立验证；
 - 出问题时容易定位；
 - 不会把“proto 变化 / 业务写逻辑 / 缓存投影 / 部署依赖”一次性混在一起。
