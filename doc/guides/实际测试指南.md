# LCChat 实际测试指南

> 适用场景：功能开发完成后，在真实进程、真实 MySQL/Redis/Kafka/MinIO 依赖下验证 HTTP、gRPC、WebSocket 和消息下行链路。
> 单元测试只能证明局部逻辑正确；实际测试要证明“服务能启动、路由能打通、数据能落库、异步链路能自愈”。

## 1. 测试分层

建议按成本从低到高逐层推进：

| 层级 | 目的 | 常用命令/方式 |
|---|---|---|
| 编译检查 | 发现接口、依赖注入、生成代码不一致 | `go build ./...` |
| 单元测试 | 验证纯业务逻辑、错误映射、DTO 转换 | `go test ./pkg/...`、`go test ./apps/user/internal/service` |
| 路由/服务测试 | 验证 Gin handler、middleware、gateway service mock | `go test ./apps/gateway/internal/router ./apps/gateway/internal/service` |
| 集成测试 | 验证真实 MySQL/Redis/Kafka/MinIO 与服务启动 | `docker compose up -d --build` |
| 端到端实际测试 | 从 Gateway 发真实 HTTP 请求，必要时连 WebSocket | PowerShell/curl/Postman/wscat |

选择原则：
- 只改纯函数或错误码：跑目标包单元测试即可。
- 改 handler、middleware、DTO、路由：补跑 gateway router/service 测试，并打一次实际 HTTP。
- 改 Redis、DB、Kafka、Wire、服务启动、消息链路：必须跑 Docker Compose 集成测试。
- 改 Connect、message-push、消息投递：必须让接收方 WebSocket 在线，并验证 Redis 路由表与下行推送。

- `EMAIL_SENDER`

- `EMAIL_SMTP_HOST`

## 4. 用户注册、登录和鉴权实际测试

### 4.1 本地验证码注入

本地测试可以不依赖 SMTP，直接写入验证码 Redis key。仅限本地/测试环境使用。

验证码类型：
- `1`：注册
- `2`：登录
- `3`：重置密码
- `4`：换绑邮箱

PowerShell 示例会注册两个用户、登录并保存 token：

```powershell
$base = "http://localhost:8080"
$ts = [DateTimeOffset]::UtcNow.ToUnixTimeSeconds()
$emailA = "lcchat-a-$ts@example.com"
$emailB = "lcchat-b-$ts@example.com"
$pass = "Password123"
$deviceA = "win-dev-a-$([guid]::NewGuid())"
$deviceB = "win-dev-b-$([guid]::NewGuid())"

docker compose exec redis redis-cli SET "user:verify_code:${emailA}:1" "123456" EX 300
docker compose exec redis redis-cli SET "user:verify_code:${emailB}:1" "123456" EX 300

$registerA = @{
  email = $emailA
  password = $pass
  verifyCode = "123456"
  nickname = "TesterA"
} | ConvertTo-Json

$registerB = @{
  email = $emailB
  password = $pass
  verifyCode = "123456"
  nickname = "TesterB"
} | ConvertTo-Json

Invoke-RestMethod -Method Post -Uri "$base/api/v1/public/user/register" -ContentType "application/json" -Headers @{"X-Device-ID"=$deviceA} -Body $registerA
Invoke-RestMethod -Method Post -Uri "$base/api/v1/public/user/register" -ContentType "application/json" -Headers @{"X-Device-ID"=$deviceB} -Body $registerB

$loginBodyA = @{
  account = $emailA
  password = $pass
  deviceInfo = @{ deviceName = "PowerShell-A"; platform = "Windows"; osVersion = "local"; appVersion = "test" }
} | ConvertTo-Json -Depth 4

$loginBodyB = @{
  account = $emailB
  password = $pass
  deviceInfo = @{ deviceName = "PowerShell-B"; platform = "Windows"; osVersion = "local"; appVersion = "test" }
} | ConvertTo-Json -Depth 4

$loginA = Invoke-RestMethod -Method Post -Uri "$base/api/v1/public/user/login" -ContentType "application/json" -Headers @{"X-Device-ID"=$deviceA} -Body $loginBodyA
$loginB = Invoke-RestMethod -Method Post -Uri "$base/api/v1/public/user/login" -ContentType "application/json" -Headers @{"X-Device-ID"=$deviceB} -Body $loginBodyB

$tokenA = $loginA.data.accessToken
$tokenB = $loginB.data.accessToken
$userA = $loginA.data.userInfo.uuid
$userB = $loginB.data.userInfo.uuid
$authA = @{ Authorization = "Bearer $tokenA"; "X-Device-ID" = $deviceA }
$authB = @{ Authorization = "Bearer $tokenB"; "X-Device-ID" = $deviceB }

$userA
$userB
```

判断标准：
- 注册响应 `code == 0`。
- 登录响应 `code == 0`，并返回 `accessToken`、`refreshToken`、`userInfo.uuid`。
- Gateway 日志中同一请求能看到 `trace_id`，且没有服务器级 Error。

### 4.2 认证失败 smoke

```powershell
curl.exe -i http://localhost:8080/api/v1/auth/blacklist
```

预期：HTTP 401。注意本项目业务错误通常是 HTTP 200 + body.code；认证中间件可直接返回 401。

## 5. 好友关系实际测试

消息单聊发送会校验好友/黑名单关系，因此发送 P2P 消息前先建立好友关系。

```powershell
$applyBody = @{
  targetUuid = $userB
  reason = "local actual test"
  source = "manual"
} | ConvertTo-Json

$applyResp = Invoke-RestMethod -Method Post -Uri "$base/api/v1/auth/friend/apply" -ContentType "application/json" -Headers $authA -Body $applyBody
$applyId = $applyResp.data.applyId

$handleBody = @{
  applyId = $applyId
  action = 1
  remark = "accepted in local test"
} | ConvertTo-Json

Invoke-RestMethod -Method Post -Uri "$base/api/v1/auth/friend/apply/handle" -ContentType "application/json" -Headers $authB -Body $handleBody
Invoke-RestMethod -Method Get -Uri "$base/api/v1/auth/friend/list?page=1&pageSize=20" -Headers $authA
```

判断标准：
- 申请响应返回 `applyId`。
- B 处理申请响应 `code == 0`。
- A 的好友列表能看到 B。

## 6. 消息发送、拉取和下行推送测试

### 6.1 发送并拉取消息

```powershell
$msgBody = @{
  clientMsgId = [guid]::NewGuid().ToString()
  convType = 1
  targetUuid = $userB
  msgType = 1
  content = '{"text":"hello from actual test"}'
  atUsers = @()
} | ConvertTo-Json -Depth 4

$sendResp = Invoke-RestMethod -Method Post -Uri "$base/api/v1/auth/messages/send" -ContentType "application/json" -Headers $authA -Body $msgBody
$convId = $sendResp.data.convId
$msgId = $sendResp.data.msgId

$sendResp
Invoke-RestMethod -Method Get -Uri "$base/api/v1/auth/messages/pull?convId=$convId&anchorSeq=0&limit=20&direction=1" -Headers $authB
```

判断标准：
- 发送响应 `code == 0`，返回 `msgId`、`seq`、`convId`。
- B 拉取同一 `convId` 能看到刚发送的 `msgId`。
- 即使 Kafka 或 Push-Job 暂时失败，消息落库成功后仍应能通过 PullMessages 自愈拉取。

### 6.2 WebSocket 在线路由与下行推送

先让 B 在线。可使用 `wscat`、Postman 或自己的客户端连接：

```powershell
npm exec --yes wscat -- -c "ws://localhost:8081/ws?token=$tokenB&device_id=$deviceB"
```

连接后发送心跳时，客户端需要发送 Binary `MessageEnvelope{type:"heartbeat"}`：

```json
{"type":"heartbeat"}
```

预期收到：

```json
{"type":"heartbeat_ack"}
```

检查 Redis 路由表：

```powershell
docker compose exec redis redis-cli HGETALL "user:routing:${userB}"
```

预期能看到 `deviceB -> connect:9091` 一类的映射。保持 B 的 WebSocket 在线，再执行 [6.1](#61-发送并拉取消息) 的发送步骤：
- `msg` 日志应显示 Kafka 投递或非阻断告警。
- `message-push` 日志应显示消费、查路由、调用 Connect。
- `connect` 日志应显示 PushToUser/PushToDevice 或连接投递。
- `MSG_PUSH` 下行是 `MessageEnvelope` 二进制帧；真实客户端需要先解外层 `proto/connect/connect.proto`，再按 `type` 解 `data`，例如 `MSG_PUSH` 的 `data` 使用 `proto/msg/msg_common.proto` 中的 `MsgItem` 解码。
- 如果下行 `ack_required=true`，客户端应发送 `MessageEnvelope{type:"MSG_ACK", data: MessageAck{conv_id, seq, msg_id}}`。服务端只接受当前连接已成功下发过的 `conv_id + seq`，伪造更大 ACK 会收到 `type="error"` 且不会写 Redis ACK 位点。

如果没有收到下行推送，先不要判定消息失败：
1. 调 `PullMessages` 确认消息是否已落库。
2. 查 `user:routing:{user_uuid}` 是否存在接收方设备。
3. 看 `message-push` 是否因用户离线跳过投递。
4. 看 `connect` 是否因 device_id/token 不匹配拒绝握手。

## 7. 本地单服务调试

修改某一个服务时，可以只启动基础设施，再在 IDE/终端中运行目标服务：

```powershell
docker compose up -d mysql redis kafka minio
```

涉及 Kafka 的本地进程可能受到 Kafka advertised listener 影响；消息全链路实际测试优先用全 Docker Compose。

如果确实要在宿主机同时运行多个服务，注意端口不要与 Kafka 或 metrics 冲突。示例：

```powershell
# Terminal 1: user-service
$env:MYSQL_DSN = "root:root@tcp(localhost:3306)/chat_server?charset=utf8mb4&parseTime=True&loc=Local"
$env:REDIS_ADDR = "localhost:6379"
$env:USER_GRPC_ADDR = ":9094"
$env:USER_METRICS_ADDR = ":9194"
go run ./apps/user/cmd

# Terminal 2: msg-service，避免占用 Kafka 的 9092 宿主机端口
$env:MYSQL_DSN = "root:root@tcp(localhost:3306)/chat_server?charset=utf8mb4&parseTime=True&loc=Local"
$env:REDIS_ADDR = "localhost:6379"
$env:KAFKA_BROKERS = "localhost:9092"
$env:MSG_GRPC_ADDR = ":19092"
$env:MSG_METRICS_ADDR = ":19192"
go run ./apps/msg/cmd

# Terminal 3: gateway
$env:USER_SERVICE_ADDR = "localhost:9094"
$env:MSG_SERVICE_ADDR = "localhost:19092"
$env:GATEWAY_ADDR = ":8080"
go run ./apps/gateway/cmd
```

Connect/message-push 调试建议仍优先使用 Compose，或确保：
- `CONNECT_GRPC_ADDR` 与 user metrics 不冲突。
- `CONNECT_SELF_GRPC_ADDR` 写入 Redis 后，message-push 所在网络能访问。
- `MESSAGE_PUSH_HTTP_ADDR` 不与其他服务冲突。

## 8. 数据检查与清理

常用检查：

```powershell
# Redis 路由/验证码/幂等缓存
docker compose exec redis redis-cli KEYS "user:routing:*"
docker compose exec redis redis-cli KEYS "msg:idempotent:*"

# MySQL 表数据
docker compose exec mysql mysql -uroot -proot chat_server -e "SELECT a.user_uuid,email,p.nickname,a.status FROM user_account a LEFT JOIN user_profile p ON p.user_uuid = a.user_uuid ORDER BY a.id DESC LIMIT 5;"
docker compose exec mysql mysql -uroot -proot chat_server -e "SELECT conv_id,msg_id,from_uuid,seq,status FROM message ORDER BY id DESC LIMIT 5;"
docker compose exec mysql mysql -uroot -proot chat_server -e "SELECT owner_uuid,target_uuid,conv_id,unread_count FROM conversation ORDER BY id DESC LIMIT 10;"
```

停止服务但保留数据：

```powershell
docker compose down
```

彻底重置数据卷：

```powershell
docker compose down -v
```

`down -v` 会删除 MySQL、Redis、MinIO 数据；协作环境中不要擅自执行，必须先确认当前数据可以丢弃。

## 9. 常见问题排查

| 现象 | 优先检查 |
|---|---|
| PowerShell `curl` 行为异常 | 使用 `curl.exe`，或改用 `Invoke-RestMethod` |
| HTTP 200 但业务失败 | 看 body 的 `code/message/trace_id`，业务错误不会都映射成 HTTP 4xx |
| 登录 401 或 token 无效 | `Authorization: Bearer ...`、`X-Device-ID` 是否与登录设备一致 |
| 注册提示验证码错误/过期 | Redis key 是否为 `user:verify_code:{email}:1`，TTL 是否还在 |
| P2P 发消息失败 | 是否已成为好友；是否存在黑名单关系；targetUuid 是否是对方用户 UUID |
| 发送成功但收不到推送 | 先 PullMessages 验证落库，再查 Redis 路由表和 message-push/connect 日志 |
| 本地 msg-service 端口冲突 | Kafka 常占宿主机 9092，msg-service 本地 gRPC 改用 `:19092` |
| Kafka 本地连接异常 | 优先使用全 Docker Compose；宿主机进程可能受 advertised listener 影响 |
| MinIO 上传失败 | 检查 `MINIO_SECRET_KEY`、bucket 初始化、文件 MIME/扩展名校验 |

## 10. 测试记录模板

每次提交或交付前，建议在回复/PR 中记录：

```markdown
## 测试
- 编译/单元：`go test ./apps/...`，通过/失败原因
- 集成环境：`docker compose up -d --build`，核心服务 healthy
- 实际接口：注册/登录/好友/发消息/拉取消息，响应 code
- WebSocket：连接、心跳、路由表、下行推送结果
- 未覆盖：例如未验证真实 SMTP、未验证群聊、未验证 MinIO
```

原则：不要只写“已测试”。要给出命令、响应 `code`、关键 `trace_id` 或日志现象，便于复现。
