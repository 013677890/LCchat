# 调用链路与治理
本文描述 HTTP 到 gRPC 的调用治理、上下文传递、超时、日志和错误边界。

## HTTP 请求主路径
1. 客户端请求 gateway。
2. gateway 注入 `trace_id`、解析客户端 IP、记录请求指标。
3. 公开路由直接进入 handler；认证路由先经过 JWT 中间件和用户限流。
4. handler 将 DTO 转换为 Protobuf 请求，通过 gRPC 调用后端服务。
5. gateway 将 Protobuf 响应转换为 HTTP 响应结构。

## 元数据传递

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `trace_id` | gateway 生成或透传 | 串联 HTTP、gRPC、Kafka、WebSocket 日志。 |
| `user_uuid` | JWT 解析 | 标识当前登录用户。 |
| `device_id` | JWT 或 `X-Device-ID` | Token、消息幂等、多端同步和设备状态。 |
| `client_ip` | gateway/connect 中间件 | 风控、日志、验证码限流。 |

gateway 出站 gRPC 会透传这些元数据，下游服务通过拦截器或上下文工具读取。

## 超时预算
gateway 在 [apps/gateway/internal/router/router.go](../../apps/gateway/internal/router/router.go) 中为主要路由配置 1 到 3 秒请求预算：

| 类型 | 预算 | 示例 |
| --- | --- | --- |
| 轻量读 | 1 秒 | `/health`、二维码、在线状态。 |
| 常规读写 | 2 秒 | 登录、好友操作、会话设置、群资料。 |
| 重操作 | 3 秒 | 搜索、批量资料、上传头像、发送消息。 |

服务间 gRPC 调用应服从父级 context 的 deadline；如果父级预算更短，不能重新放大超时。

## 重试和熔断

### gRPC 配置式重试原则

**默认不重试；只有方法级显式白名单才允许自动重试。**

| 规则 | 说明 |
| --- | --- |
| 粒度 | 必须是完整 full method：`/package.Service/Method`（例如 `/group.GroupService/GetGroupInfo`）。 |
| 禁止 | 禁止只填 service 名的 Service 级重试；禁止按 Get/List/Search 前缀运行时推断；禁止非法方法名静默降级为无重试或 Service 级。 |
| 允许 | 只读查询，或已确认幂等/最后写入覆盖的方法。 |
| 默认禁止 | Register/Login/RefreshToken/SendVerifyCode、CreateGroup/AddMember、SendFriendApply、UpdateProfile、RecallMessage、SendMessage 等无充分幂等证明的写操作。 |
| SendMessage | 即使存在 `client_msg_id`，当前也**不**进白名单；若要恢复，必须有专项测试证明重复调用不会重复写 message、outbox 和会话副作用。 |
| 装配 | `pkg/grpcx.DefaultClientRetryConfig(fullMethods...)`；ServiceConfig 的 `name` 必须同时含 `service` 与 `method`。 |
| 校验 | 非法 full method、空 service/method、重复方法在 `NewClient` 时直接返回错误。 |
| Retry=nil | 仍生成 round_robin 负载均衡配置，不写入任何 retryPolicy。 |

### gateway 初始白名单范围

| 下游 | 可配置式重试的方法类型 |
| --- | --- |
| auth | 设备查询、在线状态、内部账号查询（如 `FindAccountByEmail`） |
| user | 获取资料、搜索、批量获取、二维码读 |
| relation | 列表、同步列表、关系检查、黑名单检查 |
| group | Get/List/Search/Check 类读取 |
| msg | Pull、BatchSync、GetMessages、GetConversations |

写接口（建群、加好友、发验证码、改密等）**默认不会**被 gRPC 自动重试。

### 内部服务客户端

| 调用方 → 被调方 | 配置式重试 |
| --- | --- |
| msg → group | 仅 `CheckGroupMember`、`CheckGroupSendPermission` |
| msg → relation | 仅 `CheckIsFriend`、`CheckIsBlacklist` |
| relation → auth | 仅 `BatchCheckAccountStatus`（好友申请前的目标账号存在性检查） |
| message-push → group | 仅 `GetGroupMemberIds`、`GetMemberList` |
| connect → auth | 仅已确认幂等的 `UpdateDeviceStatus` |
| message-push → connect | **不**配置自动重试，避免与 Kafka 消费重试叠加造成重复投递 |

### 其他

- 只对短暂不可用等可重试错误执行重试（ServiceConfig `retryableStatusCodes`）。
- 业务错误不重试，例如参数错误、权限不足、验证码错误。
- 方法级 deadline 由 `ClientTimeout` 拦截器负责；配置式重试默认不写入 service 级 `timeout`，避免钳制更大的方法预算。
- gateway 出站连接另装配熔断器；Kafka 消费链路根据错误类型区分永久错误和可重试错误。

## 限流

| 位置 | 策略 | 降级 |
| --- | --- | --- |
| gateway 全局 IP | Redis 黑名单 + 令牌桶，默认 10 rps、burst 20 | Redis 不可用时 Fail-Open（失败放行）。 |
| gateway 登录用户 | 默认 100 rps、burst 200 | Redis 不可用时 Fail-Open。 |
| gateway 敏感操作 | 修改密码、换绑邮箱、注销账号使用更严格用户限流 | 超限返回请求过于频繁。 |
| connect | WebSocket 入口限流 | 保护长连接入口。 |

## 错误边界
统一响应结构见 [api/00-接口通用规范.md](../api/00-接口通用规范.md)。业务错误使用业务码返回，系统错误使用 `30000` 段错误码。

- 服务内使用 `pkg/apperr` 表达业务错误。
- repository 与 domain repository 使用 `pkg/repoerr` 归一化 GORM、Redis 和驱动错误；service 通过 `errors.Is` 识别后再映射为 `apperr`，仓储层不直接创建业务错误。
- gRPC 出站前对错误做 Sanitize（脱敏），只传业务码和标准文案。
- gateway 业务失败使用 `result.Fail`，系统或上游错误使用 `result.FailServer`。
- HTTP 状态码策略：业务成功和业务失败通常返回 200；`30000` 段系统错误返回 500。

## 日志边界
- 最终请求日志只在 gateway HTTP、gateway 出站 gRPC、服务端 gRPC 拦截器、Recovery 中间件记录。
- 业务层不重复打印成功日志。
- 可降级失败记录 Warn，例如缓存失败、异步投递失败、设备状态同步失败。
- 敏感字段禁止记录原文，包括密码、验证码、完整 Token；HTTP 查询参数必须先脱敏，Recovery 不得转储 Authorization、Cookie 等完整请求头。

## WebSocket 差异
WebSocket 握手由 connect 处理，鉴权比 gateway HTTP 更严格：

1. 校验 token 和 `device_id` 是否存在。
2. 解析 JWT 并检查 claims 中的 `device_id` 与握手参数一致。
3. JWT 有效且未过期即允许握手，不读取 Redis AccessToken 状态。

登出、踢设备和注销会撤销 RefreshToken，但旧 AccessToken 在 `exp` 前仍可重新握手；当前实现
不会主动断开已经建立的 WebSocket。
