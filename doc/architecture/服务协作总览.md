# 服务协作总览

本文描述 LCChat 当前服务之间的协作方式。单个服务的内部结构见 [services](../services)，跨服务数据和事件见 [data](../data)。

## 协作原则

- Gateway 只做入口治理和聚合转发，不拥有业务数据。
- 每个业务服务只写自己拥有的表，跨域读取通过 gRPC 或缓存投影完成。
- 用户请求路径优先保持短链路，非关键副作用通过 Kafka 或异步任务完成。
- Redis 用于缓存和路由，不作为长期权威事实。
- Connect 只负责最后一公里连接和投递，不做消息、关系、群权限判断。

## 同步调用矩阵

| 调用方 | 被调方 | 协议 | 场景 |
| --- | --- | --- | --- |
| gateway | auth | gRPC | 注册、登录、验证码、Token、设备、账号安全。 |
| gateway | user | gRPC | 资料、搜索、头像、二维码、批量资料。 |
| gateway | relation | gRPC | 好友、黑名单、关系状态。 |
| gateway | group | gRPC | 群资料、群成员、入群申请、群管理。 |
| gateway | msg | gRPC | 消息发送、拉取、撤回、会话管理。 |
| connect | auth.DeviceService | gRPC | 连接建立、断开时异步同步设备在线状态。 |
| msg | relation | gRPC | 单聊发送前校验好友和黑名单。 |
| msg | group | gRPC | 群聊发送前校验群成员、角色和禁言；必要时获取群成员。 |
| message-push | group | gRPC | 群聊下行扩散和群类实时提醒前获取群成员/管理员 UUID 列表。 |
| message-push | connect | gRPC | 按 Redis 路由把消息或实时提醒投递到目标 connect 节点。 |
| user | auth.InternalAuthService | gRPC | 资料展示字段变更后同步登录冗余字段。 |

## 异步协作矩阵

| Topic | 来源 | 目标 | 一致性语义 |
| --- | --- | --- | --- |
| `user_created` | auth Outbox | user | 注册账号后最终创建用户资料。 |
| `profile_display_changed` | user | auth | 资料展示字段最终回写到登录冗余字段。 |
| `account.deleted` | auth Outbox | user、relation、group 等 | 注销后各域最终清理或标记不可见。 |
| `group.cache` | group Outbox | group Redis projector、msg membership projector | 群写模型分别投影到 Redis 和 msg 群成员会话读模型。 |
| `msg.push` | msg | message-push | 消息、撤回、已读、回执等下行事件最终推送。 |
| `realtime.push` | relation、group | message-push | 好友、关系、群申请和群状态等非消息类实时提醒。 |

## 数据所有权

| 数据 | 权威服务 | 主要读取方 | 说明 |
| --- | --- | --- | --- |
| 账号、Token、设备会话 | auth | gateway、connect | WebSocket 会额外校验 Redis 中的 AccessToken 哈希。 |
| 用户资料 | user | gateway、relation、group | 资料展示聚合优先通过 user 能力。 |
| 好友和黑名单 | relation | gateway、msg | msg 发送前依赖 relation 做权限校验。 |
| 群资料和成员 | group | gateway、msg、message-push | 群缓存投影用于高频读、消息推送扩散和群类实时提醒。 |
| 消息和会话 | msg | gateway、message-push | message-push 不写消息表，只消费下行事件。 |
| 在线路由和 ACK | connect | message-push、connect | 在线路由存 Redis，ACK 位点短期存 Redis；消息与提醒共用 `MessageEnvelope`。 |

## 请求与事件分层

| 层级 | 典型链路 | 失败处理 |
| --- | --- | --- |
| 请求内同步 | HTTP -> gateway -> gRPC -> service | 失败直接返回业务错误或系统错误。 |
| 请求内异步 | service 写库后启动短异步任务 | 失败只记录 Warn，不回滚已成立事实。 |
| Kafka 异步 | Outbox 或 Producer 写入 Kafka | 消费端幂等处理，可重试错误不提交或短重试。 |
| 客户端自愈 | PullMessages、BatchSyncMessages、会话同步、资料重新读取 | 下行推送失败时靠下一次拉取修正。 |

## gRPC 重试协作约定

跨服务 gRPC 客户端统一经 `pkg/grpcx.NewClient` 装配。配置式重试采用**方法级显式白名单**：

- 默认不重试任何方法。
- 仅对已确认安全的 full method（只读或幂等写）开启有界重试。
- message-push → connect 的 `PushToUser`/`PushToDevice` 不配置 gRPC 自动重试，避免与 Kafka 层重试叠加。
- 完整策略见 [调用链路与治理](./调用链路与治理.md)。

## 不变量

- 消息落库成功即代表发送事实成立，下行推送失败不改变消息状态。
- 群权限事实只以 group 为准，msg 只消费校验结果。
- 账号注销同步阶段只完成账号标记与 Token 清理，下游域通过事件最终收敛。
- Redis 路由可能短暂失真，下游必须按离线处理并允许客户端拉取补偿。
