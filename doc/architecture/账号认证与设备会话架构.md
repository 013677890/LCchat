# 账号认证与设备会话架构

本文从架构视角描述 LCChat 的账号认证、Token 生命周期、设备会话、WebSocket 鉴权与在线状态协作方式。它不逐条展开接口字段，而是回答以下问题：

1. 登录态由谁签发、谁校验、谁失效。
2. 为什么 AccessToken 保持无状态，而 RefreshToken、设备会话和在线路由需要服务端状态。
3. HTTP 鉴权、WebSocket 鉴权、设备管理和在线状态之间如何协作。

接口字段和前端对接细节见：

- [认证与账号接口](../api/01-认证与账号接口.md)
- [WebSocket协议](../api/06-WebSocket协议.md)
- [登录注册与Token](../flows/登录注册与Token.md)
- [设备在线与WebSocket生命周期](../flows/设备在线与WebSocket生命周期.md)

## 1. 核心目标

LCChat 的认证与设备架构同时满足以下目标：

| 目标 | 说明 |
| --- | --- |
| 统一身份 | HTTP、gRPC、WebSocket 都以同一 `user_uuid` 作为身份核心。 |
| 多端登录 | 同一账号可以在多个设备上共存，每台设备有独立 `device_id`。 |
| 设备可管理 | 用户可以查看设备列表、踢掉指定设备、查询在线状态。 |
| 登录态有界失效 | 登出、踢设备、注销后不能继续刷新；旧 AccessToken 在自身有效期内仍可鉴权和重新建连。 |
| 在线状态可观测 | 既能知道“这台设备登录过”，也能知道“它现在是否在线”。 |

## 2. 参与组件

| 组件 | 职责 |
| --- | --- |
| gateway | HTTP 入站鉴权、JWT claims 透传、设备 ID 透传。 |
| auth | 账号、Token、验证码、设备会话的权威服务。 |
| connect | WebSocket 握手、在线连接表、在线路由、ACK。 |
| Redis | RefreshToken、验证码、在线路由（presence）等短期状态。 |
| MySQL | `user_account`、`device_sessions` 等长期事实。 |
| message-push | 基于在线路由把下行消息投递到 connect。 |

## 3. 四类状态的职责边界

认证与设备体系不是靠单一状态完成，而是由四类状态共同构成：

### 3.1 账号事实：`user_account`

这是“这个用户是否存在、是否已注销、是否可登录”的长期事实。

| 状态 | 存储 | 用途 |
| --- | --- | --- |
| 账号信息 | MySQL `user_account` | 登录、注销、账号状态判断。 |
| 登录展示冗余 | `login_nickname`、`login_avatar` | 登录成功后返回最小用户资料。 |

### 3.2 设备会话事实：`device_sessions`

这是“这个用户在哪些设备上登录过”的长期事实。

| 状态 | 存储 | 用途 |
| --- | --- | --- |
| 设备 ID、平台、版本、IP | MySQL `device_sessions` | 设备列表、踢设备、最后活跃、状态展示。 |

设备会话不等于当前在线，只代表“存在一个设备级登录记录”。

### 3.3 Token 状态：无状态 AccessToken 与 `auth:rt/*`

AccessToken 是自包含 JWT，不写入 Redis。gateway 和 connect 都直接验证签名、有效期及必要
claims；服务端不维护 AccessToken 白名单或黑名单，因此已经签发的 AccessToken 会一直有效到
自身 `exp`。

RefreshToken 承担续期职责，是 Redis 中唯一持久化的 Token 状态：

| Key | 含义 |
| --- | --- |
| `auth:rt:{user_uuid}:{device_id}` | 当前设备的 RefreshToken。 |

该 Key 的核心价值是控制设备能否继续续期：

- 登出时删除；
- 踢设备时删除；
- 注销账号时删除；
- 刷新 AccessToken 时要求该值存在、匹配，并重新检查账号状态。

删除 RefreshToken 不会让旧 AccessToken 立即失效，也不会自动关闭已有 WebSocket；它只保证
客户端无法越过 AccessToken 的有限有效期继续获得新凭据。

### 3.4 在线路由状态：`user:routing/*`

这是“某台设备当前连接在哪个 connect 节点”的在线事实。

| Key | 结构 | 用途 |
| --- | --- | --- |
| `user:routing:{user_uuid}` | Hash，field=`device_id`，value=`connectGrpcAddr|lastActiveMs` | 实时下行、在线状态、精确投递。 |

它只描述“在线连接位置”，不描述账号或设备长期事实。

## 4. 登录态建立链路

### 4.1 登录输入

登录请求进入 gateway 后，核心输入包括：

| 输入 | 来源 | 作用 |
| --- | --- | --- |
| `account` / `password` 或 `email` / `verifyCode` | HTTP Body | 认证凭据。 |
| `X-Device-ID` | Header | 设备唯一 ID。 |
| `deviceInfo` | HTTP Body | 设备名称、平台、系统版本、App 版本。 |

### 4.2 auth 建立登录态

auth 在登录成功时会同步完成以下动作：

1. 校验账号状态和凭据。
2. 生成 AccessToken / RefreshToken。
3. 将 RefreshToken 写入 Redis；AccessToken 不落服务端存储。
4. 创建或更新 `device_sessions`。
5. 返回 Token 与最小登录资料给 gateway。

最终形成的状态分布：

| 状态 | 是否同步完成 | 是否影响登录成功返回 |
| --- | --- | --- |
| `user_account` 账号校验 | 是 | 是 |
| `auth:rt/*` RefreshToken | 是 | 是 |
| `device_sessions` 设备会话 | 尽力完成 | 否，失败时降级记录告警 |
| `user:routing/*` 在线路由 | 否，需要后续建 WebSocket | 否 |

也就是说：**登录成功不代表当前设备已经在线，只代表该设备已经具备建立在线连接的资格。**

## 5. HTTP 鉴权与 WebSocket 鉴权的区别

### 5.1 HTTP 鉴权

HTTP 请求通过 gateway 的 JWT 中间件建立调用身份。

gateway 的主要职责：

1. 解析 `Authorization: Bearer <access_token>`。
2. 提取 claims 中的 `user_uuid` 等身份字段。
3. 结合 `X-Device-ID` 形成设备上下文。
4. 把 `trace_id`、`user_uuid`、`device_id`、`client_ip` 透传给下游。

HTTP 层强调“请求级身份”。

### 5.2 WebSocket 鉴权

WebSocket 与 HTTP 使用同一套无状态 AccessToken 信任边界。connect 在握手时执行：

connect 在握手时执行：

1. `token` 必填。
2. `device_id` 必填。
3. JWT claims 中必须有 `user_uuid` 和 `device_id`。
4. claims 的 `device_id` 必须与 query `device_id` 一致。

这意味着：

- Redis 不参与 WebSocket 握手鉴权；
- 未过期且 claims 匹配的旧 AccessToken 仍可重新握手；
- 同一设备必须稳定复用同一个 `device_id`。

## 6. WebSocket 的失效窗口

采用纯 JWT 握手后，各类安全动作具有明确的有限窗口：

| 场景 | 当前行为 |
| --- | --- |
| 用户主动登出 | RefreshToken 被撤销；旧 AccessToken 在过期前仍可握手成功。 |
| 用户踢掉某台设备 | RefreshToken 被撤销；旧 AccessToken 在过期前仍可握手成功。 |
| 修改/重置密码 | 全部 RefreshToken 被撤销；旧 AccessToken 自然过期。 |
| 账号注销 | RefreshToken 被清理；旧 AccessToken 自然过期。 |

Redis 故障不会影响新 WebSocket 的 JWT 握手，但会影响在线路由、ACK 及实时投递可靠性。
当前连接建立后不会周期性重新校验 JWT，也不会因为 JWT 到期自动断开；到期只会阻止使用该
Token 再次握手。这一行为是现有实现边界，不能描述为“立即踢线”。

## 7. 设备会话与在线连接的关系

### 7.1 设备会话

设备会话由 auth 维护，典型用于：

- 设备列表；
- 踢设备；
- 离线设备的 last_seen（最后一次登录/上线/下线等状态迁移时刻）；
- 设备状态展示。

### 7.2 在线连接

在线连接由 connect 维护，典型用于：

- WebSocket 是否已建立；
- 当前设备在哪个 connect 节点；
- 是否可以实时收到消息。

二者关系如下：

| 问题 | 看哪类状态 |
| --- | --- |
| 这个设备登录过吗？ | `device_sessions` |
| 这个设备现在在线吗？ | `user:routing` + connect 内存连接 |
| 这个 AccessToken 还能继续鉴权吗？ | JWT 签名、claims 与 `exp` |
| 这个设备还能继续续期吗？ | `auth:rt/*` |

## 8. 在线路由与实时投递

设备建连成功后，connect 会在 `OnConnect` 阶段写入：

```text
key   = user:routing:{user_uuid}
field = {device_id}
value = {connectGrpcAddr}|{lastActiveMs}
```

该路由是 presence 契约的事实源：connect 是唯一写方，**每个应用层心跳无条件刷新**
`lastActiveMs` 与 key TTL，断连时 CAS 删除。消费方统一通过 `pkg/presence` 读取并按
各自窗口过滤：

1. message-push 处理 `msg.push` 时查询在线路由；
2. 按路由中的 `connectGrpcAddr` 将目标设备分组，不同节点有界并发；
3. 完整用户目标调用 `PushToUser`，由 connect 广播到该用户在本节点的全部设备；
4. 需要排除当前设备的多端同步目标逐设备调用 `PushToDevice`；
5. connect 把消息写入本节点对应设备的 WebSocket 连接；
6. auth 的在线状态接口同样以该路由为在线判据（见第 9 节）。

所以在线路由既是"消息最后一公里"的路由表，也是在线状态的唯一事实源。

## 9. 在线状态与设备状态同步链路

**在线判定完全以 presence 路由为准**：设备在窗口（`PRESENCE_ONLINE_WINDOW_SECONDS`，
默认 120s）内有存活 WS 连接才算在线；纯 HTTP 活跃不算在线（没有 WS 就收不到实时推送，
展示在线反而失真）。auth 聚合时会防御性排除会话已处于 `logged_out` / `kicked` 终态的设备。

connect 在连接生命周期内异步回写 auth 的设备状态：

| 时机 | 动作 |
| --- | --- |
| OnConnect | 无条件写入路由；上报设备在线。 |
| OnHeartbeat | 无条件刷新路由 `lastActiveMs` 与 TTL（presence 新鲜度=心跳新鲜度）。 |
| OnDisconnect | CAS 删除路由；上报设备离线（该迁移时刻即离线设备的 last_seen）。 |

这意味着在线状态的分工是：

- connect 负责实时感知，是路由的唯一写方；
- auth 只做聚合展示：路由（在线判据）× 设备会话（平台元数据与终态排除）；
- gateway 通过 auth 暴露设备列表与在线状态接口。

## 10. 踢设备与登出的架构意义

### 10.1 登出

登出本质上是：

1. 删除该设备的 RefreshToken；
2. 更新设备会话状态；
3. HTTP 与 WebSocket 都继续接受尚未过期的旧 AccessToken；已有 WebSocket 也不会主动断开；
4. AccessToken 到期后，因为 RefreshToken 已被撤销，设备无法继续续期。

### 10.2 踢设备

当前踢设备与登出使用相同的 Token 失效边界：

1. 删除目标设备 RefreshToken；
2. 将设备会话状态更新为 `kicked`；
3. 不调用 connect `KickConnection`，因此已有 WebSocket 不会主动断开；
4. 未过期的旧 AccessToken 仍可重新握手，直到 `exp` 后才因无法续期而彻底失效。

所以“踢设备”同时作用于：

- 长期设备事实；
- RefreshToken 续期状态；
- 设备会话展示状态。

## 11. 故障与一致性边界

### 11.1 Redis 异常

| 场景 | 策略 |
| --- | --- |
| 登录后写 RefreshToken 失败 | 阻断登录成功成立，不返回 AccessToken。 |
| WebSocket 握手期间 Redis 不可用 | JWT 鉴权不受影响；路由与 ACK 能力可能降级。 |
| 在线路由刷新失败 | 影响实时投递，但不等于设备会话丢失。 |

### 11.2 connect 异常退出

如果 connect 进程异常退出：

- 内存连接立即消失；
- Redis 路由可能暂时残留；
- 路由依赖 TTL 过期或后续清理自愈；
- 前端需要重连并补拉消息。

### 11.3 auth 状态同步失败

如果 connect 回写 auth 的在线/离线状态失败：

- WebSocket 连接本身仍可能正常，在线判定不受影响（以路由为准）；
- 设备列表里的状态徽标和离线 last_seen 可能短暂不准；
- 后续重连或状态同步可修正。

## 12. 安全边界

账号与设备体系有几个必须坚持的边界：

1. `device_id` 不能随意漂移，否则多端管理和 RefreshToken 撤销都会混乱。
2. Token 原文不能写日志，只能使用摘要或脱敏信息。
3. gateway 与 connect 必须使用相同 JWT 密钥和 claims 校验规则。
4. 刷新 AccessToken 时必须同时校验 RefreshToken 和账号当前状态。
5. 踢设备、登出、注销只撤销续期能力；旧 AccessToken 的有限失效窗口必须作为明确契约保留。
