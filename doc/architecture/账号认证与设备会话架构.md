# 账号认证与设备会话架构

本文从架构视角描述 LCChat 的账号认证、Token 生命周期、设备会话、WebSocket 鉴权与在线状态协作方式。它不逐条展开接口字段，而是回答以下问题：

1. 登录态由谁签发、谁校验、谁失效。
2. 为什么项目同时维护 JWT、Redis Token 哈希、设备会话和在线路由。
3. HTTP 鉴权、WebSocket 鉴权、设备管理和在线状态之间如何协作。

接口字段和前端对接细节见：

- [认证与账号接口](../api/01-认证与账号接口.md)
- [WebSocket协议](../api/06-WebSocket协议.md)
- [登录注册与Token](../flows/登录注册与Token.md)
- [设备在线与WebSocket生命周期](../flows/设备在线与WebSocket生命周期.md)

## 1. 核心目标

LCChat 的认证与设备架构同时满足以下目标：

| 目标 | 说明 |
| --- | --- |
| 统一身份 | HTTP、gRPC、WebSocket 都以同一 `user_uuid` 作为身份核心。 |
| 多端登录 | 同一账号可以在多个设备上共存，每台设备有独立 `device_id`。 |
| 设备可管理 | 用户可以查看设备列表、踢掉指定设备、查询在线状态。 |
| 登录态可立即失效 | 登出、踢设备、注销后，旧 Token 不能继续建连。 |
| 在线状态可观测 | 既能知道“这台设备登录过”，也能知道“它现在是否在线”。 |

## 2. 参与组件

| 组件 | 职责 |
| --- | --- |
| gateway | HTTP 入站鉴权、JWT claims 透传、设备 ID 透传。 |
| auth | 账号、Token、验证码、设备会话的权威服务。 |
| connect | WebSocket 握手、在线连接表、在线路由、ACK。 |
| Redis | Token 哈希、验证码、设备活跃、在线路由等短期状态。 |
| MySQL | `user_account`、`device_sessions` 等长期事实。 |
| message-push | 基于在线路由把下行消息投递到 connect。 |

## 3. 四类状态的职责边界

认证与设备体系不是靠单一状态完成，而是由四类状态共同构成：

### 3.1 账号事实：`user_account`

这是“这个用户是否存在、是否已注销、是否可登录”的长期事实。

| 状态 | 存储 | 用途 |
| --- | --- | --- |
| 账号信息 | MySQL `user_account` | 登录、注销、账号状态判断。 |
| 登录展示冗余 | `login_nickname`、`login_avatar` | 登录成功后返回最小用户资料。 |

### 3.2 设备会话事实：`device_sessions`

这是“这个用户在哪些设备上登录过”的长期事实。

| 状态 | 存储 | 用途 |
| --- | --- | --- |
| 设备 ID、平台、版本、IP | MySQL `device_sessions` | 设备列表、踢设备、最后活跃、状态展示。 |

设备会话不等于当前在线，只代表“存在一个设备级登录记录”。

### 3.3 Token 短期状态：`auth:at/*`、`auth:rt/*`

这是“当前这对用户+设备的 Token 是否仍被服务端承认”的短期状态。

| Key | 含义 |
| --- | --- |
| `auth:at:{user_uuid}:{device_id}` | AccessToken 的 MD5 摘要。 |
| `auth:rt:{user_uuid}:{device_id}` | RefreshToken 的 MD5 摘要。 |

它的核心价值不是存原文，而是提供“立即失效能力”：

- 登出时删除；
- 踢设备时删除；
- 注销账号时删除；
- WebSocket 握手时强校验该值是否仍存在且匹配。

### 3.4 在线路由状态：`user:routing/*`

这是“某台设备当前连接在哪个 connect 节点”的在线事实。

| Key | 结构 | 用途 |
| --- | --- | --- |
| `user:routing:{user_uuid}` | Hash，field=`device_id`，value=`connectGrpcAddr|lastActiveMs` | 实时下行、在线状态、精确投递。 |

它只描述“在线连接位置”，不描述账号或设备长期事实。

## 4. 登录态建立链路

### 4.1 登录输入

登录请求进入 gateway 后，核心输入包括：

| 输入 | 来源 | 作用 |
| --- | --- | --- |
| `account` / `password` 或 `email` / `verifyCode` | HTTP Body | 认证凭据。 |
| `X-Device-ID` | Header | 设备唯一 ID。 |
| `deviceInfo` | HTTP Body | 设备名称、平台、系统版本、App 版本。 |

### 4.2 auth 建立登录态

auth 在登录成功时会同步完成以下动作：

1. 校验账号状态和凭据。
2. 生成 AccessToken / RefreshToken。
3. 将 Token 摘要写入 Redis。
4. 创建或更新 `device_sessions`。
5. 返回 Token 与最小登录资料给 gateway。

最终形成的状态分布：

| 状态 | 是否同步完成 | 是否影响登录成功返回 |
| --- | --- | --- |
| `user_account` 账号校验 | 是 | 是 |
| `auth:at/*` / `auth:rt/*` Token 摘要 | 是 | 是 |
| `device_sessions` 设备会话 | 是 | 是 |
| `user:routing/*` 在线路由 | 否，需要后续建 WebSocket | 否 |

也就是说：**登录成功不代表当前设备已经在线，只代表该设备已经具备建立在线连接的资格。**

## 5. HTTP 鉴权与 WebSocket 鉴权的区别

### 5.1 HTTP 鉴权

HTTP 请求通过 gateway 的 JWT 中间件建立调用身份。

gateway 的主要职责：

1. 解析 `Authorization: Bearer <access_token>`。
2. 提取 claims 中的 `user_uuid` 等身份字段。
3. 结合 `X-Device-ID` 形成设备上下文。
4. 把 `trace_id`、`user_uuid`、`device_id`、`client_ip` 透传给下游。

HTTP 层强调“请求级身份”。

### 5.2 WebSocket 鉴权

WebSocket 鉴权比 HTTP 更严格，因为连接一旦建立会持续存在，必须支持“被踢后立即失效”。

connect 在握手时执行：

1. `token` 必填。
2. `device_id` 必填。
3. JWT claims 中必须有 `user_uuid` 和 `device_id`。
4. claims 的 `device_id` 必须与 query `device_id` 一致。
5. Redis `auth:at:{user_uuid}:{device_id}` 中的 Token MD5 必须匹配。

这意味着：

- WebSocket 不是“只要 JWT 没过期就能连”；
- Token 被服务端失效后，后续握手必须失败；
- 同一设备必须稳定复用同一个 `device_id`。

## 6. 为什么 WebSocket 要额外校验 Redis Token 哈希

如果只校验 JWT，会有一个严重问题：

| 场景 | 只校验 JWT 的后果 |
| --- | --- |
| 用户主动登出 | 旧 Token 在过期前仍可握手成功。 |
| 用户踢掉某台设备 | 被踢设备仍可继续重连。 |
| 账号注销 | 已拿到的旧 Token 仍可能继续使用一段时间。 |

所以 connect 采用 **Fail-Close（失败关闭）** 策略：

- Redis 缺失或不匹配 -> 直接拒绝；
- Redis 异常 -> 也拒绝，而不是放行。

这样做是为了优先保证安全边界，而不是优先保证连通性。

## 7. 设备会话与在线连接的关系

### 7.1 设备会话

设备会话由 auth 维护，典型用于：

- 设备列表；
- 踢设备；
- 最后活跃时间；
- 设备状态展示。

### 7.2 在线连接

在线连接由 connect 维护，典型用于：

- WebSocket 是否已建立；
- 当前设备在哪个 connect 节点；
- 是否可以实时收到消息。

二者关系如下：

| 问题 | 看哪类状态 |
| --- | --- |
| 这个设备登录过吗？ | `device_sessions` |
| 这个设备现在在线吗？ | `user:routing` + connect 内存连接 |
| 这个设备还能继续鉴权吗？ | `auth:at/*` |

## 8. 在线路由与实时投递

设备建连成功后，connect 会在 `OnConnect` 阶段写入：

```text
key   = user:routing:{user_uuid}
field = {device_id}
value = {connectGrpcAddr}|{lastActiveMs}
```

后续协作关系：

1. message-push 查询在线路由；
2. 得到目标设备所在的 connect 节点地址；
3. 调用 connect gRPC `PushToDevice`；
4. connect 把消息写入本节点该设备的 WebSocket 连接。

所以在线路由是“消息最后一公里”的路由表，而不是业务缓存。

## 9. 设备状态同步链路

connect 在连接生命周期内会异步回写 auth 的设备状态：

| 时机 | 动作 |
| --- | --- |
| OnConnect | 上报设备在线。 |
| OnHeartbeat / 活跃事件 | 批量同步设备活跃时间。 |
| OnDisconnect | 上报设备离线。 |

这意味着在线状态不是单点维护，而是：

- connect 负责实时感知；
- auth 负责设备事实展示；
- gateway 通过 auth 暴露设备列表与在线状态接口。

## 10. 踢设备与登出的架构意义

### 10.1 登出

登出本质上是：

1. 删除该设备的 AccessToken / RefreshToken 摘要；
2. 更新设备会话状态；
3. 后续该设备的 HTTP / WebSocket 使用旧 Token 都应失败。

### 10.2 踢设备

踢设备本质上比登出更强：

1. 删除目标设备 Token 摘要；
2. 若能定位 connect 节点，则立即调用 `KickConnection` 断开现有连接；
3. 即使当前连接未被立即断开，后续重连也会失败。

所以“踢设备”同时作用于：

- 长期设备事实；
- Token 短期状态；
- 当前在线连接。

## 11. 故障与一致性边界

### 11.1 Redis 异常

| 场景 | 策略 |
| --- | --- |
| 登录后写 Token 哈希失败 | 应阻断登录成功成立。 |
| WebSocket 握手读 Token 哈希失败 | Fail-Close，拒绝连接。 |
| 在线路由刷新失败 | 影响实时投递，但不等于设备会话丢失。 |

### 11.2 connect 异常退出

如果 connect 进程异常退出：

- 内存连接立即消失；
- Redis 路由可能暂时残留；
- 路由依赖 TTL 过期或后续清理自愈；
- 前端需要重连并补拉消息。

### 11.3 auth 状态同步失败

如果 connect 回写 auth 的在线/离线或活跃时间失败：

- WebSocket 连接本身仍可能正常；
- 设备列表里的在线状态和最后活跃时间可能短暂不准；
- 后续心跳、重连或状态同步可修正。

## 12. 安全边界

账号与设备体系有几个必须坚持的边界：

1. `device_id` 不能随意漂移，否则多端管理和 Token 失效都会混乱。
2. Token 原文不能写日志，只能使用摘要或脱敏信息。
3. WebSocket 握手必须校验 Redis Token 哈希，不能只依赖 JWT。
4. 踢设备、登出、注销账号后，旧设备不应继续建立新连接。
