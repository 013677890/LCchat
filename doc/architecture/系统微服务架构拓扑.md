 # 系统微服务架构拓扑

 本文从系统整体视角描述 LCChat 当前微服务架构拓扑，重点回答以下问题：

 1. 系统由哪些服务和基础设施组成。
 2. 外部请求、内部同步调用、异步事件、长连接下行分别经过哪些节点。
 3. 数据所有权如何划分，为什么不能跨服务直接读写。
 4. 哪些链路追求强一致，哪些链路接受最终一致。

 单个服务内部实现见 [services](../services)，核心链路细节见 [flows](../flows)，事件与存储契约见 [data](../data)。

 ## 1. 总体分层

 当前系统可以拆成五层：

 | 层级 | 组件 | 主要职责 |
 | --- | --- | --- |
 | 接入层 | `gateway`、`connect` | HTTP API 入口、WebSocket 长连接入口。 |
 | 业务服务层 | `auth`、`user`、`relation`、`group`、`msg`、`message-push` | 承载账号、资料、关系、群、消息、下行扩散等业务能力。 |
 | 存储层 | MySQL、Redis、MinIO | 长期业务事实、缓存与短期状态、对象存储。 |
 | 事件层 | Kafka、Kafka Connect、Debezium | Outbox CDC、领域事件分发、消息下行事件分发。 |
 | 可观测与运维层 | Prometheus、Docker Compose、环境变量配置 | 指标暴露、本地编排、运行参数注入。 |

 其中两个入口节点的职责必须区分清楚：

 - `gateway` 负责短连接 HTTP 请求；
 - `connect` 负责长连接 WebSocket 会话；
 - 两者都不拥有完整业务事实，只是入口与转发边界。

 ## 2. 系统拓扑总览

 可以把当前系统理解为“一个 HTTP 入口 + 一个连接入口 + 五个核心业务域 + 一个消息下行桥接层 + 三类基础设施”的组合。

 ### 2.1 入口与业务服务关系

 | 节点 | 入站来源 | 主要出站依赖 | 说明 |
 | --- | --- | --- | --- |
 | `gateway` | 浏览器 / App HTTP 请求 | auth、user、relation、group、msg | 统一 API 入口，不写业务表。 |
 | `connect` | 浏览器 / App WebSocket 连接 | auth、Redis | 建连鉴权、在线路由、ACK、长连接生命周期。 |
 | `auth` | gateway、connect | MySQL、Redis、Kafka Outbox | 账号、Token、设备会话。 |
 | `user` | gateway、Kafka | MySQL、Redis、auth | 用户资料和资料展示冗余同步。 |
 | `relation` | gateway、msg | MySQL、Redis | 好友、黑名单、申请。 |
 | `group` | gateway、msg、message-push | MySQL、Redis、Kafka Outbox | 群资料、成员、申请、缓存投影。 |
 | `msg` | gateway | MySQL、Redis、relation、group、Kafka | 消息与会话事实、下行事件生产。 |
 | `message-push` | Kafka `msg.push` | group、connect、Redis | Kafka 到长连接下行的桥接层。 |

 ### 2.2 基础设施关系

 | 基础设施 | 被哪些服务使用 | 用途 |
 | --- | --- | --- |
 | MySQL | auth、user、relation、group、msg | 长期业务事实权威存储。 |
 | Redis | gateway、auth、user、relation、group、msg、connect、message-push | 限流、验证码、Token 哈希、缓存、幂等、在线路由、ACK 位点。 |
 | Kafka | auth、user、group、msg、message-push | 领域事件和消息下行事件总线。 |
 | Kafka Connect / Debezium | auth、group 等 Outbox 生产方 | 监听 `outbox_events`，把本地事务事件安全投递到 Kafka。 |
 | MinIO | gateway、user | 用户头像等对象存储。 |

 ## 3. 同步调用拓扑

 同步调用面决定了“一个用户请求在返回前必须经过哪些节点”。

 ### 3.1 HTTP 请求主拓扑

 ```text
 Client
   -> gateway
      -> auth / user / relation / group / msg
         -> MySQL / Redis / MinIO
 ```

 关键特点：

 1. 所有 HTTP 业务请求先进入 `gateway`。
 2. `gateway` 负责 DTO 转换、JWT 鉴权、超时、限流、日志和错误映射。
 3. 真正的业务规则下沉到后端 gRPC 服务中。
 4. 请求返回前必须完成的事实，一般在同一个同步链路内落到 MySQL 或 Redis。

 ### 3.2 服务间同步依赖图

 | 调用方 | 被调方 | 原因 |
 | --- | --- | --- |
 | gateway | auth | 注册、登录、验证码、刷新 Token、设备管理、账号安全。 |
 | gateway | user | 用户资料、二维码、头像、搜索、在线状态聚合展示。 |
 | gateway | relation | 好友、黑名单、申请与关系状态。 |
 | gateway | group | 群资料、群成员、群申请、群管理。 |
 | gateway | msg | 发送消息、拉取消息、会话管理。 |
 | connect | auth.DeviceService | 连接建立、断开、活跃时同步设备状态。 |
 | msg | relation | 单聊发送前校验好友和黑名单关系。 |
 | msg | group | 群聊发送前校验群成员、角色、禁言和群状态。 |
 | message-push | group | 群消息扩散前查询群成员集合。 |
 | message-push | connect | 根据路由把下行数据投递到目标 connect 节点。 |
 | user | auth.InternalAuthService | 用户展示字段变化后回写登录冗余字段。 |

 这里最重要的不变量是：**业务服务之间允许同步读能力，但不允许跨域直接写对方的权威表。**

 ## 4. 异步事件拓扑

 异步事件面解决的是“主事实已经成立，但副作用或跨域同步可以稍后收敛”的问题。

 ### 4.1 当前事件主干

 | Topic | 生产方 | 消费方 | 作用 |
 | --- | --- | --- | --- |
 | `user_created` | auth Outbox | user | 注册后异步创建用户资料。 |
 | `profile_display_changed` | user | auth | 资料展示字段变更后回写登录冗余。 |
 | `account.deleted` | auth Outbox | user、relation、group 等 | 账号注销后各业务域最终清理。 |
 | `group.cache` | group Outbox | group Redis projector、msg membership projector | 群写模型异步投影到 Redis 缓存和 msg 会话读模型。 |
 | `msg.push` | msg | message-push | 新消息、撤回、已读、回执等下行事件。 |

 ### 4.2 Outbox 拓扑

 对于账号注销、注册建档、群缓存投影等“本地事务 + 事件发布”场景，当前系统采用 Outbox（发件箱）模式：

 ```text
 Business Service
   -> local transaction writes business table + outbox_events
      -> Debezium captures binlog
         -> Kafka Connect EventRouter
            -> Kafka topic
               -> downstream consumer
 ```

 这样设计的原因：

 1. 避免“数据库提交成功但事件没发出去”的双写不一致。
 2. 让下游服务只消费 Kafka 事件，不反查上游库。
 3. 保证上游服务的数据所有权不被下游破坏。

 ### 4.3 最终一致性边界

 | 场景 | 一致性类型 | 说明 |
 | --- | --- | --- |
 | 登录、发消息、更新资料、改群设置 | 请求内强一致 | 返回成功前，主事实已经落库或完成必要状态更新。 |
 | 注册后创建资料 | 最终一致 | auth 成功后，user 通过事件补齐资料。 |
 | 资料展示冗余回写 | 最终一致 | auth 中 `login_nickname/login_avatar` 允许短暂滞后。 |
 | 账号注销下游清理 | 最终一致 | 注销同步阶段只做 auth 主事实和 Token 失效。 |
 | 群缓存投影 | 最终一致 | Redis 群缓存允许短暂滞后于 MySQL。 |
 | 消息下行 | 最终一致 | 消息落库成功即发送成立，实时推送只是附加体验。 |

 ## 5. 长连接与下行拓扑

 长连接面是系统与普通 CRUD 服务最不一样的部分。

 ### 5.1 建连拓扑

 ```text
 Client
   -> connect (/ws)
      -> JWT parse
      -> Redis auth:at:{user_uuid}:{device_id} hash check
      -> auth.DeviceService async status sync
      -> Redis user:routing:{user_uuid}
 ```

 connect 不参与消息持久化，也不做关系、群权限判断，它只做三件事：

 1. 连接鉴权；
 2. 在线路由登记；
 3. WebSocket 收发与 ACK 管理。

 ### 5.2 下行拓扑

 ```text
 msg
   -> Kafka(msg.push)
      -> message-push
         -> Redis online routing lookup
         -> connect gRPC PushToDevice / PushToUser
            -> WebSocket client
 ```

 这里 `message-push` 的定位非常关键：

 - 它不是消息事实服务；
 - 它不写消息表；
 - 它也不是连接服务本身；
 - 它是 **Kafka 事件到在线设备投递之间的桥接层**。

 这样拆开的收益是：

 1. `msg` 可以专注消息事实和会话事实。
 2. `connect` 可以专注连接生命周期和节点内投递。
 3. `message-push` 可以专注多端扩散、路由查找和投递策略。

 ## 6. 数据所有权拓扑

 当前系统是按领域切分数据所有权的，不能把所有表当作一个大单体数据库来用。

 | 领域 | 权威服务 | 典型表 / 状态 | 其他服务如何读取 |
 | --- | --- | --- | --- |
 | 账号与设备 | auth | `user_account`、`device_sessions`、Token 哈希 | 通过 gRPC 或 Redis 校验结果读取。 |
 | 用户资料 | user | `user_profile` | 通过 user gRPC 获取。 |
 | 好友与黑名单 | relation | `user_relations`、`apply_requests` | 通过 relation gRPC 获取。 |
 | 群资料与成员 | group | `groups`、`group_members`、`group_join_requests` | 通过 group gRPC 或缓存投影读取。 |
 | 消息与会话 | msg | `message`、`conversation`、`group_conversation` | 通过 msg gRPC 获取。 |
 | 在线路由与 ACK | connect | Redis 路由、ACK 位点、节点内连接表 | 通过 connect gRPC 或 Redis 路由消费。 |

 这套边界背后的规则是：

 1. **谁写表，谁负责业务语义正确性。**
 2. **跨域读取优先走 gRPC，热点读再考虑缓存投影。**
 3. **下游服务不能为了省事直接连表替代领域能力。**

 ## 7. 三条核心主链路

 从系统级拓扑看，当前项目最重要的是三条主链路。

 ### 7.1 账号主链路

 ```text
 Client -> gateway -> auth -> MySQL/Redis
                      -> Kafka(outbox) -> user / others
 ```

 作用：完成注册、登录、Token、设备会话、账号注销及下游清理触发。

 ### 7.2 消息主链路

 ```text
 Client -> gateway -> msg -> MySQL(message/conversation)
                        -> Kafka(msg.push) -> message-push -> connect -> Client
 ```

 作用：完成消息事实落库、会话更新和实时下行。

 ### 7.3 群协作主链路

 ```text
 Client -> gateway -> group -> MySQL(groups/group_members/...)
                          -> outbox -> Kafka(group.cache)
                                      ├-> group -> Redis cache projection
                                      └-> msg -> conversation membership projection
                          -> msg / message-push synchronous permission/fanout reads
 ```

 作用：完成群资料、成员、申请和高频读缓存投影。

 ## 8. 为什么采用这种拓扑

 当前拓扑不是为了“服务越多越高级”，而是为了解决几类明确问题：

 | 问题 | 对应设计 |
 | --- | --- |
 | HTTP 请求和 WebSocket 长连接生命周期完全不同 | 拆分 `gateway` 与 `connect`。 |
 | 消息事实与实时下行耦合会导致职责过重 | 拆分 `msg` 与 `message-push`。 |
 | 群高频读和群写模型冲突 | `group` 维护 MySQL 写模型，再投影 Redis 缓存。 |
 | 双写 Kafka 和 MySQL 容易不一致 | 使用 Outbox + Debezium。 |
 | 多端在线和精确投递需要独立路由层 | `connect` + Redis routing。 |

 ## 9. 系统级不变量

 - `gateway` 是 HTTP 入口，不拥有业务数据。
 - `connect` 是连接入口，不做消息、关系、群权限判断。
 - `msg` 以消息落库成功作为发送成功判定点，而不是以下行成功为准。
 - `group` 是群权限和群成员事实的唯一权威来源。
 - `auth` 是账号、Token 和设备会话的唯一权威来源。
 - Redis 可以失真、过期或被回收，因此不能替代 MySQL 长期事实。
 - Kafka 只负责事件传播和最终一致，不承载主业务真相。
